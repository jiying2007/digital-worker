# 产品专家团整体架构

> 本文档依据 `product-expert-team/` 插件源码逐项核对后同步（核对基线：`.codebuddy-plugin/plugin.json` version 5\.3\.0，`config/workflow.yaml` sop v4\.3，共 54 个 Skill、33 个 Schema、4 份专家 I/O 契约）。

## 1\. 插件是什么

产品专家团（`product-expert-team`）是一个 **团队型（expertType: team）专家插件**，入口 Agent 为 `product-expert-team-team-lead`（主理人），统辖四位正式专家：

|Agent|中文名|职责域|
|---|---|---|
|`product-expert-team-team-lead`|主理人|路由、编排、门禁、收口（不直接产出专业结论）|
|`pm-market-research-expert`|市场调研专家|市场机会发现与战略论证（Go/Pilot/Watch/Exit）|
|`requirement-analysis-expert`|需求分析专家|需求工程：业务问题定义→场景→痛点→分类→规格化→SRS/RTM/基线|
|`product-definition-expert`|产品定义专家|产品定型与功能/性能/PRD/路线图/埋点/验证策略|
|`product-designer`|产品设计专家|IA/交互/线框/高保真/设计系统/产品化（BOM/三新/卖点/包装）|

主线为**串行闭环**：市场调研是完整立项链路的首入口，但**不是唯一能力**——已有产品改造、PRD 审查、技术可行性评审、设计模块优化等任务可按任务类型直达对应专家（见本文档 §5）。

官方入口话术（`plugin.json`）要求用户先交代：任务类型、目标用户、要解决的问题、期望交付、不做范围、约束、已有资料、行业/领域；主理人"不处理通用百科问答、无证据硬编结论、跨行业临时拼装专家团、无限制战略咨询"。

## 3\. 编排状态机（`config/workflow.yaml`，sop v4\.3）

**设计原则**：Gate 0 管"需求是否清楚"；Gate K 管"行业 profile / 行业知识包 / 通用知识源是否真可用"；Gate M 管"已有产品资料是否接入完整"；C0/C1 缺口必须主理人统一澄清或取得降级确认；市场调研/需求分析/产品定义/产品设计均以 `run-state + checkpoint + resume` 断点续跑，不整段重跑；人工门禁保留为判断节点，AI 只做机械预检与材料整理，不替代人工拍板。

|---|---|---|---|---|---|---|

|`gate.integration.human`|最终整合验收|主理人 \+ 用户|

### 3\.3 回流 / 恢复 Transition

- 缺资料（material/knowledge）→ `ask_user_or_confirm_degradation`，每轮最多 3 个澄清问题，确认降级才前进，否则停止。

- 长阶段超限 → 携带 run\-state 从 `failed_stage/step/task` 续跑：市场调研按 Stage、需求分析按 Step1–9、产品定义按 Step1–8、产品设计按 Task（Scope→IA→Wireframe→HifiUI→DesignSystem→Productization）。

- 整合验证断链 → `integration_fail` 回流责任阶段（最多 1 次）。

- 机械预检 / 人工门禁连续 2 次不过 → `auto_fail`/`human_fail` 升级为人工强制决策（通过并记录风险 / 放弃 / 降级运行）。

- 下游发现上游数据不足 → `cross_stage_reflow` 回退一次，仍不足则降级运行并标注缺口。

- PRD 在 phase6 后被修订 → `prd_change_propagation`，`prd-impact-analyzer` 评估影响面并增量更新，不整体返工。

## 4\. 运行治理机制

- 每个关键 Gate 后更新 `team-run-state` 与 `gate-ledger`；每次跳过的专家、每次降级决策都要留痕（`degradation_decisions`、skip reason）。

- 每次收尾（含单点/短链路）必须运行 `deliverable-packager`：产物按四类归入
`00_交付物 / 01_过程资产 / 02_门禁与运行日志 / 03_数据资产`，
正式交付同时遵循 `output_envelope` 的 Markdown/JSON 双轨口径，并生成《交付清单\.md》与 `deliverable-manifest.json`；未生成交付清单不得宣称完成。

- PRD 命名需按 `config/prd-output-modes.yaml` 区分：模块化 PRD 包实际落盘使用 `00_总览.md`、`prd-package-index.json`、`module-prd.json`，而 `config/output-config.yaml` 的 `deliverable_index` 保留 `PRD-00-总览*.md / PRD-*.md` 的兼容白名单；两者分别承担输出模式与分类收口职责，不应混为一谈。

- 项目目录命名 `<YYYYMMDD>-<slug>`（如 `20260825-pet-feed-app`，产品名用英文短横线 slug）；文件一律中文语义化；核心交付物带 `<产品代号>-v<版本>`（代号如 `门锁PE-001`，Gate 0 与用户约定）。

- 阶段目录契约 `stage_dir_names`：`01_市场调研 / 02_需求分析 / 03_产品定义 / 04_产品设计 / 05_整合验证`，`00_交付物` 与 `01_过程资产` 下均按相位分组。

- 收口后机器校验 `validate_artifact.py deliverable-manifest`：市场调研报告 / 需求规格说明书 / PRD\-00\-总览 / 设计交付 / 整合验证报告 任一缺失即 BLOCKED。

- 长阶段必须每子步输出 3–5 行进度卡；预计超预算或连续 10 分钟无状态更新时先吐已完成部分再继续。

## 5\. 任务模式与路由（`config/task-modes.yaml`）

先判 `task_type` → 再选链路（不默认 full\_chain / 不默认从零立项）。

**5 种 workflow\_mode**：`full_chain`（完整链路，串行）、`single_expert`（仅市场调研单独执行）、`short_chain`（已有产品缩短链路）、`specialized_chain`（带可行性/硬件约束的专门链路）、`review_only`（只审查/给返工建议，可按门禁直达专家）。

**8 类 task\_type**（`workflow.yaml supported_task_types`）：`full_product_creation`、`market_research_only`、`existing_app_feature_addition`、`existing_feature_iteration`、`hardware_next_generation`、`prd_review_or_rewrite`、`design_module_optimization`、`technical_feasibility_review`；`task-modes.yaml` 另登记 `hardware_onboarding`（已有 App 新增硬件接入）等完整表项。

**路由要点**：

- `full_product_creation` → 市场→需求→定义→设计全链路；

- `market_research_only` → 仅市场调研专家（`single_expert` 是正式专家中唯一允许的单专家直达入口）；

- `existing_*` → `short_chain`，可自需求分析/定义/设计起步，是否补市场调研由 task\_type 与门禁判定（market\_research\_trigger 命中才补）；

- `hardware_next_generation` → `specialized_chain`；

- `prd_review_or_rewrite` / `technical_feasibility_review` / `design_module_optimization` → `review_only`，可直接派发 `product-definition-expert` 或 `product-designer`。

- 所有正式专家调用必须处于串行链路中（市场调研除外），禁止同链并行、禁止整包转发上下文。

- 单点任务必须有 `stop_condition` 与 `execution_depth/budget_profile`（`execution-budgets.yaml`），禁止自动扩展为完整立项。

## 6\. I/O 契约体系（`contracts/io-layering.md`）

三层契约，颗粒度从粗到细，各司其职、不得混写：

- **L1 专家级契约**：`contracts/experts/*.io.yaml`，职责/目标级（消费什么上下文、产出什么交付物、交给谁）。

- **L2 Skill 级契约**：各 `SKILL.md` frontmatter 的 `io:` 段，字段级（inputs/outputs/schema/contracts），机器校验入口 `scripts/validate_io_contract.py`。

- **L3 阶段间数据契约**：各阶段产物顶层的 `downstream_contract`（我交付什么字段）与 `consumed_refs`（我消费了上游哪些字段/id），消费凭证机制。

**三条铁律**：①专家层只写职责与目标、不列字段；②Skill 层只写字段与契约、不写职责；③三层必须闭环可校验（L1 交付对象在 L3 有承接方，L2 输出字段被下游消费或显式声明对外交付）。

**Schema 落点**：`consumed_refs` 位于 6 份核心 schema：market\-research / reqspec / prd / design\-spec / ia / design\-token；`downstream_contract` 位于 market\-research / reqspec / prd / design\-spec / market\-research\-stage\-manifest（ia 与 design\-token 只有 consumed\_refs，因为它们是被消费/承接方）。

**校验项**（`--check-connectivity`）：方向一致、口径一致、无环、required input 全覆盖、无断源孤儿、伪消费即 BLOCKED。

**端侧完整性（v4\.6，团队级责任）**：`integrated`/`hardware` 任务的 reqspec/prd/design\-spec 均须含端侧需求矩阵（App/设备/云端三端）；设备端必含开机复位、广播字段、指示灯、协议能力、异常处理等；机器校验 `scripts/tuning/check_prd_production.py`。

## 8\. 知识体系（knowledge/ 与 config/active\-knowledge\-profile\.yaml）

- `knowledge/` 为**只读静态资产**（口径/模板/维度/术语/可信源导航），分为通用区与行业知识包（`industry-packs/`，由 `industry_pack_manager.py` 管理）；另有 `_registry`、`brand-assets`、`common`、`project-docs`、`user-materials` 等区。

- 当前激活的行业 profile 由 `config/active-knowledge-profile.yaml` 声明（当前值例：`pet-care-cn-2026`，mode `industry_pm`），含 `kb.domain-profiles / kb.user-research / kb.competitor-feature / kb.regulatory-compliance / kb.bom-cost / kb.brand-assets / kb.historical-prd` 等挂载点，每项带质量等级 A/B/C、gap 级别 C0/C1/C2 与缺失动作。

- Gate K 机械检查（`check_knowledge_readiness.py` / `industry_pack_manager.py current` / `knowledge_router.py check --strict-content`）验证：active profile 已加载、行业包 manifest 有效、内容非占位符、按任务类型所需知识齐备；C0/C1 缺口必须澄清或确认降级。

- 行业知识包只作为**资料源/证据源/上下文增强层**，不得替代市场调研的公开调研、交叉验证、证据四件套、Fact Registry、一手调研触发与 S1–S5 方法论；`active_profile=industry_pm` 不得导致调研 Tier 自动降级或跳过外部检索。
