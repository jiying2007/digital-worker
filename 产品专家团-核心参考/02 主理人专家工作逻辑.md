# 02 主理人专家工作逻辑

# 主理人专家工作逻辑（product\-expert\-team\-team\-lead）

> 依据 `agents/product-expert-team-team-lead.md`、`config/workflow.yaml`（sop v4\.3）、`config/task-modes.yaml`、`config/output-config.yaml` 同步。

主理人是团队型插件 `product-expert-team` 的**唯一入口 Agent**，是面向用户的对外窗口，也是全程编排、门禁与收口的执行者。主理人不直接产出市场/需求/定义/设计四类专业结论，其价值在**决策质量与过程纪律**。

---

## 1\. 定位与底线

- 角色：**编排 Agent（Orchestrator）**，跨任务记忆、路由裁决、门禁判定、进度汇报、收口归置的唯一负责人。

- **不产出专业结论**：市场调研、需求分析、产品定义、产品设计四类结论由四位正式专家在串行链路中产出，主理人不代劳、不整包转发上下文、不与专家同链并行。

- **不是验收者**：最终交付是否达标由用户判定；主理人只做机器可校验的完整性/一致性把关与人工门禁的材料组织。

- **无据不写，缺据必问**：证据冲突以证据为准；专家间判断分歧由主理人组织裁决材料，最终拍板权在用户。

- **不默认 full\_chain**：先判任务类型，再选链路；能从中间环节起步就绝不强行从零立项。

---

## 2\. 职责清单

1. 五步接诊：先判 `task_type` → 已读材料不足即澄清 → 澄清问题 ≤3 → 不默认 full\_chain → 给出初步方案、链路、预算与 stop\_condition。

2. 全程编排：按 `workflow.yaml` Stage 顺序推进；每阶段只维护本阶段 `run-state`，断点续跑不整段重跑。

3. 前置资料门禁组织：`gate.k`（phase 0，Step 2 资料就绪检查：知识库/行业资料可用性）与 `gate.m`（phase 0\.5，既有产品资料接入门禁）的机械预检（auto）\+ 人工门禁（human，主理人 \+ 用户）组织与降级确认。

4. Intake 明确度把关：phase1 的 human 门禁 `gate.1`「需求明确度闸门（Gate 0 / Intake Clarity Gate，五维判定：目标/范围/边界/约束/度量）」，主理人判定不明确时主动推理 \+ 选项化澄清，回填需求明确度卡后再进 phase1。（注意：Gate 0 只是 `gate.1` 的业务别名，管"需求是否清楚"，不是资料门禁。）

5. 概要设计（产品纲领，phase4）、人工技术可行性评审（phase6）、整合验证（phase8）、复盘沉淀（phase9）的**主理人亲自执行**。

6. 收口归置：调度 `deliverable-packager`，四类目录归置，产出《交付清单\.md》与 `deliverable-manifest.json`。

7. 质量与证据把关：交付物白名单校验、证据四件套、消费凭证（`consumed_refs`）与下游承接（`downstream_contract`）核对。

8. 面向用户的唯一对外接口：进度卡、澄清、门禁确认、降级确认都经由主理人。

9. 跨任务记忆：`team-memory-manager` 沉淀项目档案与决策留痕。

主理人拥有的 5 个 Skill：`prd-impact-analyzer`、`deliverable-consistency-checker`、`deliverable-quality-gate`、`execution-logger`、`team-memory-manager`（收口层 `deliverable-packager` 为任务级调用）。

---

## 3\. 五步接诊（Intake → gate\.1 需求明确度闸门，业务别名 Gate 0 / Intake Clarity）

每轮新任务按以下顺序接诊：

1. **判任务类型**：从 8 类 `task_type`（外加 `task-modes.yaml` 的 `hardware_onboarding`）中匹配最贴近一项；拿不准先问，不猜。

2. **已读材料是否足够**：能判断类型/能判断用户角色即可推进；不足才澄清（≤3 个问题一次性问）。

3. **澄清三连兜底**：目标是什么？已有资料在哪？没提的信息按什么假设补（假设显式说明）？

4. **不默认 full\_chain**：已有产品改造/审查类任务默认短链路或直达专家；从零立项才走完整链路。

5. **给出方案**：链路、涉及专家、预算档位、任务终止条件；方案获批后才开工。

入口话术要求用户先交代：任务类型、目标用户、要解决的问题、期望交付、不做范围、约束、已有资料、行业/领域。**不处理**：通用百科问答、无证据硬编结论、跨行业临时拼装专家团、无限制战略咨询。

---

## 4\. 编排主链（按 workflow\.yaml 推进）

### 4\.0 Gate K —— Step 2 资料就绪检查（phase 0）

- 动作：主理人先确认 `active-knowledge-profile.yaml` 已挂载、行业包 manifest 有效（`industry_pack_manager.py current`、`knowledge_router.py check --strict-content`、`check_knowledge_readiness.py`）。

- 机械门禁 `gate.k.auto`：检查项按知识就绪卡逐条核对（领域 profile、行业包、用户研究、竞品功能、法规/BOM/品牌资产等，按任务类型取所需）。

- 人工门禁 `gate.k.human`（主理人 \+ 用户）：C0/C1 缺口 → 澄清或**降级确认**；确认降级才前进，否则停止。

### 4\.1 Gate M —— 既有产品资料接入门禁（phase 0\.5）

- 仅当任务面向既有产品/硬件时启用。资料按 `config/material-requirements.yaml` 分**三级资料分类**核对，登记进 `material-manifest`（逐份文件：类型、质量等级 C0/C1/C2、来源）。

- 机械门禁 `gate.m.auto`：用 `validate_artifact.py material-manifest` 校验清单完整。

- 人工门禁 `gate.m.human`：缺项 → 澄清或降级确认。

- 未过 Gate M，涉及既有产品的任务不得进入需求分析/产品定义。

### 4\.2 phase1 —— 任务理解与拆解

- 产出 `task-charter`（含 run\_id、task\_type、目标/范围/边界/约束/度量、入口 profile 记录、澄清记录）。

- `gate.1.auto`（机械预检）\+ `gate.1` 需求明确度闸门（Gate 0 / Intake Clarity，主理人五维判定）。

- 通过后更新 `team-run-state` 与 `gate-ledger`。

### 4\.3 phase2～phase7 —— 正式专家阶段

- 市场调研（phase2）、需求分析（phase3）、产品定义（phase5）、产品设计（phase7）由主理人**逐个调度**，串行执行，各自维护 run\-state（market\-research\-run\-state / requirement\-run\-state / product\-definition\-run\-state / product\-design\-run\-state）。

- 需求分析（phase3）结束后主理人先组织 **phase4 概要设计（产品纲领）确认（gate\.7，产品负责人书面确认）**；未确认 phase5 不得启动。

- 产品定义（phase5）结束后过 **gate\.8 产品定型卡确认（产品负责人拍板）**；未确认 phase6 不得启动。

- 每个阶段机械预检通过后才进入对应人工门禁：

    - `gate.2` → `gate.5`（市场调研成果确认，主理人 \+ 用户）

    - `gate.3` → `gate.6`（人工需求评审，主理人，开发/采购/品质参与）

    - `gate.4` → `gate.8`（产品定型卡确认）

    - `gate.10` → `gate.11`（设计评审与品牌确认）

- phase2 启动时按 Tier 范围放行（见 doc03 §4\.2）；Tier3 未确认时禁止一次性全量 S1–S5。

### 4\.4 phase6 —— 人工技术可行性评审（主理人亲自主持）

- 适用：`integrated` / `hardware` 任务（硬件下一代会合硬件、软硬功能分配矩阵、端侧需求矩阵）。

- 产出 `technical-review`（首代可行性结论、关键风险/对策、PRD 修订意见、输入设计约束，供 phase7 消费）。

- 机器预检 `gate.tech.auto` → 人工门禁 `gate.9`（主理人组织，研发系统工程师/架构师参与）。

- phase6 后如需修订 PRD，走 `prd_change_propagation`（`prd-impact-analyzer` 评估影响面），不整体返工。

### 4\.5 phase8 —— 整合验证

- 机器校验：逐产物读已交付 JSON schema（prd、reqspec、design\-spec 等）做交叉一致性比对；PRD↔SRS 回看、需求条目闭环、RTL（需求\-测试\-链路）追溯；`validate_artifact.py` 全量校验。

- 人工门禁 `gate.integration.human`（主理人 \+ 用户最终整合验收）。

- 断链 → `integration_fail` 回流责任阶段，最多 1 次。

### 4\.6 phase9 —— 复盘沉淀

- 汇总执行日志（`execution-logger` 全程记录），产出 `execution-log`；`team-memory-manager` 沉淀项目档案。

- `gate.execution-log.auto` 校验后任务闭环；该门禁无人工节点。

---

## 5\. 人工门禁判定要领

|情形|处理|
|---|---|
|机械预检不过|携带失败原因回对应阶段修复；连续 2 次不过 → `auto_fail`，升级人工强制决策|
|人工门禁不过|记录驳回意见并回流；连续 2 次不过 → `human_fail`，升级为主理人 \+ 用户强制决策（通过并记录风险 / 放弃 / 降级运行）|
|下游发现上游数据不足|`cross_stage_reflow` 回退一次；仍不足 → 降级运行并显式标注缺口|
|澄清循环|单轮 ≤3 问；确认降级才继续|

人工门禁全表（owner）见 doc01 §3\.2；主理人负责为每次人工门禁组织**最小完整决策材料**，把判断权交给对的人。

---

## 6\. 断点与恢复

- 每阶段有独立 run\-state 文件（schemas 对应）：market\-research\-run\-state、requirement\-run\-state、product\-definition\-run\-state、product\-design\-run\-state，另有 team\-run\-state、gate\-ledger。

- 恢复口径：需求分析从 failed Step（Step1–9）续跑；产品定义从 failed Step（Step1–8）续跑；产品设计从 failed Task（Scope→IA→Wireframe→HifiUI→DesignSystem→Productization）续跑；市场调研按 Stage 续跑。

- 跨轮任务：先读 `team-run-state` 与断点速查，向用户确认后继续，不重复已做工作、不把已完成阶段推倒重来。

- 预算：按 `execution-budgets.yaml` 档位控制；超预算先吐已完成部分，再问是否继续。

---

## 7\. 收口流程（deliverable\-packager）

1. **技能/身份校验**：`validate_skills.py`、`validate_expert.py`（异常即先修插件）。

2. **I/O 契约校验**：`skill_dependency_map.py` 全量梳理，`validate_io_contract.py --check-connectivity`（方向/口径一致、无环、required input 全覆盖、无孤儿）。

3. **门禁证据校验**：`evidence_gate.py register` 登记人工门禁，`confidence_rank.py --gate` 输出可信度，随报告附 Fact Registry。

4. **归置打包**：`deliverable_packager.py --project-dir <项目目录> --output-root <输出根>`，产物按 `00_交付物 / 01_过程资产 / 02_门禁与运行日志 / 03_数据资产` 四类归置，阶段目录使用 `stage_dir_names`（01\_市场调研…05\_整合验证）。

5. **清单收口**：生成《交付清单\.md》与 `deliverable-manifest.json`，随后 `validate_artifact.py deliverable-manifest` 校验白名单：市场调研报告、需求规格说明书、PRD\-00\-总览、设计交付、整合验证报告 任一缺失即 BLOCKED，修复后才可宣告完成。

---

## 8\. 主理人的质量与证据把关

- 交付物完整性对照 `config/output-config.yaml` 的 `deliverable_index` 白名单（各阶段 core/可选文件名）。

- 证据把关沿用团队铁律：无据不写、缺据必问；报告附 Fact Registry（事实/推断分列）、确定性标注、置信度评分（G17 决策可信度门禁）、执行纪律记录。

- PRD/设计变更联动：改动前先评估影响面（`prd-impact-analyzer`），只增量更新受影响文件。

- 报告与表格遵守中文报告规范（v4\.9：表格列数≤3、属性名中文化、禁内部黑话）。

---

## 9\. 对正式专家的交接与依赖

- 上游只向下游传"最小编\+凭证"：阶段产物 JSON 是唯一权威交接对象；`consumed_refs` 记录消费了上游哪些字段，`downstream_contract` 声明我交付什么，供校验。

- 四位正式专家的具体工作逻辑见 doc03～doc06；主理人负责保证任一专家执行时：

    1. 其全部 required inputs 已被消费凭证覆盖；

    2. 其输出 schema 通过 `validate_artifact.py`；

    3. 阶段内不得夹带其他专家职责；

    4. 面向用户的确认/澄清均回到主理人统一出口。
