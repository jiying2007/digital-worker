# 05 产品定义专家工作逻辑

# 产品定义专家工作逻辑（product\-definition\-expert）

> 依据 `agents/product-definition-expert.md`、`config/workflow.yaml`（phase4/phase5/phase6 门禁）、`config/prd-output-modes.yaml`（v3\.6 \+ v4\.2 功能点粒度）、`contracts/experts/definition.io.yaml`、`skills/def-*`（9 个 Skill）与 `references/03_产品定义/` 同步。

## 1\. 角色定位与职责边界

产品定义专家（Product Definition Specialist）负责**把需求收敛成可执行、可验收、可排期的产品方案**，是需求基线 → 设计/研发输入之间的定型环节。

- **负责**：功能定义、性能定义、PRD、路线图、埋点需求、验证策略、架构级产品定义。

- **不负责**：需求分析、视觉设计、代码实现、采购选型、型号锁定。

- 对软硬件一体产品，只定义**能力边界与产品意图**，不替下游做工程实现；关键决策点未明确先问主理人，不默认值。

## 2\. 全链位置与 I/O（L1 契约）

- 位于 `phase5`，前置为 phase4 **概要设计（产品纲领）确认**（product\-outline，产品负责人书面确认，gate\.7）与人工需求评审（gate\.6）；后置为 phase6 **人工技术可行性评审**（gate\.9）。

- **consumes**：需求规格说明书 SRS（功能清单/性能指标/优先级/法规/成本）、概要设计 product\-outline（系统设计：硬件/嵌入式/算法/应用，须人工确认）、9 个输入视角（功能/性能/关键技术意向/技术能力/价格/成本/品质/合规/场景体验）、知识源（kb\.historical\-prd / kb\.bom\-cost / kb\.regulatory\-compliance / kb\.enterprise\-baseline / kb\.tech\-supply\-capability）；既有产品任务还需 `material-manifest`、`product-context`、`change-request` 或 `hardware-next-gen brief`。

- **produces**：PRD（`single_prd` / `hybrid_prd` / `modular_prd_package`，md \+ json 双交付）、功能树、性能 KPI 双层（Goal/Threshold）、关键技术意向（能力级）、成本分解、版本路线图；外加交互需求规格、数据采集与埋点需求、验证策略、软硬件功能分配矩阵、KPI 双层定义与 RTM 对齐结果。

- **delivers\_to**：product\-designer（经人工技术可行性评审后）。

- **boundary 亮点**：也支持基于用户原始需求直接输出 `single_prd` 或定点 `technical_feasibility_review` 结论（对应 `prd_review_or_rewrite` / `technical_feasibility_review` 任务直达）；输入不足先向用户主动澄清；单次接收上下文限制在当前 task\-charter、必要上游产物与门禁摘要内；全流程任务严格串行。

## 3\. 工作方式（agent 内 8 步）

1. **接活审查**：确认任务类型、资料齐备度、关键决策点、范围与停止条件。

2. **先定型**：明确核心价值、用户分层、边界、MVP、闭环场景和成功标准。

3. **先判输出模式**：按 `prd_output_mode` 判 `single_prd` / `hybrid_prd` / `modular_prd_package`；用户原始需求即一份 PRD 或单点功能需求文档时，可直接 `single_prd`，不强制先拆多任务。

4. **按需拆分功能点**：仅当任务复杂度/模块数量/边界不清需分拆时再列功能点清单拆分；单份 PRD 可完整表达则不拆。

5. **再定标准**：每个功能定义量化门槛与测试方式。

6. **补技术意向**：只写能力规格，不锁具体实现（如"需 WiFi6\+BLE5\.3 的 SoC，功耗≤3W"）。

7. **输出 PRD**：按任务复杂度选模式。

8. **收口校验**：RTM、KPI、范围、边界、版本与门禁检查。

## 4\. 输出模式与拆分规则（`config/prd-output-modes.yaml`）

### 4\.1 三种输出模式

|模式|说明|默认任务类型|必需产物|
|---|---|---|---|
|`single_prd`|单体 PRD：小范围需求、PRD 审查、轻量功能定义、技术可行性判断|prd\_review\_or\_rewrite、technical\_feasibility\_review|product\-definition|
|`hybrid_prd`|总览 \+ 1–3 个关键模块 PRD：中等复杂度局部优化/设计模块优化|design\_module\_optimization|product\-definition、prd\-package\-index、module\-prd|
|`modular_prd_package`|模块化 PRD 包：每个模块单文件 PRD \+ 配套 JSON|full\_product\_creation、existing\_app\_feature\_addition、existing\_feature\_iteration、hardware\_next\_generation|prd\-package\-index、module\-prd、acceptance\-doc；根目录必含 `00_总览.md` \+ `prd-package-index.json`|

### 4\.2 模块拆分规则与反模式

- 原子模块定义：单一用户目标、独立入口或触发条件、独立主流程与异常流程、独立业务规则与验收标准、明确 Out of Scope。

- 反模式大词库（命中即须继续拆分，否则登记 `pending_confirmations`）：用户管理/首页优化/数据能力/AI 能力/后台管理/账号体系/用户中心/数据中心/智能能力/管理后台/设备管理模块/设备中心/权限中心/消息中心/通知中心/内容管理/CMS 等。

### 4\.3 功能点粒度（v4\.2，def\-prd 内建）

- `one_feature_one_doc=true`：一个功能点文档只覆盖 **1 个用户目标 \+ 1 条主流程 \+ 1 套可独立验收标准**。

- 原子性上限：主流程 1 条、入口 ≤3、强关联子功能 ≤3（可独立 GWT）、业务规则 ≤8、验收标准 ≤10。

- `feature_list_required`：先枚举功能点清单（对齐上游 US\-），再 1:1 映射成文档。

- `split_triggers`：\>1 条主流程 / 规则 \>8 / 验收 \>10 / 模块名命中反模式库 / 入口 \>3 → 命中即强制拆；拆不动登记 `pending_confirmations`，不得交付大模块。

- 输出结构：`PRD/00_总览.md`、`<NN>_模块名_PRD.md` \+ `<NN>_模块名_prd.json`、`prd-package-index.json`，支撑目录 `90_测试与边界/` `91_技术依赖/` `92_变更记录/`。

- 质量规则：每个 P0 模块独立 md\+json（验收标准内嵌不再拆独立文件）；模块回指上游 requirement\_refs；必有 Out of Scope；验收标准可测试；总览内容不复制进各模块；假设与待确认项显式记录。

## 5\. Skill 链（9 个 def\-\*）

|Skill|版本|输入（←来源）|输出|定位|
|---|---|---|---|---|
|`def-func-spec`|1\.0\.0|reqspec ← req\-srs\-builder|func\_spec|功能规格：系统级→模块级→子功能框架，逐功能写边界条件与异常路径|
|`def-perf-spec`|1\.1\.0|func\_spec ← def\-func\-spec|perf\_spec|性能规格：Goal（差异化）\+ Threshold（质量底线）双维度|
|`def-tech-intent`|1\.0\.0|reqspec ← req\-srs\-builder；product\_outline|tech\_intent|关键技术意向：关键器件能力规格清单，不锁实现|
|`def-architecture`|1\.0\.0|product\_outline|architecture|产品架构规划：总体架构图、模块划分、接口定义|
|`def-id-input`|1\.0\.0|func\_spec ← def\-func\-spec；architecture ← def\-architecture|id\_input|ID 输入定义（六大要素：定位风格/物理约束/环境适应性等），产 ID 设计需求书|
|`def-roadmap`|1\.0\.0|func\_spec ← def\-func\-spec|roadmap|版本路线图：V1\.0 MVP → V1\.1 快速迭代 → V2\.0 战略升级三阶规划|
|`def-cost-breakdown`|1\.0\.0|func\_spec ← def\-func\-spec；target\_price（可选）|cost\_breakdown|成本分解：功能级成本目标、器件成本限制、整体 BOM 预估|
|`def-quality-baseline`|1\.2\.0|perf\_spec ← def\-perf\-spec|quality\_baseline|品质及格线：良率/失效率/合规/可靠性等非性能质量特性的 Threshold|
|`def-prd`|4\.2\.0|func\_spec/perf\_spec/tech\_intent/cost\_breakdown/quality\_baseline ← def\-\*；rtm ← req\-srs\-builder|prd、prd\_package\_index、prd\_delta|智能 PRD 撰写与澄清：生成可评审、可验收、可追溯的 PRD 产物|

PRD 发生新增/删除/修改时，`prd-impact-analyzer`（主理人 Skill）基于 `prd_delta` 评估对设计/研发/营销/品质/供应链的影响范围、工作量与风险，支撑 `prd_change_propagation`。

## 6\. 端侧与软硬件定义

- 软硬件一体产品输出**软硬件功能分配矩阵**，明确能力边界；`integrated`/`hardware` 任务端侧需求矩阵完整性由 `scripts/tuning/check_prd_production.py` 机器校验（App/设备/云端三端，设备端含开机复位、广播字段、指示灯、协议能力、异常处理等，见 doc01 §6 端侧完整性）。

- 只定义能力与产品意图，型号/供应商选型、实现锁定留待人工技术可行性评审与下游。

## 7\. 门禁与恢复

- 机械预检 `gate.4`（PRD 包/总览/manifest 等，机器校验）→ 人工门禁 `gate.8` **产品定型卡确认（产品负责人拍板）**；未确认 phase6（人工技术可行性评审）不得启动。

- 人工技术可行性评审 `gate.9` 由主理人主持（研发系统工程师/架构师参与）；评审结论（含 PRD 修订意见与**设计输入约束**）随 `technical-review` 交给下游设计。

- 断点：`product-definition-run-state.json`，按 Step1–8（`step_mode=single/resume/full`）恢复，不整段重跑；C0 字段缺失先停摆澄清，不硬编定版。

## 8\. 交付物（产出物治理 v5\.0 白名单，03\_产品定义）

- core：`PRD-00-总览*.md`、`PRD-*.md`（模块 PRD 按 `<NN>_模块名_PRD.md` 与 `<NN>_模块名_prd.json` 落盘）。

- 选读：`交互需求规格.md`、`数据采集与埋点需求.md`、`验证策略与AB实验.md`、`版本路线图.md`、`软硬件功能分配矩阵.md`。

- PRD 包内部：`00_总览.md`、`prd-package-index.json`、`90_测试与边界/` `91_技术依赖/` `92_变更记录/`。

- 说明：`config/prd-output-modes.yaml` 决定 PRD 是 `single_prd` / `hybrid_prd` / `modular_prd_package`；`config/output-config.yaml` 的 `deliverable_index` 负责分类白名单与兼容命名，不负责决定 PRD 输出模式。模块化 PRD 包实际以 `00_总览.md`、`prd-package-index.json`、`module-prd.json` 为准。

## 9\. 协作方式

- 下游设计只接收本专家定义清楚的功能和约束，不替本专家重写需求；输出物必须能被下游专家（product\-designer）继续消费。

- 长任务每完成一步发进度卡；验收标准一律量化；有冲突先给单一推荐结论再写代价；既有产品任务先核对上下文资料，不得把未确认内容写成定版。
