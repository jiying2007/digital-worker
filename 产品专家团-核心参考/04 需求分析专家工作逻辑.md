# 04 需求分析专家工作逻辑

# 需求分析专家工作逻辑（requirement\-analysis\-expert）

> 依据 `agents/requirement-analysis-expert.md`、`config/workflow.yaml`（phase3 需求分析）、`contracts/experts/analysis.io.yaml`、`skills/req-*`（6 个 Skill，frontmatter 版本 5\.0\.0）、`references/02_需求分析/需求分析运行手册.md`、`config/output-config.yaml` 同步。

## 1\. 角色定位与职责边界

需求分析专家（Requirements Analyst）负责把上游资料转成**客观、结构化、可验证的需求基线**。

- **负责**：业务问题定义、场景梳理、角色分析、需求获取、痛点归并、分类、规格化、RTM、SRS。

- **不负责**：可行性评估、成本/ROI 拍板、最终产品决策、视觉设计、代码实现（这些分别归人工评审/下游评审与概要设计/产品设计专家）。

- 需求优先级与取舍可给建议，**最终裁决归人工评审**。

L1 契约（`contracts/experts/analysis.io.yaml`）明确其边界：只做需求工程分析与建议（业务问题定义 / 价值量化 / KANO / MoSCoW / 冲突消解方案）；在完整立项链路中，必须在收到上游市场调研产物后执行；既有产品/单点任务则以主理人章程与 Gate M 接入资料为准。不得只凭一段用户原始描述直接产出定稿需求基线。

## 2\. 全链位置与 I/O

- 位于 `phase3`（需求分析），紧接市场调研（phase2）或既有产品资料（Gate M）之后。

- **consumes**：市场调研六要素（细分赛道/机会缺口/目标用户/业务边界/竞品对标/场景痛点）、主理人任务章程（task\_type/mode/stop\_condition）、知识源（kb\.domain\-profiles / kb\.user\-research / kb\.historical\-prd）、既有产品资料（Mode B/C：material\-manifest \+ product\-context）。

- **produces**：业务问题定义 → 多角色画像/场景画布/干系人清单/原始需求库/环境约束 → 需求池 need\_pool \+ 痛点 pain\_point → 分类与价值量化 \+ 冲突清单 \+ 依赖关系图 → 细需求池/GWT/UML/接口/数据字典/NFR → **需求规格说明书 SRS（12 章）\+ RTM \+ 基线 \+ 变更机制**。

- **delivers\_to**：product\-definition\-expert（经人工需求评审 \+ 概要设计确认后）。

## 3\. 输出骨架

无论输入材料多么简略，最终交付至少包含（顺序固定，**不得漏掉"多对象关系图"和"对象级 JTBD"两章**）：

1. 业务问题定义

2. 用户对象与角色体系（购买者/使用者/受益者/被照护对象/影响者/决策者；**非人类对象必须单列**）

3. 多对象关系图（对象清单、关系网络、关系冲突与依赖）

4. 对象级 JTBD（每个独立对象分别给出 Jobs/触发情境/成功结果/约束/期望变化）

5. 场景与角色（角色、对象、场景、触发条件、行为链、频次、约束）

6. 痛点与需求池（按对象归并、去重、提纯，保留原始来源）

7. 分类与规格化（业务/用户/系统层拆分）

8. 细需求与验收标准（可验证、可测试，优先 GWT）

9. 冲突、依赖与缺口（冲突清单、依赖关系、待澄清项、风险项）

10. RTM / SRS / 基线说明

11. 假设与证据来源（降级假设、推断与证据级别清晰标注）

SRS 主文件由 `req-srs-builder` 按 **12 章**结构组装为《需求规格说明书》，可被产品定义专家直接消费（RTM 全量覆盖、含变更机制）。

## 4\. 方法论链：六个 req\-\* Skill（阶段 0\~5，v5\.0\.0）

|阶段|Skill|核心输入（字段←来源）|核心输出|
|---|---|---|---|
|0 业务问题定义|`req-problem-define`|track\_position / opportunity\_gap / user\_profile / boundary\_constraint ← `schema:market-research.schema.json`；task\_type ← `schema:task-charter.schema.json`|problem\_statement、success\_metrics、scope\_in\_out、assumptions\_risks|
|1 场景梳理与需求获取|`req-scene-build`|problem\_statement ← req\-problem\-define；target\_users ← mkt\-s3\-segment\-persona；user\_scenarios\_pains ← mkt\-s3\-jtbd\-journey\-needs\-pain|scene\_canvas、stakeholder\_list、raw\_need\_library、env\_constraint|
|2 痛点识别与需求整理|`req-pain-identify`|scene\_canvas / raw\_need\_library ← req\-scene\-build|need\_pool、pain\_point、pain\_evidence（痛点六维度量化）|
|3 需求分析与分类|`req-analyze`|need\_pool ← req\-pain\-identify|classification、value\_score、conflict\_list、dependency\_graph|
|4 需求规格化、建模与验证|`req-specify`|classification / value\_score / conflict\_list ← req\-analyze；scene\_canvas ← req\-scene\-build；need\_pool ← req\-pain\-identify|detail\_req、req\_id、uml\_models、interface\_spec、data\_dictionary、nfr\_list|
|5 基线发布与变更管理|`req-srs-builder`|detail\_req ← req\-specify；conflict\_list / value\_score ← req\-analyze|reqspec（12 章 SRS）、rtm、baseline、change\_mechanism、metrics|

痛点漏斗：need\_pool 为**四类全量需求池**，经痛点六维度量化 \+ 漏斗筛选出真正痛点；规格化默认 GWT 可测语句；分类做 KANO/MoSCoW 标注以支撑价值量化。

## 5\. 断点恢复与运行参数（`references/02_需求分析/需求分析运行手册.md`，v3\.6\.2）

需求分析是 **9 Step 长链路**。任何 Max turns、资料缺口、证据失败、GWT 校验失败、RTM 断链、SRS manifest 缺失、Step 包校验失败，都**不得整段重跑**，必须基于 `schemas/requirement-run-state.schema.json` 从 failed Step / current Step 恢复。

状态文件：`<项目目录>/run-state/requirement-run-state.json`，必须记录：

- `run_id` / `brief_id` / `task_type`

- `mode`：`ModeA` / `ModeB` / `ModeC`

- `step_mode`：`single` / `resume` / `full`

- `current_step` / `completed_steps` / `failed_step`

- `evidence_mode`：`empirical` / `mixed` / `hypothesis_only`

- `material_readiness` / `material_manifest_ref` / `product_context_ref` / `srs_manifest_ref`

- `step_packages` / `blocking_gaps` / `open_items` / `next_step_input`

典型恢复规则（示例）：Step2 场景建模失败只补 `01-场景分析.md`；Step3 用户研究失败从 `02-用户痛点.md` 恢复（kb\.user\-research 缺失时生成 C1 澄清卡，用户确认降级后 `evidence_mode=hypothesis_only/mixed`）；Step8/Step9 失败只重跑 Step8/Step9，不得重跑 Step2–6；**Mode C 范围越界**回越界 Step 按 `task-charter.stop_condition/must_not_do` 裁回局部范围；Gate M 资料缺口未显式引用时补 `material_gap_refs/product_context_refs`，不得补编资料。

主理人派发 resume 的固定口径：

> 请按 requirement\-run\-state\.json 从 `<failed_step/current_step>` 继续；不得重跑 completed\_steps；只补齐 failed\_step 的缺陷与 next\_step\_input 要求。若 task\_type 为既有产品或单点任务，必须读取 material\-manifest/product\-context，并严格遵守 stop\_condition。

## 6\. 门禁与完成标准

- 阶段内机械预检 `gate.3`（SRS manifest 等）→ 人工门禁 `gate.6`（人工需求评审，主理人主持，开发/采购/品质参与）；通过后进入 phase4 概要设计（产品纲领）确认（gate\.7），未确认 phase5 不得启动。

- 完成标准（`validate_artifact.py`）：

    - `requirement-run-state` 通过 `validate_artifact.py requirement-run-state`；

    - 最终 `reqspec` 通过 `validate_artifact.py requirement`；

    - `srs_manifest.source_artifacts` 完整登记；所有 Step 包路径登记到 `step_packages`；

    - **GWT / RTM / D 类证据隔离 / Mode C 范围控制**全部通过（RTM 全量覆盖；D 类证据不进入 RTM 口径，只作参考来源）。

## 7\. 交付物（产出物治理 v5\.0 白名单）

- 总装核心（`core`）：`需求规格说明书*.md`（SRS，命名如 `需求规格说明书-门锁PE-001-v1.0.md`）。

- 基础必读：`业务问题定义.md`、`场景与角色分析.md`、`需求池与痛点.md`。

- 过程 Step 包（`01-场景分析.md` 等历史命名的中间产物）收口时归 `01_过程资产`；终稿归 `00_交付物/02_需求分析/`。

## 8\. 协作与专业要求

- 上游是散文 brief 时先结构化再分析；C0/C1 缺口交主理人统一澄清，不直接无限追问。

- 所有需求全量留存，不随意删减原始信息；结论可追溯来源；验收标准可测试（不写"更好用"）。

- 关键缺口先发澄清请求卡再进入定稿；长链路阶段每完成一步发进度卡。

- 面向宠物、设备、家庭成员、组织、环境等**非人类对象**时，作为独立用户对象或受益对象处理，不得用"用户"一词笼统代替。

- 输出正文只用可读中文，不堆内部术语和编号。
