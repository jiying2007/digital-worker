# 系统边界与控制面

## 1. 为什么要先划边界

研发工具越来越多后，最容易出现的问题不是“功能不够”，而是多个系统都开始保存任务状态、知识、权限和验证结论，最后没有人知道哪个才是准的。

因此先规定各系统负责什么、不能负责什么，再谈具体产品选型。

## 2. 核心职责分工

|对象|长期职责|明确不承担|
|---|---|---|
|`digital-worker`|Work/Run、专家职责、领域流程、Gate、Action Policy、工程交接、Identity/Evidence、Verification、Review、Pilot/Maturity|不保存企业全部知识，不托管通用 Skill 发布，不作为 Coding Runtime Host|
|`knowledge-hub`|Knowledge Registry、authority、ACL、freshness、检索上下文、知识生命周期|不拥有源码/CI/HIL 原始事实，不给 Domain Verification PASS|
|`agent-dev-kit`|通用 Agent/Skill、资产 Profile、校验、immutable release、回滚|不持有项目任务状态，不替领域团队决定 Release|
|`llm_agent`|外部实践 intake、采用/健康度观察、Runtime 对比|不进入日常任务热链，不拥有 Domain Gate|
|Runtime Binding|在具体工程环境中执行分析、修改、构建和受控测试|不改变领域 Contract，不自行签最终 Verification/Review|
|Session Bootstrap|为一次会话装配 project/mode/contract/skill/provider identity|不成为第五控制面，不保存长期知识和放行状态|

## 3. Provider 角色要分开看

一个产品可以同时承担多个角色，但评审时必须分项证明：

|角色|需要解决的问题|典型候选|
|---|---|---|
|Interaction|人从哪里发起和查看任务|飞书、Web、IDE、CLI、办公助手|
|Work Item|任务 ID、状态、Owner、审批、审计放哪里|项目系统、飞书、Issue 系统|
|Knowledge Source|事实原文在哪里|NAS、飞书文档、Git、CI/HIL、Artifact Store|
|Knowledge Provider|怎么索引、检索、引用、处理 ACL/freshness|Knowledge Hub、RAG/Search 系统|
|Engineering Runtime|谁在工作树、构建环境中辅助实施|Codex、Claude Code、IDE Agent、内部 Runtime|
|Execution Provider|CI、HIL、设备、制品等具体动作由谁执行|Runner、实验室、HIL、发布系统|

“公司已经采购”或“支持 MCP/API”不是获得更多职责的理由。

## 4. digital-worker 与 Knowledge Hub

### digital-worker 保存什么

- 当前任务/Run 的上下文引用；
- 需要哪些知识、用了哪些知识；
- 关键 claim 对应哪些 evidence；
- Knowledge Harvest 结果；
- 领域侧的 bootstrap seed 和静态方法说明。

### Knowledge Hub 保存什么

- 统一的 Knowledge Registry；
- source authority、owner、version、ACL、freshness；
- 索引、引用、撤权和生命周期状态；
- 面向 Runtime 的稳定查询能力。

### 原始事实仍在哪里

- 当前源码、配置：Git；
- Build/Test：CI/Test System；
- HIL/设备结果：实验室/HIL；
- 发布制品：Artifact Store；
- Datasheet/TRM/供应商资料：NAS/DMS/供应商源；
- 组织决策：协作系统或正式文档。

因此 Knowledge Hub 是**控制面和访问层**，不是把所有原文复制成第二份主库。

## 5. digital-worker 与 ADK

`digital-worker` 决定“这个领域任务需要什么能力、在什么 Gate 使用、输出如何进入验证”。

ADK 决定“这项通用能力怎么打包、版本化、校验、发布和回滚”。

两者关系应是：

```text
Domain requirement
   ↓
digital-worker 定义使用场景和约束
   ↓
ADK 提供可复用资产 release
   ↓
Runtime Binding 消费 exact release/source-set
```

不应把 ADK 中的 Asset Profile 当成 Domain Verification，也不应把领域项目的临时逻辑长期塞进通用 ADK。

## 6. digital-worker 与 Runtime

Runtime 是执行工具，不是领域身份。

一个工程任务从 Codex 切到 Claude Code 或其他 Runtime 时，下列内容必须保持：

- work_item / run；
- repo_root / exact base commit；
- dirty baseline；
- goal / non-goal；
- acceptance；
- allowed / forbidden actions；
- required verification；
- evidence / blocker / risk；
- 已完成与未完成的工程动作。

Runtime 可以重新执行任务，但不能重新解释这些约束。

## 7. 与其他研发团队的边界

### 产品专家团

产品负责 What/Why、用户场景、优先级、产品范围和验收意图；嵌入式负责技术可行性、架构/平台影响、工程范围、资源/性能风险和验证策略。

正式交接使用：`technical-review-request → embedded-feasibility-review`。

### 端侧底座

使用 OWN / SHARED / CONSUME / PROVIDE / OUT_OF_SCOPE 表达职责。Boot/BSP、Kernel、RTOS、Drivers、Middleware、AI Runtime、OTA、Diagnostics、HIL、Platform Abstraction 等如果是 SHARED，必须进一步指定：

- canonical owner；
- Source of Truth；
- provider/consumer；
- version compatibility；
- change notification；
- review owner。

没有 ownership 结论时，不重复建设同一能力。

### 硬件团队

嵌入式消费 schematic、board revision、信号/电源假设和测量结果，但不能用软件日志替代硬件测量事实。硬件变化需要明确 revision 和影响范围。

### 测试/HIL

测试/HIL 提供执行环境和证据；领域专家定义验证意图和 required layer；最终 Verification 判断证据是否足够。

## 8. 边界冲突怎么处理

发生“两个系统都说自己是权威”时按以下顺序处理：

1. 先判断对象类型：源码、任务状态、知识、测试结果、发布制品还是领域结论；
2. 查询 Authority Index / Contract；
3. 若仍冲突，记录为 blocker，不由 Runtime 自行选择一个结果；
4. 由对应 Owner 做明确裁决；
5. 修改正式 Contract/Registry，避免下次重复争议。

边界不清本身就是工程风险，不应靠口头约定长期维持。
