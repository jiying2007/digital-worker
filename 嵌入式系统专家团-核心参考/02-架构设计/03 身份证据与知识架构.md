# 身份、证据与知识架构

## 1. 核心问题

一项嵌入式任务最终必须能回答：

> 这份结论针对哪个任务、哪份源码、哪个构建、哪个固件、哪台设备、哪次测试？

如果其中任何一环说不清，后续的“通过”“已修复”“可发布”都可能失去意义。

## 2. 身份主链

```text
work_item_id
   ↓
run_id
   ↓
repo_root + exact base commit
   ↓
build/config/toolchain
   ↓
artifact identity + SHA256
   ↓
board/device/firmware identity
   ↓
test/HIL run identity
   ↓
evidence ref
   ↓
verification / review decision
```

分支名、`latest`、聊天记录里的“刚才那个版本”都不能替代 exact identity。

## 3. 一份任务上下文

真实 Run 共享一份 Material/System Context。至少应明确：

- 仓库和完整 40-hex base SHA；
- 产品/项目、board revision、SoC/MCU；
- SDK、kernel、RTOS、toolchain；
- firmware/image；
- 设备和测试环境；
- schematic/TRM/datasheet 等关键材料；
- 缺失、过期或冲突的资料。

各专业角色可以补充材料，但不应各自维护互相不一致的“当前版本”。

## 4. Evidence-first

关键结论建议按以下结构表达：

```text
Claim
  + Evidence refs
  + Fact state
  + Confidence
  + Verification status
```

其中：

- `Observed`：日志、寄存器、代码、波形、hash、测试直接看到的事实；
- `Inferred`：依据事实推导但尚未用实验确认；
- `Confirmed`：经过独立证据或可重复实验确认。

Confidence 只表示判断把握，不代表验证等级。

## 5. 证据优先级不是固定一张表

不同结论需要不同证据。例如：

- 判断“代码是否包含某逻辑”：exact source；
- 判断“构建是否成功”：exact source + toolchain/config + build log + artifact；
- 判断“设备是否工作”：device identity + firmware hash + device run evidence；
- 判断“OTA 可发布”：source/artifact + upgrade/rollback + required device/HIL + open risk + human approval。

因此不能用“CI 很绿”替代所有后续证据。

## 6. 三种 Receipt/Report 不要混

### Delivery Receipt

回答“工程实施发生了什么”：修改、命令、构建、初步测试、产物、blocker 和风险。

### Runtime Execution Receipt

回答“哪个 Runtime/版本/分发身份执行了什么动作”，用于跨 Runtime 对比和审计。它属于执行身份，不等于领域验证。

### Verification Report

回答“现有证据真正证明到了哪一层”。

这三者职责不同。把它们合并成一个“执行成功”状态，会再次造成错误放行。

## 7. Acceptance → Evidence

每条 Acceptance Criterion 必须至少对应：

- required verification layer；
- artifact / device / test identity；
- evidence ref；
- `PASS / FAIL / BLOCKED / NOT_RUN`。

示例：

|验收项|验证层|对象身份|证据|状态|
|---|---|---|---|---|
|目标板连续运行 24h 无异常重启|device/hil|board=A3, fw=sha256:...|HIL run #xxx|PASS|
|升级掉电可恢复|device|boot/app exact image|power-loss test #yyy|FAIL|

第二条 FAIL 时，不能因为第一条 PASS 就把整体状态写成“验证完成”。

## 8. 知识架构

### 原则

**Source of Truth stays at source。**

Registry/搜索系统只保存“在哪里、谁负责、什么版本、谁能看、是否过期”等元数据，以及必要索引。

### Knowledge Registry 建议字段

- `knowledge_id`；
- title/domain/type；
- authority；
- source provider/ref；
- owner；
- product/platform scope；
- version/revision；
- ACL；
- freshness；
- tags；
- lifecycle status。

### 四类知识

1. Authority：Datasheet/TRM/SDK/Schematic/Git/CI-HIL evidence；
2. Engineering：Architecture、Design Rule、Compatibility、Porting；
3. Operational：RCA、Runbook、Known Issue、Checklist；
4. Execution：Skill、Golden Case、Evaluation Fixture、Tool Rule。

## 9. 知识冲突和过期

检索到多份内容时不做“多数票”。处理顺序：

1. 看 authority；
2. 看 version/revision 与适用平台；
3. 看 owner；
4. 看 freshness/expiry；
5. 必要时回到原始 Source；
6. 冲突仍无法解决则 BLOCK，并登记 stale/conflict。

## 10. 敏感数据和留存

以下内容原则上只保留受控引用，不直接提交本仓：

- 客户现场原始日志和 core；
- 生产固件、密钥、签名材料；
- HIL 串口可能包含的敏感上下文；
- 未脱敏的账号、路径、网络配置；
- 受供应商协议限制的资料。

Knowledge Provider 的“可搜索”不等于“允许复制”或“允许扩大访问范围”。

## 11. 完整性判断

一个 completed Run 至少要做到：

- exact source identity 不漂移；
- evidence artifact 有 hash；
- evidence set 与 bundle 对得上；
- required artifact 缺失时不能 completed；
- completed 后若发现事实错误，建立 superseding run，而不是静默改历史结果。
