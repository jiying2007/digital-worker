# 质量属性与非功能约束

功能流程回答“怎么做”，质量属性回答“这套工作方式长期必须具备什么特性”。当前阶段不为缺少真实数据的指标虚构数字；能量化的硬门槛直接写明，尚未量化的项绑定 Pilot 取证方式。

## 1. 质量属性总表

|属性|当前要求|当前状态|主要取证方式|
|---|---|---|---|
|Correctness|不得把缺失证据包装成 PASS；`incorrect_pass_rate = 0`|硬门槛|负向 fixture + real Pilot|
|Traceability|Task、source、artifact、device、test、decision 可追溯|硬要求|evidence bundle / identity coverage|
|Recoverability|单阶段失败可从责任阶段恢复，不要求整链重跑|已设计，待更多 real run 证明|resume/reflow 记录|
|Reliability|长稳/现场类结论必须说明时长、负载、错误阈值和恢复标准|按任务定义|device/HIL/long-run evidence|
|Security|越权动作、Secret 泄漏、不可逆操作无批准为安全失败|硬门槛|Action Policy + negative test + audit|
|Data Boundary|检索不得扩大原始 Source 的访问权限|硬要求|ACL negative / revoke test|
|Freshness|知识过期、版本冲突必须可识别并回到原 Source|待外部 Source Pilot 量化|freshness/stale/conflict tests|
|Availability|单个 Runtime/Provider 不可用时核心 Contract 和任务状态仍可继续|架构要求|provider failure / runtime switch Pilot|
|Performance|流程和检索开销不能显著抵消研发收益|尚未量化|task lead time / context rebuild / latency|
|Maintainability|同一规则只保留一份机器权威；解释文档不得形成第二套配置|已执行|CI 同步校验|
|Portability|更换 Runtime 不重做领域流程和 Verification 规则|待 Multi-runtime 证明|相同输入对照运行|
|Cost|成本用于方案比较，但不能以降低安全门槛换取成本优势|待 Pilot 量化|runtime/provider cost per completed task|

## 2. Correctness 与错误放行

最优先控制的不是“回答是否漂亮”，而是错误 PASS。以下情况必须保持 FAIL/BLOCKED/NOT_RUN：

- required evidence 缺失；
- source/artifact/device identity 对不上；
- required verification layer 没有执行；
- P0 正确性/安全 Finding 未关闭；
- A6/A7 缺人工批准；
- Release 必需 rollback/provenance 缺失。

项目进度和风险接受可以改变“是否继续业务动作”，不能改写这些事实状态。

## 3. Recoverability

恢复能力至少包括：

- Run 有明确状态和 resume point；
- Runtime 中断后能保留 worktree、receipt 和未完成步骤；
- Verification/Review Finding 能指出责任阶段；
- 已验证且未受影响的工作不机械重跑；
- completed 结果发现事实错误时建立 superseding run，不静默改历史。

真实 Pilot 需要记录“恢复花了多少人工时间”，用于判断流程是否真正可用。

## 4. Traceability

建议长期观察以下覆盖率：

- exact source coverage；
- artifact hash coverage；
- board/device identity coverage；
- Acceptance → Evidence coverage；
- audit trace completeness。

其中 Productionization 前 `audit_trace_completeness` 要求达到 1.0。

## 5. Knowledge freshness 与 ACL

外部知识源接入后至少做：

- 新版本发布后旧内容是否仍被错误召回；
- 原文删除后索引是否同步失效；
- 用户撤权后是否还能检索；
- 多份版本冲突时是否能识别 canonical authority；
- 引用是否能回到原 Source 和具体 revision。

在真实测试前不承诺统一 freshness SLA；不同 Source 可以有不同 SLA，但必须有 Owner 和测量方法。

## 6. Availability 与降级

Provider/Runtime 不可用时，优先保证以下能力仍存在：

1. Work Item / Run 身份；
2. Engineering Package；
3. evidence/receipt；
4. Verification/Review 事实状态；
5. 原始 Source 可访问路径。

可以降级到人工或备用 Runtime，但不得降级掉 evidence、权限和放行规则。

## 7. 性能和成本如何评估

当前不设置脱离真实任务的统一“响应时间 KPI”。优先测：

- 端到端 task lead time；
- Debug MTTR；
- context rebuild count；
- review re-ask count；
- human correction time；
- 知识检索延迟和命中后回源时间；
- Runtime/Provider 单个 completed task 成本。

只有真实数据连续证明某项成为瓶颈，才进入平台化优化。

## 8. 评审规则

任何新的平台能力如果声称改善质量属性，都要说明：

- 改善的是哪个属性；
- 如何测量；
- 是否引入新的复杂度或锁定；
- 失败时如何降级；
- 是否改变现有安全边界。

“更智能”“更自动”“更统一”本身不是质量属性。
