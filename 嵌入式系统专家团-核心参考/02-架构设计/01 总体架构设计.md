# 总体架构设计

## 1. 架构目标

嵌入式数字员工体系不是“多建几个 Agent”，而是建立一条可追溯、可替换 Runtime、可 fail-closed 的研发责任链。设计必须同时解决：

- 同一任务使用不同源码、固件、板卡或设备身份；
- 推断在协作过程中被误写成事实；
- Runtime 修改成功被误当作 Verification PASS；
- Hosted CI 被跨层推导为 Device/HIL/Release PASS；
- 知识全文被复制到多个仓形成第二 SSOT；
- Provider 更换导致流程、权限和 Evidence 语义漂移。

## 2. 责任模型

```text
Edge Foundation Domain
├─ Edge Coordination Role
├─ Structure Expert
├─ Hardware Expert
└─ Embedded System Expert
   └─ Capability → Skill

Assurance Plane
├─ Verification
└─ Independent Review
```

正式组织语义是：

`Domain → Expert → Capability → Skill`

Expert 数量不等于 Agent 数量；Capability 不等于 Worker；一个任务可以使用多个 Capability，但仍由同一个 Domain Expert 承担专业责任。

Embedded System Expert 当前固定 5 个 Capability：

`embedded.architecture / embedded.linux-bsp / embedded.mcu-rtos / embedded.driver-component / embedded.debug-reliability`。

## 3. 四个平面

### Responsibility Plane

定义“谁对什么专业结论负责”。由 Domain、Expert、Capability、Assurance contracts 构成。

### Orchestration Plane

定义“任务怎么被分类、路由、Gate、恢复和收口”。Edge Coordination 属于这一平面的责任 Role，但不新增专业 Expert 身份。

### Execution Plane

Engineer + replaceable Engineering Agent Runtime 实际执行代码修改、构建、测试、资料读取等动作。Runtime 是执行机制，不拥有 Domain responsibility。

### Assurance Plane

Verification 负责直接 Evidence 与验证层级；Independent Review 在需要时独立检查风险和错误放行。当前 iterative Pilot 允许 Review unavailable 时使用 static/Hosted CI + Verification evidence 作为 completion substitute，但不改变长期 Assurance 边界。

## 4. 工作链

```text
Task / Work Item
→ Material & System Context
→ Edge Coordination
→ Routed Domain Expert / Capability
→ Technical Decision
→ Engineering Package
→ Engineer + Runtime
→ Delivery Receipt
→ Verification
→ optional Independent Review when available
→ Human Gate for high-risk action
→ Closure / Knowledge Harvest
```

任何阶段都必须保留 exact identity、未验证项和 residual risks。缺材料时正确结果可以是 BLOCKED。

## 5. 控制面与仓库边界

长期采用四个稳定控制面 + N 个 Runtime Binding：

- `digital-worker`：责任模型、Task/Gate、Action Policy、Evidence、Verification、Pilot；
- `knowledge-hub`：知识 authority / ACL / freshness / lifecycle / retrieval；
- `agent-dev-kit`：可复用 Agent/Skill 资产、Asset Profile、immutable release；
- `llm_agent`：外部实践、健康度、采用度、Runtime comparison；
- Runtime Binding：Codex/其他 CLI、IDE 或内部执行环境。

Thin Session Bootstrap 只负责单次会话装配，不成为新的控制面。

## 6. Target routing 与当前执行

目标高层模式为：

`single_domain / multi_domain / diagnostic / review`。

当前 `canonical_routing_switched=false`，所以 legacy task/mode 仍作为执行 adapter；但目标语义由 `domains/edge-foundation/routing-shadow.yaml` 维护。核心参考展示 target mode / Expert / Capability / Assurance，不再把兼容执行身份当组织结构。

跨域升级必须 evidence-triggered。例如 Bring-up/Driver 只有出现板级电气状态、原理图/电源时序、信号完整性等真实证据时才升级到 Hardware Expert。

## 7. Identity / Evidence spine

每个真实 Run 至少绑定：

```text
work_item_id / run_id
repo + full base SHA
artifact / firmware identity
board / device / test identity
Acceptance Criteria
Engineering Receipt
Verification Evidence
open risks / unverified items
Runtime binding identity when used
```

Source of Truth stays at source。本仓不复制源码、原始日志、原理图、测试全文或知识全文形成第二权威源。

## 8. Golden Cases 与 Skill ownership

Golden Case 唯一权威：`domains/edge-foundation/evaluation/golden-cases.yaml`。

Skill ownership 唯一 target registry：`domains/edge-foundation/skills.yaml`。Skill 文件在 canonical switch 前仍可能物理位于兼容目录，但**物理路径不定义 owner**。

同理 Gate ownership 以 `domains/edge-foundation/gate-policy.yaml` 为准，Verification / Review 不再作为 Embedded 专业角色出现在核心能力目录。

## 9. Provider-neutral

Provider-neutral 表示：

- Runtime 可替换；
- Domain responsibility、Capability、Gate、Evidence、Action Policy 不随品牌变化；
- Runtime-local PASS 不能形成 Domain Verification PASS；
- Provider 切换不得丢失 Work Item、exact source、Acceptance、风险和未验证项。

## 10. 当前成熟度边界

Feature real Pilot 已完成并形成首条 eligible receipt；Debug 与 Review/Release 仍缺真实外部/设备 Evidence。三轨未满足前 phase-3 readiness 正确保持 BLOCKED，`canonical_routing_switched=false`。

当前不把 Knowledge Graph、统一 Context Broker、统一 Runtime Gateway、更多 Expert/Agent 或 A5-A7 自动化当成前置条件。只有重复真实 evidence 证明需要时才增加平台层。
