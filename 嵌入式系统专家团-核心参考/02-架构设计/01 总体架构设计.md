# 总体架构设计

## 1. 架构目标

嵌入式数字员工体系不是“多建几个 Agent”，而是建立一条可追溯、可替换 Runtime、可 fail-closed 的研发责任链。设计必须同时解决：源码/固件/板卡/device identity 漂移、推断被写成事实、Runtime PASS 被误当 Verification PASS、Hosted CI 被跨层推导为 Device/HIL/Release PASS、知识复制形成第二 SSOT，以及 Provider 更换导致 Contract 漂移。

## 2. 责任模型

```text
Edge Foundation Domain
├─ Edge Coordination Role
├─ Structure Expert
├─ Hardware Expert
└─ Embedded System Expert
   └─ Capability → Skill

Assurance Plane
├─ Verification
├─ Independent Review
├─ Evidence
└─ Evaluation
```

正式组织语义是 `Domain → Expert → Capability → Skill`。Expert 数量不等于 Agent 数量；Capability 不等于 Worker；同一 Embedded System Expert 可以按影响面组合多个 Capability。

Embedded System Expert 当前固定 5 个 Capability：`embedded.architecture / embedded.linux-bsp / embedded.mcu-rtos / embedded.driver-component / embedded.debug-reliability`。

## 3. 四个平面

### Responsibility Plane
定义谁对什么专业结论负责，由 Domain、Expert、Capability、Assurance contracts 构成。

### Orchestration Plane
定义任务怎么分类、路由、Gate、恢复和收口。Edge Coordination 属于这一平面的责任 Role，不新增专业 Expert。

### Execution Plane
Engineer + replaceable Engineering Agent Runtime 实际执行代码修改、构建、测试和资料读取。Runtime 是执行机制，不拥有 Domain responsibility。

### Assurance Plane
Verification 负责直接 Evidence 与验证层级；Independent Review 在需要时独立检查风险与错误放行。当前 iterative Pilot 允许 Review unavailable 时使用 static/Hosted CI + Verification evidence 完成 Pilot，但不改变长期 Assurance 边界。

## 4. 工作链

```text
Task / Work Item
→ Material & System Context
→ Edge Coordination
→ Routed Domain Expert / Capability
→ Technical Decision
→ Engineering Package
→ Engineer + Runtime
→ Delivery Receipt
→ Verification
→ Review when required/available by current-stage policy
→ Human Gate for high-risk action
→ Closure / Knowledge Harvest
```

任何阶段都必须保留 exact identity、未验证项和 residual risks。缺材料时正确结果可以是 BLOCKED。

## 5. 控制面与仓库边界

- `digital-worker`：责任模型、Routing、Task/Gate、Action Policy、Evidence、Verification、Pilot、Product readiness；
- `knowledge-hub`：知识 authority / ACL / freshness / lifecycle / retrieval；
- `agent-dev-kit`：可复用 Agent/Skill 资产、Asset Profile、immutable release；
- `llm_agent`：外部实践、健康度、采用度、Runtime comparison；
- Runtime Binding：Codex/其他 CLI、IDE 或内部执行环境。

Thin Session Bootstrap 只负责单次会话装配，不成为新控制面。

## 6. Canonical routing

高层责任模式保持：`single_domain / multi_domain / diagnostic / review`。

`domains/edge-foundation/routing.yaml` 是 canonical routing authority，`runtime/task-modes.yaml` 定义实际 runtime mode 与允许范围；两者由 CI 强制 14 类 task taxonomy 一致。跨域升级必须 evidence-triggered，例如 Bring-up/Driver 只有出现板级电气状态、原理图/电源时序、信号完整性或供电证据时才升级到 Hardware Expert。

## 7. Identity / Evidence spine

每个真实 Run 至少绑定：

```text
work_item_id / run_id
repo + full base SHA
artifact / firmware identity
board / device / test identity
Acceptance Criteria
Engineering Receipt
Verification Evidence
open risks / unverified items
Runtime binding identity when used
```

Source of Truth stays at source。本仓不复制源码、原始日志、原理图、测试全文或知识全文形成第二权威源。

## 8. Golden Cases / Skills / Gates

Golden Case 唯一权威：`domains/edge-foundation/evaluation/golden-cases.yaml`。

Skill registry 与物理路径唯一权威：`domains/edge-foundation/skills.yaml`，23 个 Skill 均位于 `domains/edge-foundation/skills/<id>/SKILL.md`，frontmatter owner 必须与 registry 一致。

Gate ownership 唯一权威：`domains/edge-foundation/gate-policy.yaml`。Verification / Review 属于 Assurance，不作为 Embedded 专业角色出现。

## 9. Provider-neutral

Provider-neutral 表示 Runtime 可替换；Domain responsibility、Capability、Gate、Evidence、Action Policy 不随品牌变化；Runtime-local PASS 不能形成 Verification PASS；Provider 切换不得丢失 Work Item、exact source、Acceptance、风险和未验证项。

## 10. Product readiness 边界

架构/runtime 已切为 canonical Edge Foundation，不再由产品试点成熟度控制 routing authority。当前真实产品证据状态仍是 Feature 1 条 eligible、Debug 0、Review/Release 0，因此 Product readiness 保持 BLOCKED。只有三轨都满足真实 Evidence 后，才可进入 Productionization Review；这仍不自动等于 Release Ready 或 Production Ready。
