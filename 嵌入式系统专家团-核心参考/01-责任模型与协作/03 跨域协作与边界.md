# 跨域协作与边界

本页只说明 Edge Foundation 内部什么时候需要跨 Expert 协作。默认原则是：**单域优先，证据触发跨域，复杂度本身不是升级理由。**

## 1. 三个 Domain Expert

- Structure Expert：结构、机构、装配、机械约束等专业责任；
- Hardware Expert：原理图、电气接口、器件、电源、时序、板级测量等专业责任；
- Embedded System Expert：Linux / BSP / MCU / RTOS / Driver / Component / Debug / Reliability 等软件专业责任。

Edge Coordination 只组织协作，不替任何 Expert 做专业结论。

## 2. 默认单域

以下任务即使内部涉及多个 Embedded Capability，默认仍是 `single_domain` 或 `diagnostic`：

- Boot / Kernel / DT / Storage / UBIFS；
- MCU Startup / Linker / RTOS / HardFault；
- Driver / Component / API；
- 性能、长稳、Crash、Memory、Deadlock/Race；
- 普通 Feature / Porting / Review。

例如新 I2C 传感器驱动需要 `embedded.driver-component + embedded.linux-bsp`，仍然属于 Embedded System Expert 内部协作。

## 3. Hardware Expert 的 evidence-triggered escalation

`platform_bringup` 和 `driver_development` 当前定义了明确跨域触发条件。典型证据包括：

- board electrical state 无法由软件证据确认；
- schematic 与实际 power sequence / pin state 不一致；
- peripheral electrical interface 不确定；
- signal integrity / power cause 有直接迹象；
- 缺少决定软件行为所必需的电气契约。

命中后才从 Embedded 单域升级为 `multi_domain`，并记录触发 Evidence。没有证据时，不因为“怀疑硬件”就创建 Hardware 结论。

## 4. Structure Expert 的边界

当前 Embedded routing 没有默认把 Structure Expert 拉入软件任务。只有产品结构、机械装配、运动机构、散热/空间/物理接口等事实成为问题的必要条件时，才由 Edge Coordination 建立跨域工作项或明确 handoff。

软件日志不能替代结构/机械测量；同样，结构判断也不能替代软件源码、trace 或设备验证。

## 5. Assurance 不是第四个业务域

Verification / Independent Review 属于 Assurance Plane。它们可以服务任何 Domain Expert，但不应作为“另一个专业 Expert”出现在任务路由里。

- Verification 判断 Acceptance 对应的直接 Evidence 是否满足；
- Independent Review 在需要时检查风险、证据、错误放行和 Release Readiness；
- Human Gate 决定 A6/A7 等高风险动作授权。

## 6. 跨域交接最小内容

任何跨域 handoff 至少包含：

1. Work Item / Run identity；
2. exact source / board / device / artifact identity；
3. 已确认事实与未确认假设；
4. 请求另一 Expert 判断的具体问题；
5. 所需 Evidence 与返回格式；
6. 对 Acceptance / Verification / rollback 的影响。

禁止只写“请硬件看看”“请结构确认”而没有问题边界和证据请求。

## 7. Source of Truth

跨域协作不复制权威资料。原理图、TRM、代码、日志、测试报告、设备测量各自保留在权威 Source，本仓只保存 identity、引用、必要摘要与 Evidence relationship。这样才能避免跨团队协作重新产生第二 SSOT。
