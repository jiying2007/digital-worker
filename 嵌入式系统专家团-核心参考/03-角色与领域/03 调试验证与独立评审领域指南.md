# 调试、验证与独立评审领域指南

# 一、调试与可靠性

## 1. 责任

调试负责人维护问题事实链、Hypothesis Registry 和 Root Cause 推进过程；Linux/MCU/Driver 等领域专家提供对应平台事实。

它不是“万能技术专家”，也不应脱离领域 Owner 对具体寄存器、协议或板级能力做无证据判断。

## 2. 时间线优先

复杂问题先建立事件时间线：

- 正常状态；
- 第一个异常迹象；
- 错误/恢复动作；
- 最终用户可见故障；
- 重启/掉电/恢复。

很多 Root Cause 被误判，是因为只看最后一条错误，没有看第一个异常点。

## 3. Hypothesis 质量

一个好的假设：

- 能解释主要现象；
- 可被实验证伪；
- 有明确 evidence_for / evidence_against；
- 不把多个独立原因混成一句话；
- 有下一步 discriminating experiment。

坏例子：“可能是系统不稳定”。

好例子：“DMA completion 中断到达后 CPU 读取的 buffer 仍为旧 cache line；若对相同范围做 invalidate 后错误消失，支持 cache maintenance 假设”。

## 4. 长稳和偶发问题

除了单次复现，还要记录：

- 运行时长和发生频率；
- 温度/功耗/负载；
- memory/handle/socket/task 指标趋势；
- 重试/恢复次数；
- watchdog/reset reason；
- 环境变化。

偶发问题不能只靠“跑了一夜没再出现”证明修复。

# 二、验证

## 1. 验证的对象是 claim

验证不是“跑测试清单”，而是证明具体验收项。

例如“低速电机控制更平顺”必须转成可重复的测量和判定条件；“系统稳定”需要定义时长、负载、异常阈值和恢复标准。

## 2. Verification Plan 至少包含

- acceptance criterion；
- required layer；
- object identity；
- precondition；
- steps；
- expected result；
- evidence；
- failure handling；
- regression scope。

## 3. Build evidence

必须能定位：source/base、toolchain、config、command、target、artifact/hash、warning/error。

## 4. Device evidence

必须能定位：board/device、firmware hash、环境、步骤、日志/measurement 和结论。

## 5. HIL evidence

必须能定位：case、fixture/environment、target identity、run result、artifact/log hash。不能使用“实验室同事说跑过”作为正式 HIL PASS。

## 6. PASS_WITH_RISK

只有在 required evidence 已达到基本要求、剩余风险已清楚且有明确接受人时使用。缺 required layer 不应转换成 PASS_WITH_RISK。

# 三、独立审查

## 1. Review 重点

- 技术结论是否真的被 evidence 支持；
- required verification 是否完整；
- blocker/unverified item 是否被隐藏；
- action policy 是否越界；
- 回滚、版本兼容、provenance 是否满足；
- Release 是否还有 P0/P1 finding；
- 当前状态描述是否夸大。

## 2. Code Review 场景

`code_review` 默认 `review_only`：

- 只评审，不隐式修改；
- 先判断变更风险；
- 需要领域事实时拉 BSP/MCU/Driver；
- 需要修复时另开工程执行链；
- 修改后的 diff 需要重新 Review。

## 3. Release Review 场景

Review Governor 重点看：

- source/artifact identity；
- Verification required layer；
- rollback/provenance；
- open risk / waiver；
- 人工 Release approval；
- 版本升级/降级路径。

HIL PASS 不能直接推导 Release PASS。

# 四、三者如何形成闭环

```text
Debug/Reliability
  负责找出“为什么”
       ↓
Engineering
  负责实施“怎么改”
       ↓
Verification
  负责证明“改完后证据说明什么”
       ↓
Independent Review
  负责判断“这些证据是否足以交付/放行”
```

任何角色同时承担四个环节都会提高确认偏差和错误放行风险。

# 五、审查时的红线问题

遇到以下情况应暂停“继续优化”而先修证据链：

- Root Cause 没有 discriminating evidence；
- 实现者同时给自己 final verification + final review；
- 设备/固件版本无法确认；
- Acceptance 与测试用例无法对应；
- Release 缺 rollback，却因为进度原因直接放行；
- 结果只存在聊天总结，没有受控 evidence ref。
