# 调试与可靠性领域指南

## 1. 职责

调试与可靠性负责把异常从现象、时间线、假设和实验推进到可证实 Root Cause，并定义最小修复和回归边界。具体平台事实仍由 BSP/MCU/Driver 等领域 Owner 提供。

## 2. 必要输入

- exact source/firmware/device；
- 现象、时间、概率和环境；
- 完整前后文日志/trace/core/dump/register；
- 最近变更和版本差异；
- 原复现步骤；
- 性能/长稳趋势数据（如适用）。

## 3. 工作顺序

```text
冻结 Context
 → 建时间线
 → 区分 Observed / Inferred / Confirmed
 → 一份 Hypothesis Registry
 → discriminating experiment
 → reject / support / confirm
 → Root Cause
 → 最小修复
 → regression / stress / failure injection
```

## 4. Hypothesis 质量

好的假设必须可证伪、有 evidence_for/evidence_against，并说明实验结果如何区分候选。坏例子是“系统不稳定”“可能硬件问题”这种无法直接验证的描述。

## 5. 长稳/偶发问题

至少记录运行时长、发生频率、负载、温度/功耗、memory/handle/socket/task 趋势、恢复/重试次数和 reset reason。

“跑了一夜没出现”只能说明当前样本未复现，不能单独证明修复。

## 6. 常见诊断模型

- Crash/HardFault：fault context + ELF/map + task/ISR；
- Memory corruption：OOB/UAF/double free/stack/DMA ownership/cache/concurrency；
- Deadlock：wait-for graph + lock order + priority + ISR；
- Storage：media/ECC→MTD→UBI→FS→app；
- Performance：baseline→measurement→bottleneck→change→remeasurement。

## 7. Root Cause 确认

至少要求：能解释主要现象、与版本/平台差异一致、有区分其他候选的 evidence、修复/故障注入按预期改变结果，并能由 Verification 独立复核。

若只能做到“改后暂时不出现”，应保持 supported/workaround，不写 confirmed root cause。

## 8. 常见失败模式

- 只看最后一条 error，不看第一个异常点；
- 先认定根因，再只搜支持证据；
- 不同专业维护多份互相矛盾的 RCA；
- 一次改多个变量导致无法确认因果；
- 复现版本和验证版本漂移；
- 用置信度代替 evidence。

## 9. 输出

时间线、Hypothesis Registry、Root Cause/evidence insufficient、engineering recommendation、regression scope、residual risk 和 Knowledge candidate。

## 10. 边界

调试负责人主导方法和根因闭环，不替领域 Owner 编造寄存器、协议或硬件事实；实施修改、Verification 和 final Review 仍分别独立。
