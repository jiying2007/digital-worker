# 驱动与组件领域指南

## 1. 职责

驱动与组件负责把具体硬件能力可靠地接入系统，并把一次性项目实现收敛为可维护、可测试、可移植的接口。

## 2. 分层模型

```text
Hardware / Bus
   ↓
Low-level Driver
   ↓
Platform Adapter
   ↓
Stable Component API
   ↓
Application / Service
```

平台事实尽量停留在底层和 Adapter，不让业务层长期绑定 DTS 节点、寄存器地址或板级 GPIO 编号。

## 3. 必要输入

- hardware/board/device identity；
- datasheet/TRM/schematic；
- bus/protocol；
- Linux/MCU 平台资源；
- current driver/component/API；
- error/timeout/power 行为；
- firmware/NVM/calibration；
- 目标平台和复用范围。

## 4. Driver Integration Review

至少检查：

1. identity/resource；
2. init/probe/deinit；
3. IRQ/DMA/thread context；
4. error/timeout/retry；
5. power/suspend/resume；
6. concurrency/lifetime；
7. API/ABI/version；
8. logging/diagnostics；
9. build/config；
10. test/rollback/field diagnosability。

## 5. 器件替代 Compatibility Matrix

至少覆盖：电气/板级、总线协议、初始化、能力差异、时序/性能、异常行为、firmware/NVM、Linux/MCU 接口、生产校准/测试和回归范围。

“API 兼容、能编译”只能证明很小一部分兼容性。

## 6. 组件化判断

适合沉淀公共组件的信号：

- 至少两个平台/项目重复使用；
- 差异点可明确隔离；
- stable API 能覆盖真实需求；
- 测试和诊断方式可复用；
- 抽象不会隐藏关键硬件约束。

不要为尚未发生的第三个平台提前增加复杂抽象。

## 7. 常见失败模式

- init 成功但 deinit/error recovery 缺失；
- timeout 后资源/lifetime 没有恢复；
- suspend/resume 只测正常路径；
- API 过度暴露平台细节；
- workaround 无适用条件和退出计划；
- 替代器件只做功能 smoke，不测异常/功耗/生产流程；
- 日志无法定位 bus/device/error state。

## 8. 输出

输出应包含 integration checklist、API/compatibility、error/power/concurrency 行为、平台差异、回归范围、技术债和 Verification 要求。

## 9. 边界

Linux 平台资源由 BSP 证明；MCU scheduling/ISR discipline 由 MCU/RTOS 证明；系统级职责和 API 边界由架构决定；Root Cause 流程由调试可靠性主导。
