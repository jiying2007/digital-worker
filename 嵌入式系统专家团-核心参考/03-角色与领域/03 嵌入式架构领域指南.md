# 嵌入式架构领域指南

## 1. 职责

嵌入式架构负责把产品/工程目标转成可实现的系统边界和技术约束，重点回答“系统怎么分、接口怎么定、资源够不够、失败怎么隔离、如何验证”。

主要覆盖 Linux/MCU/RTOS 分工、进程/任务模型、IPC、资源预算、Boot/OTA/Power、故障隔离、API/ABI、平台抽象、性能/实时性/可靠性目标分解。

## 2. 必要输入

- Task Brief 与 Acceptance；
- 产品/平台/board/SoC/MCU identity；
- 当前系统架构、接口和依赖；
- CPU/RAM/ROM/buffer/thread/task 现状或预算；
- 时延、周期、功耗、成本、可靠性约束；
- 相关 TRM/datasheet/schematic/source/log/evidence。

缺少资源事实时可以给 target/budget 和风险，不把目标数字写成已经测得的数据。

## 3. 判断顺序

```text
目标与约束
 → 模块/责任边界
 → 接口与数据流
 → 资源与时序预算
 → 生命周期与失败模式
 → 平台/版本兼容
 → 实施边界
 → Verification 范围
```

## 4. 设计检查

### 模块和责任

- Linux 与 MCU 各自承担什么；
- 哪些能力属于 BSP、Driver、Service、Application；
- 是否出现两个模块都认为对方负责的空档；
- 是否为了复用而提前增加没有真实需求的抽象层。

### 接口

至少说明 owner、方向、sync/async、数据单位、lifetime、thread/ISR context、timeout/retry、错误码、versioning、compatibility 和 rollback。

### 资源

资源预算至少区分 target 与 measured：CPU、RAM、ROM、stack、buffer、DMA/CMA、task/thread、带宽和存储。

### 生命周期

检查 boot、normal runtime、suspend/resume、watchdog/recovery、OTA/rollback、异常掉电和升级中间态。

## 5. 常见失败模式

- 接口只定义正常路径，没有 timeout/error/version；
- Linux/MCU 同一字段单位或枚举语义不一致；
- 资源数字来自估算却被写成实测；
- 为“未来平台化”增加当前无人使用的抽象；
- 只设计升级后的终态，不考虑升级中间态；
- 架构文档要求领域事实服从假设，而不是根据 TRM/代码更新设计。

## 6. Evidence

架构结论常用证据：

- exact source/interface；
- TRM/datasheet/schematic；
- map/size/profile；
- timing trace/measurement；
- compatibility matrix；
- prototype/device/HIL 结果。

“业界一般这样做”只能作为候选方案来源，不是本项目事实。

## 7. 输出

至少形成：

- architecture impact；
- interface/compatibility 结论；
- resource/timing budget 与待验证项；
- failure/recovery；
- platform/version impact；
- engineering scope；
- Verification 要求；
- unresolved questions / risks。

## 8. 边界

架构可以提出 BSP/MCU/Driver 的验证要求，但不替领域 Owner 证明具体寄存器、时钟、协议或硬件事实，也不能自签最终 Verification PASS。

出现系统级职责冲突、跨仓接口冲突、资源预算互相挤压或 OTA/Power 生命周期变化时，应由架构角色参与收敛。
