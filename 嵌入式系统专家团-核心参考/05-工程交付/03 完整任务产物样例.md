# 完整任务产物样例

本例使用一个虚构的 UBIFS 异常只读任务，把核心产物用同一 `work_item_id / run_id / source identity` 串起来。示例文件位于 [`examples/ubifs-run/`](examples/ubifs-run/)。其中 JSON 文件由核心参考校验器按现有 Schema 校验；示例不代表真实 Pilot evidence。

## 1. 固定身份

```text
work_item_id: EXAMPLE-EMB-001
run_id: EXAMPLE-UBIFS-001
repo: firmware/main
base_commit: 1111111111111111111111111111111111111111
board: example-board-rev-a
device: EXAMPLE-DEVICE-001
```

后续每个产物都引用这组身份。真实任务中如果 base/board/firmware 改变，应显式产生新的 evidence 或 Run，而不是静默复用旧结论。

## 2. 产物链

```text
task-brief.json
  ↓
material-manifest.json
  ↓
task-charter.json
  ↓
routing-decision.json
  ↓
technical-analysis.json
  └─ hypothesis-registry.json
  ↓
technical-decision.json
  ↓
engineering-task-package.json
  ↓
delivery-receipt.json
  ↓
acceptance-evidence-matrix.md
  ↓
verification-report.json
  ↓
review-report.json
  ↓
deliverable-manifest.json
  ↓
knowledge-harvest.md
```

## 3. 关键变化如何逐步收敛

### Task Brief

只描述工程目标、非目标、验收、仓库和动作边界。此时不预设 Root Cause。

### Material Manifest

确认 exact base、board、firmware、device 和 test environment 都可用。缺关键 identity 时不能进入正式诊断。

### Task Charter / Routing

把入口任务转换成 `defect_debugging + diagnostic_chain`，主责为调试可靠性，BSP 作为领域协作者。

### Technical Analysis / Hypothesis

Technical Analysis 只写当前事实和风险；Hypothesis Registry 单独维护 H1/H2 等候选及实验，不把推断直接写成根因。

### Technical Decision

只有假设收敛后才形成工程决策。本例选择“修正 MTD/ECC status mapping，同时保留真正 uncorrectable 的 fail-closed 行为”。

### Engineering Package

把修改范围、base、计划、动作上限和 required verification 交给工程实施。

### Delivery Receipt

记录实际改了什么、跑了什么、生成了什么 artifact。Receipt 不负责宣布最终 PASS。

### Acceptance → Evidence

把“交叉构建通过”和“目标设备复现条件不再出现只读”分别映射到直接 evidence。

### Verification / Review

Verification 证明 cross-build/device 证据成立；Review 再检查是否只是吞错、是否保留真正 ECC failure 的错误路径和残余风险。

### Closure / Knowledge

Deliverable Manifest 只在 blocker/unverified item 处理后进入 COMPLETED。Knowledge Harvest 再判断是否形成可复用的 ECC mapping / UBI-UBIFS Runbook。

## 4. 为什么要保留这些中间产物

不是为了“文件越多越规范”，而是为了避免几类高频丢失：

- Task Brief 不保存 Root Cause，避免入口假设污染诊断；
- Hypothesis 与 Technical Decision 分开，避免候选变结论；
- Package 与 Receipt 分开，避免“计划做了什么”和“实际做了什么”混用；
- Receipt 与 Verification 分开，避免 Runtime 自签 PASS；
- Verification 与 Review 分开，避免风险接受改写验证事实。

简单任务可以让部分阶段更轻，但这些语义不能被合并成一个模糊的“处理结果”。
