# 权限、安全、风险与例外

> **本页是 A0-A7 Action 与高风险人工边界的唯一详细人类来源。** 其他总览和案例只摘要或引用；机器权威是 `domains/edge-foundation/runtime/action-policy.yaml`。

## 1. 权限按动作，不按工具品牌

当前使用 A0-A7：

|等级|动作|默认策略|
|---|---|---|
|A0|读取已授权源码、文档、日志、配置和证据|允许|
|A1|静态分析、检索、风险识别、方案比较|允许|
|A2|生成设计、任务包、补丁建议、测试计划、知识候选|允许|
|A3|修改隔离工作树/任务分支|受控|
|A4|Host/交叉构建/受控测试|受控|
|A5|串口/JTAG/SSH/ADB 等设备只读诊断|需授权|
|A6|烧录、配置写入、重启、升级等改变设备状态动作|需人工批准|
|A7|发布、签名、promotion、生产 OTA|需人工批准|

Codex、Claude、IDE、WorkBuddy 或其他办公入口都不能天然获得更高等级。Runtime Binding 只能在已授权 action ceiling 内执行。

## 2. A3/A4 前置条件

修改工作树前至少确认 repo root、exact base commit、dirty baseline、scope 和 action ceiling。构建/测试前至少确认 command scope、toolchain/config、目标平台以及 artifact identity 的记录方式。

A3/A4 成功只说明对应工程动作完成，不能自动推导 Verification、Device、HIL、Release 或 Production PASS。

## 3. A5/A6 设备边界

设备访问必须绑定具体 target identity。A6 还需要：rollback/recovery、明确批准人、写入内容和范围、失败后的设备状态处理。不要使用“测试机”这种模糊名称作为正式 identity。

对于 Boot、Flash、OTA、文件系统恢复、电机控制参数写入等可能改变设备状态的操作，必须先区分“取证”与“修复动作”。能先只读取证时，不应直接进入破坏性或不可逆路径。

## 4. A7 发布边界

至少要求：Release Owner、source/artifact identity、release evidence、required Verification、适用的 Review、rollback/provenance 与 explicit human approval。自动生成 release note、Hosted CI 全绿或单台设备成功，都不等于获得发布权限。

## 5. 默认禁止自动执行的事项

- OTP/Fuse；
- 导出生产签名密钥；
- 绕过批准服务直接生产签名；
- 不可逆 Boot 配置；
- 破坏性生产数据操作；
- 未经过 Release Gate 的生产 OTA；
- 在没有明确 target identity / rollback 的情况下进行设备状态写入。

## 6. Secret 与敏感资料

普通交付物不应包含密钥、token、密码、生产签名材料、客户隐私数据、未脱敏 core/log、供应商保密全文、内网敏感拓扑或凭证。

推荐做法：保留受控 Source 的引用；必要时记录 hash；文档只描述结论和最小上下文；对 Knowledge Provider 做 ACL negative test；删除或撤权后验证索引同步失效。

## 7. Risk Acceptance

不能立即修复但业务确需继续时，至少记录 risk、severity/impact、evidence、mitigation、owner、acceptor、expiry/target fix、rollback 以及对 Release/客户的影响。

Risk Acceptance 不能改变 Verification 的事实状态，例如 HIL 没跑仍然是 NOT_RUN；也不能把缺失的 rollback、device evidence 或 A7 approval 变成 PASS。

## 8. Stage-aware 仓库治理

当前仓库处于 `iterative-development`：repository-local CI 继续要求；main server-side protection 暂不作为 real Pilot 的前置条件；治理审计当前可以 advisory；进入 Productionization 前必须启用 strict server governance 并通过 `verify_repository_governance.py --strict`。

这不是降低质量要求，而是把“真实任务闭环”和“多人生产化治理”按阶段拆开。Canonical routing 已成立也不等于 Product readiness、Release readiness 或 Production readiness 已完成。

## 9. 安全失败优先级

以下问题优先于效率和速度：incorrect PASS、unauthorized action、identity 静默断链、生产 Secret 泄漏、不可逆操作无批准、Release 无 rollback/provenance、权限撤销后知识系统仍可检索。

这些指标不应被平均满意度或开发速度抵消。任何 Runtime、Capability 或 Skill 的扩展都必须继续服从 action policy、Gate 和 Assurance 的 fail-closed 约束。
