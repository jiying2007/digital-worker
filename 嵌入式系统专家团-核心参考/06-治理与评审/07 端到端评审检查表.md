# 端到端评审检查表

> 用于正式设计评审、阶段评审、Pilot 复盘与 Productionization 前检查。  
> 不要求每次逐项机械打勾；但任何宣称“闭环、成熟、可生产化”的结论，都应能覆盖相关章节。

## A. 架构与边界

- [ ] Domain / Role / Expert / Capability / Skill 五类概念是否没有混用？
- [ ] Edge Coordination 是否仍是 Role，而不是第四 Expert？
- [ ] Structure / Hardware / Embedded System 三个 Domain Expert 的边界是否清楚？
- [ ] Verification / Independent Review 是否仍在 Assurance plane？
- [ ] 是否存在第二套路由、shadow mapping、旧 compatibility tree 回流？
- [ ] Runtime 替换后责任模型是否仍成立？
- [ ] Product readiness 是否没有反向控制 canonical routing？
- [ ] 历史设计只由 ADR/Git 保存，而不是继续成为活动控制面？

## B. 责任与 RACI

- [ ] 每个重要决策有唯一 accountable owner？
- [ ] Coordination 是否避免替专业 Capability 给结论？
- [ ] Engineering 是否不能自签 Verification？
- [ ] Review 是否不执行工程修改？
- [ ] A6/A7 是否仍由授权人类批准？
- [ ] 跨域升级是否有 evidence trigger，而不是“多叫几个专家更保险”？
- [ ] shared ownership 是否有 canonical owner 和 consume/provide 边界？

## C. Task / Routing / Mode

- [ ] 所有受支持 task type 都在 routing 中有明确映射？
- [ ] unknown task 是否 fail-closed？
- [ ] diagnostic task 是否保持 hypothesis/evidence 驱动？
- [ ] review task 是否禁止隐式 execution？
- [ ] release task 是否绑定 verification/review/human approval？
- [ ] 简单任务是否避免不必要的多域展开？
- [ ] capability expansion 是否有清晰触发条件？

## D. Skill 体系

- [ ] 当前 canonical Skill 与 planning candidate 是否明确分开？
- [ ] 每个 Skill owner 是否与 registry 一致？
- [ ] 每个 Skill 是否有明确 Use When / Do Not Use For？
- [ ] Required Inputs 是否足以判断 READY/BLOCKED？
- [ ] Method 是否可以由不同 Runtime 重复执行？
- [ ] Output 是否能被后续 Gate/Assurance 消费？
- [ ] Evidence rule 是否区分 Observed / Inferred / Confirmed？
- [ ] Action ceiling 是否明确？
- [ ] 是否存在“Skill 文件有了就宣称能力成熟”的误判？
- [ ] 新 Skill 是否有重复真实任务证据，而不是目录对称需求？
- [ ] 是否有 Skill 拆分/合并/退役机制？
- [ ] 23 个 canonical Skill 是否都存在 positive + BLOCK evaluation case？
- [ ] 是否把 Skill invocation provenance 和 Skill evaluation verdict 明确分开？
- [ ] `EVALUATED` 是否要求 positive + BLOCK 两张独立 semantic PASS evidence，而不是单 case/CI fixture？
- [ ] semantic evidence 是否绑定 evaluator identity、ref 与 SHA-256？
- [ ] positive + BLOCK 是否使用同一 frozen Skill Contract / Runtime / source type？
- [ ] real Pilot 是否真的冻结 Runtime-owned Skill invocation receipt，还是仅凭事后说明？
- [ ] Skill maturity 是否没有被转换成 Product readiness 或扩大 Action authority？

## E. Material / Context / Identity

- [ ] exact repository / commit / branch/base 是否绑定？
- [ ] firmware/image/artifact identity 是否绑定？
- [ ] board/device/SKU/revision 是否绑定？
- [ ] flash/partition/kernel/config/toolchain/test environment 是否按任务需要绑定？
- [ ] 日志是否来自目标对象，而非“类似版本”？
- [ ] 材料缺失时状态是否真实保持 BLOCKED/DEGRADED？
- [ ] L1→L2 等治理升级后是否重新冻结 Execution Source Set？

## F. Engineering Execution

- [ ] Engineering Package 是否包含 acceptance、scope、source set、action ceiling、rollback？
- [ ] Runtime identity 是否可追踪？
- [ ] 执行动作是否在允许 action level 内？
- [ ] 多仓修改是否有一致 source/artifact identity？
- [ ] 部分成功/部分失败时是否保持真实状态？
- [ ] 失败是否能回到明确责任阶段，而不是“重新问一次模型”？
- [ ] 生成产物是否有 manifest / receipt / provenance？

## G. Debug / Reliability

- [ ] 是否建立 timeline？
- [ ] Observed / Inferred / Confirmed 是否分开？
- [ ] 是否维护同一 Hypothesis Registry？
- [ ] 每个关键 hypothesis 是否有 discriminating experiment？
- [ ] 是否避免从单条日志直接跳 root cause？
- [ ] crash 是否绑定 exact symbol/ELF/firmware？
- [ ] memory corruption 是否考虑 secondary symptom？
- [ ] performance 是否有 baseline、measurement method、before/after？
- [ ] long-run/stress 是否有时间、负载、环境和指标身份？

## H. Linux / BSP

- [ ] boot chain 是否能定位 last confirmed stage？
- [ ] DT 与实际 board/resource identity 是否一致？
- [ ] clock/reset/pinctrl/regulator/IRQ/DMA/cache 是否按平台 contract 分析？
- [ ] kernel config/defconfig 是否纳入关键行为判断？
- [ ] storage 问题是否区分 controller/MTD/ECC/UBI/FS/app 层？
- [ ] power/suspend/resume/wakeup 是否有 target evidence？
- [ ] BSP porting 是否有 source/config/device 差异清单？

## I. MCU / RTOS

- [ ] reset/vector/startup/init 顺序是否明确？
- [ ] linker/MAP/ELF/ROM/RAM 是否量化，而不是只看编译成功？
- [ ] ISR/task/thread context 是否明确？
- [ ] lock/queue/semaphore/priority inversion/deadlock 是否分析？
- [ ] worst-case latency/jitter 是否与实时要求对应？
- [ ] watchdog/reset reason/recovery 是否可追踪？
- [ ] low-power/wakeup 是否有时序与状态证据？
- [ ] bootloader/OTA/version/rollback 是否与 application contract 对齐？

## J. Driver / Component

- [ ] bus/protocol/electrical assumption 是否有权威 Source？
- [ ] probe/init/deinit/suspend/resume 生命周期是否完整？
- [ ] IRQ/DMA/thread context 与 lifetime 是否明确？
- [ ] timeout/retry/recovery/error path 是否覆盖？
- [ ] API/ABI/versioning 是否稳定？
- [ ] 器件替代是否有 compatibility matrix？
- [ ] normal + failure + power path 是否都验证？
- [ ] calibration/production test 是否纳入量产可用性？

## K. Evidence

- [ ] 每个实质 claim 是否能指向直接 Evidence？
- [ ] Evidence 是否绑定 exact object identity？
- [ ] Synthetic evidence 是否没有冒充 real product evidence？
- [ ] 文档描述是否没有高于 Evidence 强度？
- [ ] Evidence 是否可重放/可审计？
- [ ] frozen bundle 是否防止事后漂移？
- [ ] 同一事实是否避免复制成多个“权威版本”？

## L. Verification

- [ ] Acceptance 是否逐条映射 required verification layer？
- [ ] Build/static/SIL/device/HIL/release 层是否没有混淆？
- [ ] required device evidence 缺失时是否不会 PASS？
- [ ] regression scope 是否与 change impact 一致？
- [ ] Verification identity 是否独立于 Engineering output？
- [ ] PASS_WITH_RISK 是否有明确风险 owner/expiry？
- [ ] 不可验证项是否显式保留？

## M. Independent Review

- [ ] Review 是否独立检查 correctness/safety/risk，而非重复 Engineering？
- [ ] Review unavailable 时是否只使用明确 stage exception？
- [ ] exception 是否没有被写成 Review PASS？
- [ ] findings 是否有 severity/owner/closure evidence？
- [ ] open risk 是否有 acceptor/expiry/mitigation？
- [ ] release readiness 是否仍不等于 A7 release decision？

## N. Knowledge

- [ ] Source of Truth 是否仍留在原 Source？
- [ ] Knowledge registry 是否记录 authority/freshness/ACL？
- [ ] 多 Source 冲突时是否有裁决规则？
- [ ] stale knowledge 是否能检测？
- [ ] ACL negative case 是否测试？
- [ ] Harvest 是否只沉淀被证据支持的增量？
- [ ] 无增量时是否允许 NO_KNOWLEDGE_DELTA？
- [ ] 后续任务是否有真实 reuse evidence？

## O. Security / Action / Audit

- [ ] 默认 action 是否最小化？
- [ ] A5-A7 是否需要显式批准？
- [ ] credential / secret / production access 是否受控？
- [ ] risky change 是否有 rollback？
- [ ] 谁做了什么动作是否可审计？
- [ ] Runtime 更换是否不会偷偷扩大权限？
- [ ] exception 是否有 owner、原因、期限和重新审查条件？

## P. Product Readiness

- [ ] Feature / Debug / Review-Release 三轨是否分开评价？
- [ ] real evidence 是否来自目标产品？
- [ ] 一个 track eligible 是否没有推出整体 PASS？
- [ ] target device/HIL 要求是否满足？
- [ ] release candidate provenance 是否完整？
- [ ] install/boot/resulting-version/rollback 是否在 scope 内有证据？
- [ ] Product readiness 是否没有被文档完整度替代？

## Q. Productionization

- [ ] server-side repository governance 是否达到生产化要求？
- [ ] 权限模型是否经过多人/真实组织环境验证？
- [ ] runtime/provider failure 是否有降级与恢复？
- [ ] audit / observability / metrics 是否持续可用？
- [ ] Skill/Contract/schema 变更是否有兼容和回退？
- [ ] 是否有 incident response 与 kill switch/stop condition？
- [ ] 关键 owner 不可用时是否有治理替代路径？
- [ ] 是否完成真实用户/团队 adoption evidence？
- [ ] 是否有成本、时延、成功率、incorrect-pass 等运行指标？
- [ ] 是否至少有 1 个持久化 bounded `EVALUATED` Skill summary（E09）？
- [ ] 是否至少有 1 个 real Run 的 Runtime-owned Skill attribution（E10）？

## R. 最终评审结论

评审报告至少明确：

- [ ] 哪些项是 ACCEPTED_BASELINE；
- [ ] 哪些项是 EVIDENCE_PENDING；
- [ ] 哪些项需要 REVISE；
- [ ] 哪些缺口当前 BLOCK 下一阶段；
- [ ] Owner / tracking / exit criteria；
- [ ] 是否允许继续 Pilot；
- [ ] 是否允许扩大 automation/action；
- [ ] 是否允许进入 Productionization；
- [ ] 是否出现需要新 Skill / 新 Capability / Expert 晋级的真实证据；
- [ ] 是否存在需要退役的旧资产。

**禁止结论**：仅因为“文档齐、CI 绿、Skill 多、模型表现好”就写“闭环成熟落地”。正式结论必须绑定当前范围、对象、证据和治理阶段。
