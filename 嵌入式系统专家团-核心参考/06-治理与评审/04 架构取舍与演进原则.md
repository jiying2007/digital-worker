# 架构取舍与演进原则

## 1. 为什么不是一个“万能专家”

### 备选方案

A. 单一责任单元从接单一直负责到发布。  
B. Domain Expert 保持稳定责任边界，Embedded 内部用 Capability → Skill 组织专业能力，Assurance 独立。  
C. 按 Wi-Fi / Flash / Audio / Motor / Camera 等专项不断新增 Expert。

### 当前选择：B

原因：

- A 容易形成自我确认：同一责任单元既判断、又实施、又验证、又放行；
- C 会让 Expert 数量随产品和器件快速膨胀；
- B 把长期稳定责任与专项方法分开：Structure / Hardware / Embedded System 三个 Domain Expert 稳定，Embedded 的变化优先进入 Capability / Skill；
- Verification / Independent Review 保持在 Assurance，不因 Runtime topology 改变。

重新讨论新增 Expert 的条件不是“专项很重要”，而是多个真实任务证明其长期拥有独立责任边界、独立任务入口、生命周期、核心交付物、知识域和持续稳定工作量，并形成清晰跨 Expert I/O Contract。

## 2. 为什么 Expert 不绑定 Agent topology

Expert 是责任归属，不是运行时实例。一个 Expert 可以由一个人、多个 Agent/Session、脚本、CI/HIL 或这些执行单元的组合承载；一个 Agent 也可以在受控路由下执行多个 Capability 的具体任务。

因此：

```text
Expert count != Worker count != Session count != Skill count
```

如果组织架构直接按当前模型/Agent 数量设计，Runtime 一升级就会造成责任架构漂移。

## 3. 为什么不绑定一个 Coding Runtime

### 备选方案

A. 全团队只允许一种 Runtime。  
B. 工程师自由选择，输出格式也自由。  
C. 多 Runtime + 稳定 Engineering Contract。

### 当前选择：C

A 治理简单但存在能力和供应锁定；B 灵活但 Evidence、权限和恢复碎片化。C 增加少量适配成本，但可以真实比较 Runtime，同时不破坏 Task、Gate、Evidence、Verification 和 release authority。

## 4. 为什么不把全部资料搬进一个知识库

集中迁移会带来：

- Git / CI / HIL 的版本事实变成副本；
- NAS / 供应商资料 ACL 难以保持；
- 删除、撤权和 freshness 传播困难；
- Provider 锁定；
- “搜索命中”被误当成“原文权威”。

因此采用 federated / hybrid：Source 保留原权威，Knowledge Provider 负责 registry、索引、引用和上下文访问。核心原则保持 `Source of Truth stays at source`。

## 5. 为什么不现在建设 Context Broker / Knowledge Graph

它们可能有价值，但是否引入必须由真实成本和失败模式证明，例如：

- 手工/脚本组装 Context 已成为主要瓶颈；
- 跨 Source 关系复杂到需要稳定图模型；
- Context rebuild、duplicate analysis、late mismatch 已重复发生；
- 新基础设施维护成本明确低于减少的重复劳动和错误成本。

没有这些 evidence 时不把未来能力提前做成当前架构前置条件。

## 6. 为什么 Verification 与 Review 分开

Verification 是事实问题：直接 Evidence 实际证明到哪一层。  
Review 是独立风险判断：这些事实、open risk、rollback 和 provenance 是否足以允许下一步。

合并后，项目压力很容易把“尚未验证”改写成“可以接受”。分开后可以进行 Risk Acceptance，但不会改写 Verification 事实。

当前 iterative Pilot 若 Independent Review unavailable，可以显式采用 static checks + Hosted CI + traceable Verification evidence 作为 completion substitute；这不产生 Independent Review PASS，也不能替代 Device/HIL/Release/A7 证据。

## 7. 为什么当前 Skill 默认只拥有有限动作权限

Skill 沉淀的是可复用方法。如果 Skill 自动继承设备写、生产操作或发布权限，会把“方法复用”变成“权限复用”。因此实际动作统一受 Engineering Runtime + Action Policy + human gate 约束，Skill owner 不等于 action approver。

## 8. 为什么先 Engineering Closed Loop 再扩大知识与自动化

如果真实 Task → Engineering → Verification 都没有稳定闭环，就过早讨论“知识自进化”或“自动形成 Skill”，会把错误经验快速复制。

演进顺序保持：

```text
先证明真实工程闭环
→ 再证明知识能正确复用
→ 再用重复 Evidence 驱动 Capability / Skill 改进
→ 最后扩大受控自动化
```

## 9. 什么时候应该修改 Schema

先在真实 Run 中用轻量 artifact 记录字段；满足以下条件再正式 Schema 化：

- 同一信息在多个任务重复出现；
- 字段含义稳定；
- 有自动校验或跨系统交换需求；
- 不 Schema 化已经造成真实错误或明显重复劳动。

不要因为“以后可能用到”就新增 Schema。

## 10. 演进触发器

|观察|可能动作|
|---|---|
|同类诊断方法反复出现|新增/拆分 Skill|
|一个 Embedded 专业子域责任持续扩大|先评估 Capability 拆分，再按晋级条件评估 Expert|
|多个 Domain 反复需要同一协调模式|增强 Orchestration/Coordination，不新增伪 Expert|
|多个领域都重复组装相同 Context|评估 Context Package/Broker|
|Artifact identity 经常断链|正式 Artifact Lineage Contract|
|多仓 Integration Reconciliation 成为稳定独立工作量|评估新的 Capability/Skill|
|Knowledge ACL/freshness 成为主要故障|加强 Knowledge Provider adapter|
|Runtime 切换成本仍很高|完善 Runtime Receipt/Adapter|
|设备读写自动化样本稳定且风险可控|评估扩大受控 Action level|

## 11. 文档也按同一原则演进

活动文档只保留当前有效结论。历史由 Git / PR / Issue 保存；compatibility mapping 只在专用机器路径存在，不复制到核心参考。失效的 review pack、过渡身份、重复 Golden 数据和旧术语不长期留在主阅读路径。
