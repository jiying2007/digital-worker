# 架构取舍与演进原则

## 1. 为什么不是一个“万能专家”

### 备选方案

A. 单一角色负责从接单到发布。  
B. 1+7 稳定职责，专项能力做 Skill。  
C. 按 Wi-Fi/Flash/Audio/Motor/Camera 等不断新增角色。

### 当前选择：B

原因：

- A 容易形成自我确认：同一角色既判断、又实施、又验证、又放行；
- C 组织会随产品和器件快速膨胀；
- B 把长期稳定职责和专项方法分开，真实需求出现后仍可扩展。

重新讨论的条件：多个真实任务证明某专项长期承担独立判断权和持续工作量。

## 2. 为什么不绑定一个 Coding Runtime

### 备选方案

A. 全团队只允许一种 Runtime。  
B. 工程师自由选择，输出格式也自由。  
C. 多 Runtime + 稳定 Engineering Contract。

### 当前选择：C

A 治理简单但存在能力和供应锁定；B 灵活但证据、权限和恢复碎片化。C 增加少量适配成本，但能真实比较工具又不破坏工程规则。

## 3. 为什么不把全部资料搬进一个知识库

集中迁移看起来最简单，但会带来：

- Git/CI/HIL 的版本事实变成副本；
- NAS/供应商资料 ACL 难以保持；
- 删除/撤权和 freshness 传播困难；
- Provider 锁定；
- “搜索命中”被误当成“原文权威”。

因此当前采用 federated/hybrid：Source 保留原权威，Knowledge Hub/Provider 负责 registry、索引、引用和上下文访问。

## 4. 为什么不现在建设 Context Broker/Knowledge Graph

它们可能有价值，但当前真实任务数量还不足以证明：

- 手工/脚本组装 Context 已成为主要瓶颈；
- 跨 Source 关系复杂到需要图模型；
- 维护规则的成本低于减少的重复劳动。

当前先记录 context rebuild、duplicate analysis、late mismatch；重复出现再立项。

## 5. 为什么 Verification 与 Review 分开

Verification 是事实问题：证据证明了哪一层。  
Review 是风险判断：这些事实是否足以交付/放行。

如果合并，项目压力很容易把“尚未验证”变成“可以接受”；分开后 Risk Acceptance 可以发生，但不会改写验证事实。

## 6. 为什么 P0 Skill 默认只到 A2

Skill 主要沉淀分析方法。如果 Skill 本身直接拥有修改、设备和发布权限，会把“方法复用”变成“权限复用”，难以按任务最小授权。

工程动作统一通过 Engineering Runtime + Action Policy，更容易记录 repo/base、命令、artifact 和 approval。

## 7. 为什么先 E2 再 E3/E4

如果真实 Task→Execution→Verification 都没有稳定闭环，就过早讨论“知识自进化”“自动形成 Skill”，容易把错误经验快速扩散。

因此顺序是：

```text
先证明工程闭环
 → 再证明知识能正确复用
 → 再用重复 evidence 驱动能力改进
 → 最后扩大受控自动化
```

## 8. 什么时候应该修改 Schema

先在真实 Run 中用轻量 artifact 记录字段；满足以下条件再正式 Schema 化：

- 同一信息在多个任务重复出现；
- 字段含义稳定；
- 有自动校验/跨系统交换需求；
- 不 Schema 化已经造成真实错误或明显重复劳动。

不要因为“以后可能用到”就新增 Schema。

## 9. 演进触发器

|观察|可能动作|
|---|---|
|同类诊断方法反复出现|新增/拆分 Skill|
|多个领域都重复组装相同 Context|评估 Context Package/Broker|
|Artifact identity 经常断链|正式 Artifact Lineage Contract|
|多仓 Integration Reconciliation 成为独立工作量|评估 integration Skill/角色|
|Knowledge ACL/freshness 成为主要故障|加强 Knowledge Hub/Provider adapter|
|Runtime 切换成本仍很高|完善 Runtime Receipt/Adapter|
|设备读写自动化样本稳定且风险可控|评估扩大 A5/A6|

## 10. 文档也按同一原则演进

活动文档只保留当前有效结论。历史由 Git 保存；失效的 review pack、兼容段落和过渡术语不长期留在主阅读路径。这样可以避免后来的人把历史建议误当成当前规则。
