# 评审说明与决策清单

## 1. 评审目的

评审不是判断某个模型或办公产品是否“好用”，而是判断嵌入式研发的责任边界、工程运行、验证、恢复、权限和审计是否清楚，哪些已经是团队基线，哪些仍必须用真实工程证据证明。

## 2. 当前评审范围

持续评估：Edge Foundation 的 3 个 Domain Expert、Edge Coordination Role、Embedded System Expert 的 5 个 Capability、14 类 task、canonical routing、Gate K/M/0/T/E/V/R/C、Engineering / Verification / Review 分离、A0-A7、Provider-neutral 工程交接、Source of Truth stays at source、真实 Pilot、Product readiness 与 Productionization 门槛。

Edge Foundation target runtime 已是 canonical execution authority；旧组织执行面已经退役。Product readiness 是独立证据 Gate，不控制 routing authority。当前 Feature 已有 1 条 eligible real receipt，Debug 与 Review/Release 仍待真实材料，因此产品成熟度保持 BLOCKED。

本轮不因为文档完整而提前冻结唯一知识平台、唯一 Coding Runtime、全量 Context Broker、A5-A7 自动扩权或 Production Ready。

## 5. 评审时优先追问

### 架构
- 某个 Runtime 下线后，Task/Package/Evidence 是否还能继续？
- 多个 Knowledge Source 冲突时谁是 authority？
- 多仓一部分成功、一部分失败时系统级状态是否真实？
- 某项能力只是 Capability/Skill，还是已经满足 Expert 晋级条件？

### 流程
- 简单任务是否被迫走过多 Gate？
- `review` 是否可能隐式执行工程修改？
- Debug 是否维护同一 Hypothesis Registry？
- Acceptance 是否逐条映射 Evidence？
- 失败后是否知道回到哪个责任阶段？

### 责任与可信保障
- Edge Coordination 是否越过 Domain Expert 给专业结论？
- Engineering 是否试图自签 Verification？
- Review unavailable substitute 是否被误写成 Review PASS？
- Risk Acceptance 与 A6/A7 的批准人是否明确？

## 6. 评审输出

正式评审至少形成 Decision Register 状态变化；`REVISE / EVIDENCE_PENDING` 的 Owner、Tracking 与退出条件；是否继续真实 Pilot；是否需要修改 ADR/Contract/Schema；是否出现新的 Skill/Capability/Expert 晋级候选。没有 Evidence 的能力不填 PASS；没有完成验证的工程结果不写“已闭环”；Product readiness BLOCKED 也不能被误解释为 canonical runtime 不成立。
