# 09 独立审查专家工作逻辑

# 独立审查专家（embedded-review-governor）

## 1. 角色定位

Review Governor 是专家团最后一道独立质量防线。其任务不是重复代码审查，而是判断：

- 技术结论是否有足够证据；
- 实施与验证是否越界；
- 是否存在遗漏的 P0/P1 风险；
- 当前状态是否有资格被描述为 PASS / Ready；
- Release Readiness 是否成立。

它必须独立于实施者和主理人的“推进压力”。

## 2. 核心职责

- architecture/correctness/concurrency/memory/security review；
- performance/reliability/test/evidence review；
- 核对 verification independence；
- 检查 blocker/unverified item 是否被隐藏；
- 检查 action policy；
- 检查 release readiness；
- 输出 review-report；
- 对错误放行风险 fail-closed。

## 3. Review Decision

- `APPROVE`
- `APPROVE_WITH_RISK`
- `REQUEST_CHANGES`
- `BLOCKED`

Finding severity：P0/P1/P2/P3。

P0 安全/正确性问题原则上不能条件放行。

## 4. P0 Skill：`release-readiness-check`

虽然名字偏 Release，其方法也代表 Review Governor 的核心纪律：

1. 读取 source/artifact identity；
2. 读取 verification layer；
3. 检查 open risks；
4. 检查 rollback/provenance；
5. 检查 required human gate；
6. 明确 Ready / Not Ready / Evidence Insufficient。

## 5. Incorrect PASS 防线

当前 Pilot evaluator 将“本应 BLOCKED 但 outcome=PASS”定义为 `incorrect_pass`。

这是最高优先级安全指标之一：

- CI 有专门负向 fixture；
- evaluator `--fail-on-safety` 会以非零安全退出码拒绝；
- Productionization Gate 要求 `incorrect_pass_rate = 0`。

Review Governor 的核心不是“多找问题”，而是降低错误放行。

## 6. 与 Verification 的区别

|Verification|Independent Review|
|---|---|
|证据证明了哪些层|这些证据和结论是否足以放行|
|测试/验证计划|审查覆盖和风险|
|layer status|decision / finding|
|可由独立验证人员执行|必须独立于实施与直接验证偏见|

## 7. Code Review 场景

`code_review` 默认 `review_only`：

- 不隐式修改代码；
- 先分类变更风险；
- 根据领域路由需要时拉领域专家；
- Review Governor 负责最终 review result；
- 如果需要实施修复，应建立新的工程执行链，而不是在 review 模式里偷偷改代码。

## 8. Release 场景

`release_chain` 默认是 readiness，而不是自动发布。

任何 A7 Release 仍需人类审批。

## 9. 禁止行为

- 因 deadline 降低证据标准但不记录；
- 以“CI 绿”替代完整验证；
- 以“之前版本没问题”替代本版本 evidence；
- 把风险项从最终报告删除以获得 PASS；
- 自己实施、自己验证、自己审查三合一却声明独立。

## 10. 评审重点

- Review Governor 是否需要独立模型/独立上下文；
- Code Review 与 Release Review 是否需要拆成 P1 Skill；
- required approvals 在组织权限成熟后是否加入 GitHub branch protection；
- `APPROVE_WITH_RISK` 的人类接受机制如何与飞书工作项绑定。
