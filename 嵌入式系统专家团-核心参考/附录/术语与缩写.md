# 术语与缩写

本文统一核心参考中的常用术语。术语用于减少沟通歧义，不要求日常交流刻意使用英文。

|术语|本文含义|
|---|---|
|Work Item|业务或工程工作项，负责承载请求、Owner、状态、审批和外部协作关系。|
|Run|一次受控的工程运行实例。同一 Work Item 可以因重跑、修订或 supersede 产生多个 Run。|
|Task Brief|任务入口说明，记录目标、范围、验收、仓库、约束和允许动作。|
|System Context|某个 Run 共用的平台、板卡、源码、固件、工具链、设备和关键材料上下文。|
|Gate|进入下一阶段前必须回答的问题和退出条件。Gate 不是会议本身。|
|Mode|根据任务类型选择的流程路径，如 diagnostic、bringup、review_only。|
|Expert Role|稳定专业职责，如 Linux/BSP、MCU/RTOS、验证。它是责任边界，不等同于某个具体人或模型。|
|Skill|可重复使用的工程方法，例如 Linker Map 分析或 Device Tree Review。|
|Engineering Package|把技术判断转成可直接实施的工程任务包。|
|Runtime|执行分析、修改、构建或受控测试的具体工程环境，如 CLI/IDE/内部工具。|
|Session Bootstrap|一次工程会话启动时装配项目、模式、Contract、Skill、知识访问和权限边界。|
|Receipt|对实际发生动作的记录。Receipt 说明“做了什么”，不自动等于验证通过。|
|Evidence|可追溯的工程证据，如 source SHA、build log、artifact hash、设备日志、HIL run。|
|Identity|能够唯一定位对象的身份，如完整 Git SHA、artifact SHA256、board revision、device ID。|
|Acceptance Criterion|任务完成必须满足的可判定条件。|
|Acceptance → Evidence|把每条验收项映射到验证层、对象身份、证据和状态。|
|Verification|判断现有证据真正证明到了哪一层。|
|Independent Review|在 Verification 基础上判断风险、例外和证据是否足以交付或放行。|
|HIL|Hardware-in-the-loop，硬件在环验证。|
|SIL|Software-in-the-loop，软件在环或受控仿真验证。|
|SSOT|Single Source of Truth，某类事实的唯一权威来源。本文更常直接写“权威来源”。|
|Provider|提供入口、知识、执行或其他能力的具体产品/系统。|
|Knowledge Source|原始事实所在位置，如 Git、NAS、CI/HIL、协作文档。|
|Knowledge Provider|负责知识登记、检索、引用、ACL/freshness 等能力的系统。|
|Knowledge Harvest|任务结束时判断是否形成可复用知识，并提交候选或明确无新增知识。|
|RCA|Root Cause Analysis，根因分析。|
|Hypothesis Registry|Debug 共用的假设清单，记录支持/反对证据、实验和状态。|
|RACI|Responsible / Accountable / Consulted / Informed 的职责矩阵。|
|A0-A7|按动作风险划分的权限等级，从读取到生产发布。|
|P0/P1|本文中的能力优先级或 Finding 严重度，具体语境以章节说明为准。|
|Productionization|从试运行进入可规模化、受治理的生产使用阶段。|

## 使用约定

- 首次出现不常见缩写时优先写中文含义；
- 能直接说“验证报告”“完整源码 SHA”的，不为了显得专业额外堆叠英文；
- 产品名只在描述真实实现关系时出现，不把品牌名写成架构概念；
- 机器字段名、Schema 字段和正式状态值保持原拼写，避免人与机器之间再次翻译漂移。
