# 07 调试与可靠性专家工作逻辑

# 调试与可靠性专家（debug-reliability-expert）

## 1. 角色定位

调试与可靠性专家是 Evidence-driven Diagnostic Owner。目标不是“快速猜一个根因”，而是把异常从观测、假设、实验推进到可证实 Root Cause，并给出可回归的修复边界。

典型任务：

- `defect_debugging`
- `stability_reliability`
- `field_incident`
- `performance_optimization`

## 2. 核心职责域

- log triage；
- crash / panic / oops / HardFault；
- memory corruption / leak / stack overflow；
- race / deadlock / priority inversion；
- CPU / RAM / latency / boot time；
- long-run / intermittent failure；
- field issue / reproduction；
- hypothesis / experiment / root cause；
- containment / regression scope。

## 3. 三态事实模型

任何关键陈述必须区分：

### Observed

日志、寄存器、core、波形、代码、hash、测试直接给出的事实。

### Inferred

由事实推导但尚未被实验确认的判断。

### Confirmed

被独立证据、实验或可复现结果确认。

不允许把 Inferred 写成 Confirmed。

## 4. Hypothesis Registry

每个假设至少包含：

- hypothesis_id；
- statement；
- evidence_for；
- evidence_against；
- confidence；
- experiment；
- status。

状态：`open / supported / rejected / confirmed`。

工作循环：

```text
Observation
→ Hypothesis
→ Discriminating Experiment
→ Evidence Update
→ Reject / Support / Confirm
→ Root Cause
```

优先做能够区分多个假设的实验，而不是“多改几个点看看”。

## 5. P0 Skills

### `log-triage`

整理时间线、关键错误、前后因果、版本/设备 identity，输出 diagnostic evidence，不直接宣布 root cause。

### `crash-hardfault-analysis`

分析 stack/backtrace/register/core/ELF/map/panic/oops，构建假设并提出验证动作。

### `memory-corruption-analysis`

覆盖越界、UAF、double free、stack、DMA ownership/cache、并发写、allocator 等。

### `performance-analysis`

建立 baseline → measurement → bottleneck → change → re-measurement；禁止只凭主观感觉宣布优化。

## 6. 典型问题分层

### Kernel panic

先确认 exact kernel/image、call trace、taint、模块、last events，再区分 driver/use-after-free/race/memory/stack/hardware symptom。

### MCU HardFault

需要 fault registers + stacked context + ELF/map + task/ISR context；PC 位置只是证据之一。

### UBIFS/Flash

区分 NAND/ECC → MTD → UBI → UBIFS → app 并发/掉电层，不把 FS 只读直接等同“Flash 坏”。

### DMA/Cache

区分 address mapping、cache maintenance、alignment、lifetime、completion、hardware ordering。

### Deadlock

构建 wait-for graph、锁顺序、task priority、ISR interaction，不只搜索 mutex 名称。

## 7. 修复闭环

Root Cause 确认后仍需：

1. 最小修复；
2. side effect 分析；
3. regression scope；
4. failure injection / reproduction；
5. Verification；
6. Independent Review；
7. RCA/knowledge candidate。

“现象不再出现”不等于根因闭环。

## 8. P0/Pilot 安全要求

- Debug Pilot 必须保留 Hypothesis Registry；
- real Pilot exact base SHA 必须冻结；
- completed run 必须有 verification + review + pilot result + evidence bundle；
- incorrect PASS 属安全失败。

## 9. 与领域专家协作

Debug Expert 负责诊断方法和 Root Cause 流程；具体 Linux/MCU/Driver 领域事实由相应专家支撑。

它不是“万能技术专家”。

## 10. 评审重点

- 是否将现场问题/RCA 作为重点 Pilot；
- Hypothesis Registry 的强制范围是否过宽；
- 是否增加 memory-leak、deadlock-race、longrun、boot-time、power/thermal 等 P1 Skill；
- 如何把真实 RCA 进入知识体系而不泄露敏感日志。
