# 案例：器件替代兼容性走查

> 流程示例，可用于 Wi-Fi、Flash、Power、Sensor 等国产替代或第二供应商导入，**不代表任何具体料号已经验证，也不计入 real Pilot evidence**。  
> 通用规则见 [任务类型运行矩阵](../03-流程与运行/05%20任务类型运行矩阵.md)、[任务生命周期与 Gate](../03-流程与运行/01%20任务生命周期与Gate.md)、[验证/评审/发布](../03-流程与运行/04%20验证评审发布与异常恢复.md)。专业方法见 [驱动与组件](../04-专业能力/04%20驱动与组件能力域指南.md) 和 [嵌入式架构](../04-专业能力/01%20嵌入式架构能力域指南.md)。

## 1. Task

现有器件因成本、供应或国产化要求需要替换。新器件宣称 pin/API 兼容，目标是判断它是否真的能在指定 product / board / SDK 上工程使用，而不是证明“代码能编译”。

## 2. Context / Material

冻结产品、board revision、原/新器件 revision、schematic、关键外围、SDK/firmware、现有 driver/component、生产校准/测试流程和 Acceptance。

采购/供应商信息可作为输入，但不能替代工程兼容性 Evidence。

## 3. Routing

任务由 **Embedded System Expert** 负责，`embedded.driver-component` 主责设备行为、driver/component 和 Compatibility Matrix；`embedded.architecture` 判断系统接口、资源、启动或 OTA 影响；按实际平台组合 `embedded.linux-bsp` 或 `embedded.mcu-rtos`。若存在电压、电源时序、pin、电气接口或 signal-integrity 不确定性，再凭直接 Evidence 升级到 **Hardware Expert**。Verification 属于 Assurance。

## 4. Analysis / Compatibility Matrix

至少覆盖：

|维度|核对内容|
|---|---|
|电气/板级|电压、电流、pin、reset、上电时序、外围器件|
|总线/协议|I2C/SPI/UART/SDIO/USB 语义和时序|
|初始化|寄存器、firmware、NVM/calibration|
|能力|缺失/新增 feature、限制条件|
|性能|吞吐、时延、功耗、温升|
|异常|timeout、掉线、坏块、brownout、reset 行为|
|软件接口|Linux/MCU API、DT、配置、版本兼容|
|生产|烧录、校准、ATE/老化、序列号/追溯|
|回归|直接功能和间接系统影响|

## 5. Evidence

按 `Datasheet/board compatibility → low-level communication → init/basic function → error/recovery → performance/power → system integration → stress/long-run → production calibration/test` 分阶段建立 Evidence。

早期关键不兼容应停止扩大测试。最容易漏掉的是掉电/重启、timeout/retry、弱网/掉线、边界温度/电压、Flash bad block/ECC、Power brownout、NVM/calibration 和生产流程差异。

## 6. Decision / Engineering

Technical Decision 明确：哪些差异由 driver/adapter 隔离，哪些需要系统接口变化，哪些是产品限制，哪些仍是未验证风险。公共组件抽象只覆盖真实复用范围，不为未来假想器件增加复杂层。

工程修改绑定 exact base，并保留新旧器件切换和 rollback/containment 方案。

## 7. Verification

Verification Plan 基于当前产品定义 required layer，覆盖正向功能、异常/恢复、性能/功耗、系统回归、长稳和 required 生产校准/测试。每个 Evidence 绑定 product/board/SDK/device revision。

实验室 basic function 通过不能自动推导 Engineering 或 Production readiness。

## 8. Review

当前可使用 `LAB_COMPATIBLE / ENGINEERING_COMPATIBLE / PRODUCTION_READY_CANDIDATE` 作为**人类评审表达**，但它们不是机器状态；若未来要 Schema 化，必须先由真实 Pilot 证明稳定语义。

最终量产导入仍由正式组织流程批准，Independent Review 重点核 residual risk、版本/料号适用边界、生产追溯和 rollback；A7 release authority 不属于 Review。

## 9. Knowledge Harvest

Compatibility Matrix 是高价值组织资产，但必须带 product / board / SDK / device revision 和 Evidence。知识 ownership 落 target Capability；不要把“某项目可替代”传播成“所有平台通用替代”。
