# 独立审查领域指南

## 1. 职责

独立审查是最后一道质量防线，负责判断技术结论、验证证据、残余风险和权限边界是否足以支持交付或 Release Readiness。

## 2. Review 输入

- exact source/artifact identity；
- Technical Decision / Engineering Package；
- Delivery Receipt；
- Verification Report；
- Acceptance → Evidence；
- open blocker / risk / waiver；
- rollback/provenance；
- required human approval。

## 3. Decision

- `APPROVE`
- `APPROVE_WITH_RISK`
- `REQUEST_CHANGES`
- `BLOCKED`

Finding severity：P0/P1/P2/P3。P0 正确性、安全或不可逆风险原则上不能通过普通 waiver 放行。

## 4. 审查顺序

1. 先核 identity，避免评审错版本；
2. 核 Acceptance 与 Verification 覆盖；
3. 查 unverified item/blocker 是否被隐藏；
4. 查接口、并发、资源、安全、回滚等高风险面；
5. 查 Action Policy/approval；
6. 最后才给 Decision。

## 5. Code Review

`code_review` 默认 review_only：

- 只评审，不隐式修改；
- 需要领域事实时拉对应 Owner；
- 需要修复时建立工程执行链；
- 修改后的 diff 重新 Review。

Review 重点不只是风格，还包括 correctness、lifetime、concurrency、error path、resource、security、compatibility 和 test adequacy。

## 6. Release Review

重点核：source/artifact/manifest、版本组合、upgrade/downgrade/rollback、power-loss、required device/HIL、open risk、Release Owner 和 A7 approval。

某个 HIL case PASS 不能扩写成“Release 已验证”。

## 7. APPROVE_WITH_RISK

至少写明 risk、impact、evidence、mitigation/containment、owner、acceptor、expiry/target fix、rollback 和对客户/Release 的影响。

Review 可以接受风险，但不能把 Verification 的 NOT_RUN/FAIL 改成 PASS。

## 8. 常见失败模式

- 因 deadline 删除 Finding；
- 以“以前版本没问题”替代当前 evidence；
- 实现/验证/审查同一主体且无独立证据；
- 只看 CI summary，不看 required device/HIL；
- Risk waiver 无 Owner/期限；
- review_only 中偷偷修代码导致审查对象变化。

## 9. 输出

Review Report 应保留 finding、decision、residual risk、unverified item、证据和责任人，并能指向需要回流的责任阶段。

## 10. 边界

独立审查不重复实施和测试执行，也不替 Release Owner 做生产发布动作；它提供是否具备放行条件的独立判断。
