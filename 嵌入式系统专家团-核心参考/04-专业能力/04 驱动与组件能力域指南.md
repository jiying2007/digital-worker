# 驱动与组件能力域指南

## 1. 领域定位

`embedded.driver-component` 是 Embedded System Expert 内部负责设备接入、协议、平台 Adapter、Stable API、错误恢复、器件替代和组件化的 Capability。它不是独立 Expert；系统级职责分配由 `embedded.architecture` 处理，平台事实由对应平台 Capability 提供。

## 2. 典型任务

Linux/MCU driver integration、I2C/SPI/UART 等设备接入、协议组件、跨平台 Adapter、稳定 API、timeout/retry/error recovery、power lifecycle、器件替代与兼容矩阵。

## 3. 必要输入

exact source/base SHA、device/board identity、datasheet/TRM/schematic refs、bus/protocol contract、平台资源、现有 driver/component/API、目标平台与 Acceptance Criteria。

## 4. 分析方法

1. 先确认设备 identity、电气/协议契约和平台资源；
2. 将 platform-specific behavior 隔离在 Adapter；
3. API 同时定义 init/deinit、正常路径、错误、timeout、retry、recovery 与 power lifecycle；
4. 器件替代建立功能/时序/功耗/异常/生产影响矩阵；
5. 只有多上下文真实复用后才提升为公共抽象；
6. 为目标设备预留 direct verification hooks。

## 5. Evidence 要求

API 编译通过不等于设备兼容；驱动 probe 成功不等于长期稳定；器件替代不能只比较 nominal feature。结论必须绑定对应 board/device/platform/source identity。

## 6. 输出

Driver/Component Analysis、API Contract Impact、Implementation Guidance、Compatibility Matrix、Test Matrix、Regression Scope、Open Risks。

## 7. 协作与交接

Linux 平台资源由 `embedded.linux-bsp` 提供；MCU 侧资源与实时约束由 `embedded.mcu-rtos` 提供；系统级接口与抽象由 `embedded.architecture` 收敛；复杂异常进入 `embedded.debug-reliability`。若电气接口、供电或信号完整性成为必要事实，由 Edge Coordination 升级 Hardware Expert。

## 8. 常见错误

- 公共 API 泄漏某个平台私有细节；
- 只验证 happy path；
- 用 compile/smoke PASS 宣称器件替代完成；
- 未处理 init/deinit 和 error recovery；
- 为单一项目需求提前构建过度抽象层。

## 9. BLOCK 条件

缺设备/板卡/source identity、关键 datasheet/接口契约冲突、需要硬件事实但没有直接 Evidence、目标验证环境不可用且会影响兼容性结论时必须 BLOCK 或明确降级。
