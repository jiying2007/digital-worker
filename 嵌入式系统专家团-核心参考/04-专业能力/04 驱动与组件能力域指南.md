# 驱动与组件能力域指南

`embedded.driver-component` 是 Embedded System Expert 内负责设备接入、驱动生命周期、协议适配、稳定接口、器件替代和跨平台组件化的 Capability。目标不是“把设备跑起来”，而是形成可维护、可测试、可诊断、可移植的产品能力。

## 1. 典型任务

设备 Bring-up、Linux/MCU Driver 集成、Platform Adapter、Stable API、器件替代/国产化/第二供应商导入、错误恢复、Power/Suspend/Resume、跨平台组件化和兼容矩阵维护。

## 2. 必要输入与 Context

- hardware / board / device identity；
- datasheet / TRM / schematic；
- bus / protocol / timing；
- Linux/MCU 平台资源；
- current driver/component/API；
- error/timeout/power 行为；
- firmware/NVM/calibration；
- 目标平台、真实复用范围和生产约束。

## 3. 分析主链

```text
Hardware / Bus
→ Low-level Driver
→ Platform Adapter
→ Stable Component API
→ Service / Application
→ Diagnostics / Verification
```

平台事实尽量停留在 Driver/Adapter，不让上层长期绑定 DTS 节点、寄存器地址、board GPIO、SDK 私有 handle 等细节。

### 3.1 Driver Integration

依次检查：identity/resource → init/probe/deinit → IRQ/DMA/thread context → error/timeout/retry → power/suspend/resume → concurrency/lifetime → API/ABI/version → logging/diagnostics → build/config → test/rollback/field diagnosability。

重点确认资源在失败路径是否完整释放，timeout 后状态是否可恢复，异步回调对象 lifetime 是否稳定，错误码是否能支撑上层决策。

### 3.2 器件替代

Compatibility Matrix 至少覆盖：

- 电气/板级；
- bus/protocol；
- 初始化与寄存器差异；
- 功能与能力差异；
- 时序/性能/功耗；
- error/timeout/recovery；
- firmware/NVM/calibration；
- Linux/MCU interface；
- 生产校准/测试；
- 供应链版本与回归范围。

“API 兼容”或“能编译”只覆盖很小一部分兼容性。

### 3.3 组件化

只有多个真实平台/项目已经重复使用、差异点可隔离、stable API 能覆盖真实需求、测试/诊断方法可复用，且抽象不会隐藏关键硬件约束时，才沉淀公共组件。优先用 capability/adapter 管理差异，不为未发生的平台增加抽象层。

### 3.4 错误恢复与可诊断性

定义 retry/backoff、reset/reinit、resource recovery、degraded mode、fatal boundary、日志字段、device state、bus status 和 field diagnostics。workaround 必须有适用条件、风险和退出计划。

## 4. Evidence 模型

Driver/Component 结论应绑定 device/board、平台资源、初始化/错误/Power 路径、目标设备行为和必要性能/长稳 Evidence。替代器件还需绑定 product/board/SDK/device revision 与生产流程。

## 5. 输出 Contract

Driver Integration Review、Compatibility Matrix、Stable API / Platform Adapter Decision、Error/Power/Concurrency Contract、Platform Delta、Regression Scope、Technical Debt、Verification Scope。

## 6. 协作与交接

- `embedded.linux-bsp`：DT、IRQ/DMA、platform resource 与 Linux lifecycle；
- `embedded.mcu-rtos`：MCU ISR/DMA、scheduler、实时性与 low-level driver；
- `embedded.architecture`：系统职责、stable contract、版本与公共 API 边界；
- `embedded.debug-reliability`：未知原因的复杂设备异常；
- Hardware Expert：电气、时序、器件与板级约束；
- `assurance.verification`：target device、兼容和回归 Evidence。

## 7. Verification 要求

除 normal path 外，根据 scope 覆盖 init/deinit、timeout、retry、bus error、reset/reinit、concurrency、power/suspend/resume、不同 revision、性能/功耗、生产校准/测试和长期运行。器件替代至少验证兼容矩阵中的 required dimensions。

## 8. 常见错误

- init 成功但 deinit/error recovery 缺失；
- timeout 后 resource/lifetime 未恢复；
- suspend/resume 只测正常路径；
- API 过度暴露平台细节；
- workaround 无适用条件和退出计划；
- 替代器件只做功能 smoke，不测异常/功耗/生产流程；
- 日志无法定位 bus/device/error state；
- 为尚不存在的平台提前增加复杂抽象。

## 9. BLOCK 条件

设备/board identity 不清、平台资源事实未确认、datasheet/协议关键语义缺失、目标复用范围不明确却要求公共抽象、替代器件缺异常/Power/生产约束或关键兼容维度无 Evidence 时，应 BLOCK 或明确保持候选状态。

## 10. Knowledge Harvest 与质量指标

可沉淀 driver integration checklist、compatibility matrix、adapter pattern、error recovery rule、production calibration/test note 和 field diagnostic runbook。主要指标：接口稳定性、兼容覆盖率、error-path coverage、目标设备回归逃逸率、跨平台复用收益。
