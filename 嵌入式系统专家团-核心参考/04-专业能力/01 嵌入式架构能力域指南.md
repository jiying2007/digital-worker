# 嵌入式架构能力域指南

## 1. 领域定位

`embedded.architecture` 是 Embedded System Expert 内负责系统边界、接口、资源、生命周期和平台影响的 Capability。它负责把产品/工程目标转成可实现、可验证的技术约束，但不能用架构假设覆盖 Linux/MCU/Driver/Hardware 的直接事实。

## 2. 典型任务

- 架构设计、技术可行性与方案比较；
- Linux / MCU / RTOS / Driver / Service / Application 责任边界；
- 跨仓、跨 MCU、跨进程接口或协议变化；
- CPU / RAM / ROM / 带宽 / 时延 / 功耗资源冲突；
- Boot、Power、OTA、Watchdog、Recovery 生命周期设计；
- 平台迁移、兼容性、故障隔离和系统级 NFR 影响分析。

## 3. 必要输入

至少确认：Task Brief 与 Acceptance、产品/平台/board/SoC/MCU identity、当前系统架构与依赖、接口契约、资源现状或预算、时延/周期/功耗/成本/可靠性约束，以及相关 TRM / datasheet / schematic / source / log / measurement。

缺少直接资源事实时可以提出 target / budget / estimate 与待验证项，但不得把目标数字写成 measured fact。

## 4. 分析方法

```text
目标与约束
→ 系统/模块责任边界
→ 接口与数据流
→ 资源与时序预算
→ 生命周期与失败模式
→ 平台/版本兼容
→ Engineering scope
→ Verification scope
```

### 4.1 责任边界

明确 Linux 与 MCU 各自承担什么、BSP/Driver/Service/Application 的层级边界、谁拥有状态、谁负责错误恢复、是否存在责任空档或重复实现。公共抽象必须由真实复用需求驱动，不为假设中的未来平台提前复杂化。

### 4.2 接口契约

接口至少回答：owner、方向、sync/async、数据单位、lifetime、thread/ISR context、timeout/retry、错误码、versioning、compatibility、rollback、observability。跨 MCU/跨仓协议必须说明升级顺序与新旧版本组合。

### 4.3 资源与时序

CPU、RAM、ROM、stack、heap、buffer、DMA/CMA、task/thread、带宽、存储均区分 `target / estimate / measured`。若采用预算，应给出来源、余量和重新测量条件。

### 4.4 生命周期与失败模式

覆盖 boot、normal runtime、suspend/resume、watchdog/recovery、OTA/rollback、异常掉电、升级中间态、版本不匹配和资源耗尽。不能只设计正常终态。

### 4.5 平台与兼容

明确平台私有差异、stable contract、feature capability matrix、fallback、unsupported combination 与退出策略；不要把某一 SoC/SDK 行为伪装成通用接口事实。

## 5. Evidence 要求

可接受证据包括 exact source/interface、TRM/datasheet/schematic、MAP/size/profile、timing measurement、compatibility matrix、prototype/device/HIL 结果。涉及实测指标必须能追到对象 identity、测量条件和原始记录。

“业界通常如此”只可作为候选设计来源，不能写成本项目事实。

## 6. 输出

至少包含：Architecture Impact、Responsibility Boundary、Interface/Compatibility Decision、Resource/Timing Budget、Lifecycle/Recovery、Platform/Version Impact、Engineering Scope、Verification Scope、Unresolved Questions、Residual Risk。

## 7. 协作与交接

- `embedded.linux-bsp`：平台、Boot、Kernel、Storage、Power 事实；
- `embedded.mcu-rtos`：MCU/RTOS/实时性/Bootloader 事实；
- `embedded.driver-component`：设备协议、driver 生命周期与 reusable API；
- `embedded.debug-reliability`：未知根因或跨层异常的 hypothesis/RCA；
- Hardware Expert：电气、器件、时序、板级约束的直接 Evidence；
- `assurance.verification`：把系统 Claim 转为 required Verification。

跨域调用由 Edge Coordination 基于 evidence trigger 组织；Capability 本身不扩张为新的 Expert identity。

### 7.1 Verification 关注点

系统级变化至少检查受影响接口、版本兼容、资源预算、异常路径、Power/OTA/Recovery、关键性能和目标设备行为。实现成功只说明实施完成，不等于系统 Claim 被验证。

## 8. 常见错误

- 接口只有正常路径，没有 timeout/error/version/recovery；
- Linux/MCU 对单位、枚举、lifetime 或升级顺序理解不一致；
- 资源估算被写成实测值；
- 为未来可能的平台提前增加复杂抽象；
- 只设计升级终态，不覆盖中间失败状态；
- 用架构假设要求领域事实“服从设计”；
- 公共层泄漏 DTS 节点、寄存器地址、板级 GPIO 等平台细节；
- 没定义 Verification 就进入 Engineering。

## 9. BLOCK 条件

目标/Acceptance 不清、关键平台 identity 不清、接口一方事实缺失、关键资源约束无来源、硬件/软件 authority 冲突且未取证、系统变化无法定义最小 Verification 范围时，应 BLOCK 或保持明确的未验证假设。

## 10. Knowledge Harvest 与质量指标

应沉淀可复用的 interface contract、compatibility rule、resource budget method、platform constraint、lifecycle checklist；没有复用价值时允许 `NO_KNOWLEDGE_DELTA`。

主要质量指标：unsupported claim rate、evidence coverage、跨接口缺陷发现率、human correction rate、由架构遗漏导致的返工率。
