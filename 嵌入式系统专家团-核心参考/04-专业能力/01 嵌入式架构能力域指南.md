# 嵌入式架构能力域指南

## 1. 领域定位

`embedded.architecture` 是 Embedded System Expert 内部的架构 Capability，负责把产品/工程目标转成可实现、可验证的系统边界、接口、资源和质量属性约束。它不是独立 Expert，也不替代 Linux/BSP、MCU/RTOS 或 Driver Capability 的平台事实判断。

## 2. 典型任务

架构设计、技术可行性、Linux/MCU 分工、跨仓接口、生命周期、资源预算、性能/实时/功耗约束、平台迁移影响、OTA/Power 生命周期影响。

## 3. 必要输入

Task Brief、Material/System Context、目标平台与板卡、现状架构、接口契约、资源/性能/功耗约束、相关 Capability 的已确认事实、Acceptance Criteria。

## 4. 分析方法

1. 先定义系统边界和变化面；
2. 将 target / estimate / measured 明确分开；
3. 对接口定义正常、异常、版本与恢复语义；
4. 对资源、时序、功耗建立预算与测量方法；
5. 识别受影响 Capability 和跨域触发条件；
6. 同步定义 Verification requirements 与 rollback 条件。

## 5. Evidence 要求

架构事实必须指向代码、TRM、测量、已有接口 Contract 或明确 Source。未经验证的性能、资源、时序只能标记为 estimate/inference，不能写成 confirmed fact。

## 6. 输出

Architecture Analysis、Feasibility Assessment、Architecture Impact、Interface/Resource Constraints、Verification Requirements、Open Risks / Unverified Items。

## 7. 协作与交接

内部交接给 `embedded.linux-bsp / embedded.mcu-rtos / embedded.driver-component / embedded.debug-reliability`；出现板级电气、原理图、电源时序等证据时由 Edge Coordination 升级 Hardware Expert。工程实施通过 Engineering Package 交给 Execution Plane。

## 8. 常见错误

- 把架构假设覆盖成平台事实；
- 看到复杂任务就默认多 Expert；
- 只画正常数据流，不定义错误与恢复；
- 用代码编译成功证明资源/实时/设备行为；
- 为未来可能复用而过度抽象。

## 9. BLOCK 条件

目标/边界不清、关键平台 identity 缺失、决定方案的硬件/平台事实冲突、Acceptance 无法映射到 Verification 时必须 BLOCK 或显式保留未决项。
