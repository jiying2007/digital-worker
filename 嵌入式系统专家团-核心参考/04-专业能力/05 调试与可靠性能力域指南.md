# 调试与可靠性能力域指南

`embedded.debug-reliability` 是 Embedded System Expert 内负责异常时间线、Hypothesis、Root Cause、长稳、性能与跨层故障收敛的 Capability。具体平台、MCU、Driver 和硬件事实仍由对应责任边界提供直接 Evidence。

## 1. 典型任务

现场偶发、长稳异常、Crash/HardFault、Memory Corruption、Deadlock/Race、DMA/Cache、Storage 异常、性能退化、资源增长、温升异常和跨多个 Capability 的 Root Cause 收敛。

## 2. 必要输入与 Context

- exact source / firmware / device / test identity；
- 现象、时间、概率、环境和触发条件；
- 完整前后文 log/trace/core/dump/register；
- 最近变更和版本差异；
- 原始复现步骤或权威现场日志；
- 性能/长稳趋势数据（如适用）；
- 相关 Capability / Hardware 已确认的直接事实。

## 3. 诊断主链

```text
冻结 Context
→ 建时间线
→ 区分 Observed / Inferred / Confirmed
→ 维护唯一 Hypothesis Registry
→ 设计 discriminating experiment
→ reject / support / confirm
→ Root Cause 或 evidence insufficient
→ 最小修复建议
→ regression / stress / failure injection
```

好的 Hypothesis 必须可证伪，包含 evidence_for、evidence_against、区分实验和预期结果。诸如“系统不稳定”“可能硬件问题”不能作为可执行 Hypothesis。

### 3.1 Crash / HardFault

收集 fault context、register、stack、ELF/MAP、task/ISR、最近事件和版本身份。crash site / PC 落点不自动等于 corruption origin。

### 3.2 Memory Corruption

按 OOB/UAF/double free/stack overflow/heap corruption/DMA ownership/cache/concurrency/lifetime 分组假设。优先找首个破坏证据，不只看最终崩溃点。

### 3.3 Deadlock / Race

构建 wait-for graph、lock order、owner/waiter、priority、IRQ context、timeout 和调度时间线。区分真正 deadlock、priority inversion、starvation 和 lost wakeup。

### 3.4 Storage / DMA / 跨层问题

Storage 按 `media/ECC → controller → MTD → UBI → filesystem → app`；DMA 按 buffer owner → mapping/address → cache → start/completion → lifetime。每跨一层都保留“已确认事实”和“待验证假设”。

### 3.5 Performance / Long-run

使用 `baseline → measurement → bottleneck → controlled change → remeasurement`。长稳关注资源趋势、orphan/socket/thread/fd/memory、温度、周期性任务和累计误差。一次“跑了一夜没出现”只能说明当前样本未复现。

## 4. Evidence 与 Root Cause 标准

Confirmed Root Cause 至少满足：

1. 能解释主要现象；
2. 与版本/平台差异一致；
3. 有证据区分主要候选；
4. 修复或故障注入按预期改变结果；
5. 能由 Verification 独立复核。

否则应保持 `supported hypothesis`、`workaround` 或 `evidence insufficient`。

## 5. 输出 Contract

Timeline、Hypothesis Registry、Observed/Inferred/Confirmed Facts、Root Cause / Evidence Insufficient、Engineering Recommendation、Regression Scope、Residual Risk、Knowledge Candidate。

## 6. 协作与交接

- `embedded.linux-bsp`：Kernel、DMA、Storage、Power、BSP 事实；
- `embedded.mcu-rtos`：fault context、RTOS、ISR/DMA、timing；
- `embedded.driver-component`：driver lifecycle、device/bus/error state；
- `embedded.architecture`：系统责任、接口、资源假设；
- Hardware Expert：电气、器件、波形、板级直接证据；
- `assurance.verification`：独立复核修复和回归证据。

## 7. Verification 要求

修复至少覆盖原复现/现场特征、直接回归、负向/异常路径和必要 stress/long-run。若根因涉及 timing/concurrency/power/storage，还应包含能区分原假设的针对性验证，而不是只确认“问题暂未再出现”。

## 8. 常见错误

- 只看最后一条 error，不找第一个异常点；
- 先认定根因，再只搜支持证据；
- 多个参与方维护互相矛盾的 RCA；
- 一次改变多个关键变量导致无法确认因果；
- 复现版本和验证版本漂移；
- 用语言置信度代替 Evidence；
- workaround 或“暂未复现”被升级成 confirmed root cause；
- 从相似平台经验直接外推当前设备事实。

## 9. BLOCK 条件

source/fw/device identity 不一致、关键日志只有截断片段且无法恢复上下文、复现条件未知却要求 Confirmed Root Cause、需要平台/硬件事实但尚未取得、区分实验无法执行且替代 Evidence 不足时，应保持 `evidence insufficient` 或 BLOCK。

## 10. Knowledge Harvest 与质量指标

可沉淀 known issue、RCA pattern、fault capture method、diagnostic checklist、failure-injection case 和 monitoring rule。主要指标：root-cause accuracy、incorrect-pass rate、time-to-discriminating-evidence、recurrence rate、knowledge reuse rate。
