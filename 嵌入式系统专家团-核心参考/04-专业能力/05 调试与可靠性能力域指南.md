# 调试与可靠性能力域指南

## 1. 领域定位

`embedded.debug-reliability` 是 Embedded System Expert 内部负责复杂故障、现场问题、长稳、性能和 Root Cause 闭环的 Capability。它通过统一 Timeline 与 Hypothesis Registry 把 Observed / Inferred / Confirmed 分开，不以语言置信度替代 Evidence。

## 2. 典型任务

Crash/HardFault、memory corruption、deadlock/race、长稳异常、资源增长、性能退化、field incident、跨层偶发问题、SPI-NAND/UBIFS/DMA 等需要多层区分实验的问题。

## 3. 必要输入

exact source/firmware/device/test identity、原始 log/trace/core/dump 或稳定 reproduction、最近变更、环境与时间线、相关 Capability 已确认事实、Acceptance/Regression requirements。

## 4. 分析方法

1. 先建立事件 Timeline 和证据身份；
2. 将事实严格标记为 Observed / Inferred / Confirmed；
3. 维护一个共享 Hypothesis Registry；
4. 每个 hypothesis 必须可证伪，并定义 discriminating experiment；
5. 优先选择能最大区分多个假设的实验；
6. Root Cause 只有在可复现或直接 Evidence 支撑时确认；
7. 修复后验证原复现、受影响层和必要长稳范围。

## 5. Evidence 要求

日志片段、单次不复现、修改后现象消失都不足以自动确认 Root Cause。复杂问题必须保留 alternative hypotheses、排除证据和仍未验证项。Debug 真实 Pilot 至少需要 reproduction 或 authoritative raw log 之一。

## 6. 输出

Timeline、Hypothesis Registry、Diagnostic Report、Root Cause Assessment 或 Evidence Insufficient、Engineering Recommendation、Regression Requirements、Knowledge Harvest candidate。

## 7. 协作与交接

平台事实由 `embedded.linux-bsp / embedded.mcu-rtos / embedded.driver-component` 提供；系统影响由 `embedded.architecture` 收敛。出现板级电气直接证据时升级 Hardware Expert。Verification 独立复核修复后 Evidence，不由 RCA 实施者自签更高层 PASS。

## 8. 常见错误

- crash site = corruption origin；
- 先修改代码再补假设；
- 每个参与者维护一份相互冲突的 RCA；
- “没复现”被写成“已修复”；
- 用概率/措辞强度代替直接 Evidence；
- 只验证原现象，不做受影响层 regression。

## 9. BLOCK 条件

source/firmware/device identity 对不上、原始日志不可追溯且无法复现、关键上下文被覆盖、需要跨域事实却没有对应 owner/evidence、修复验证层不满足 Acceptance 时必须 BLOCK 或输出 Evidence Insufficient。
