# 验证领域指南

## 1. 职责

验证负责回答：**现有证据到底证明了什么，尚未证明什么。** 它不是测试执行器，也不是“CI 绿了”的盖章角色。

## 2. Verification Plan

至少包含：

- Acceptance Criterion；
- required layer；
- object identity；
- precondition；
- steps；
- expected result；
- evidence；
- failure handling；
- regression scope。

required layer 应尽量在 Engineering Package 前明确，不能在失败后为了提高完成率改成 N/A。

## 3. 七层状态

`implemented / host_verified / cross_build_verified / sil_verified / device_verified / hil_verified / release_verified`。

每层只由该层直接证据支持。低一层 PASS 不向高层推导。

## 4. Evidence 检查

### Build

source/base、toolchain、config、command、target、artifact/hash、warning/error。

### Device

board/device、firmware hash、环境、步骤、日志/measurement、结果。

### HIL

case、fixture/environment、target identity、run identity、artifact/log hash。

### Release

exact candidate、manifest/provenance、upgrade/rollback/power-loss、open risk 和 required device/HIL。

## 5. PASS_WITH_RISK

只有 required evidence 已达到基本要求、剩余风险可描述且有明确接受人时使用。缺 required layer 时保持 NOT_RUN/BLOCKED，不能改写为 PASS_WITH_RISK。

## 6. Regression Scope

至少看：

- 直接模块；
- 接口/协议消费者；
- 共享资源；
- 并发和生命周期；
- Boot/OTA/Power；
- 性能/长稳；
- 负向/异常路径。

回归不是“全量都跑”或“只跑修改点”二选一，而是根据影响面给出最小充分集合。

## 7. 常见失败模式

- 测试 case PASS 但对象 identity 不清；
- 将另一块板/另一版本 evidence 复用到当前 Run；
- HIL 执行者口头说通过但无原始 run；
- Verification 自己补代码后直接重新签 PASS；
- Acceptance 无法映射到具体 evidence；
- residual risk 在后续报告中丢失。

## 8. 输出

Verification Report 应明确 implementation owner、verifier、独立性、每层状态、overall、evidence refs、failures、unverified items 和 risks。

## 9. 边界

测试/HIL Owner 负责执行和保存原始证据；Verification 负责证据有效性和覆盖判断；是否最终放行由 Independent Review/Release Owner 决定。
