# 验证领域指南

> 岗位职责与任职资格见 [《数字岗位与能力模型》](../01-数字组织与岗位/03%20数字岗位与能力模型.md)。本文只描述 **Verification 岗位如何建立计划、检查 Evidence 和给出验证判断**。  
> Verification Layer 的完整定义只在 [《验证、独立评审、发布与异常恢复》](../03-流程与运行/04%20验证评审发布与异常恢复.md) 维护。

## 1. 领域定位

Verification 负责回答：**现有 Evidence 到底证明了什么，尚未证明什么。** 它不是测试执行器，也不是“CI 绿了”的盖章角色。

## 2. 典型任务

Acceptance → Verification Plan、required layer 定义、Build/Device/HIL evidence check、Regression Scope、Release candidate evidence check、失败层定位和 Verification Report。

## 3. 必要输入

- 明确的 Acceptance Criterion / Claim；
- exact source / artifact / target identity；
- Engineering Package / Delivery Receipt；
- 测试/HIL 原始结果；
- 环境、fixture、case、run identity；
- 已知风险和 required layer。

## 4. 分析方法

### Verification Plan

至少包含 Acceptance Criterion、required layer、object identity、precondition、steps、expected result、evidence、failure handling 和 regression scope。

required layer 应尽量在 Engineering Package 前明确，不能在失败后为了提高完成率改成 N/A。

### Evidence Check

- **Build**：source/base、toolchain、config、command、target、artifact/hash、warning/error；
- **Device**：board/device、firmware hash、环境、步骤、日志/measurement、结果；
- **HIL**：case、fixture/environment、target identity、run identity、artifact/log hash；
- **Release candidate**：exact candidate、manifest/provenance、upgrade/rollback/power-loss、open risk 和 required device/HIL。

### Regression Scope

检查直接模块、接口/协议消费者、共享资源、并发和生命周期、Boot/OTA/Power、性能/长稳、负向和异常路径，形成最小充分集合，而不是“全量都跑”或“只跑修改点”。

## 5. Evidence 要求

每个 PASS 必须映射到直接 Evidence 和明确对象 identity。低层 PASS 不能推导高层 PASS；测试执行者口头结论、另一块板/另一版本结果、无原始 run 的 HIL summary 都不能替代当前 Run 的直接 Evidence。

`PASS_WITH_RISK` 只适用于 required evidence 已达到基本要求且残余风险有明确接受人；缺 required layer 时保持 NOT_RUN/BLOCKED。

## 6. 输出

Verification Report 应明确 implementation owner、verifier、独立性、required layer、每层状态、overall、evidence refs、failures、unverified items、regression scope 和 risks。

## 7. 协作与交接

- 测试/HIL Owner：正确执行 case 并保存原始 Evidence；
- 实现岗位/Engineering：对失败负责修复或补充直接 Evidence；
- P01：提供 Acceptance、Engineering Package 和 Closure 上下文；
- P08：使用 Verification 事实做风险与放行审查；
- Release Owner：保留实际发布批准。

## 8. 常见错误

- case PASS 但 object identity 不清；
- 复用另一块板/另一版本 evidence；
- HIL 执行者口头说通过但无原始 run；
- Verification 自己补代码后直接重新签 PASS；
- Acceptance 无法映射到具体 Evidence；
- residual risk 在后续报告中丢失；
- 为提高完成率事后把失败层改成 N/A。

## 9. BLOCK 条件

Acceptance/Claim 不明确、required layer 未定义、source/artifact/device identity 不一致、required Evidence 缺失、测试环境或 fixture 无法确认、实施者与 verifier 独立性不满足且无补偿控制时，应保持 BLOCKED/NOT_RUN/FAIL，不得用低一层 PASS 或风险接受改写事实状态。
