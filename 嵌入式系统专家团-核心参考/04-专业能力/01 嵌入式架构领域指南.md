# 嵌入式架构领域指南

> 岗位职责与任职资格见 [《数字岗位与能力模型》](../01-数字组织与岗位/03%20数字岗位与能力模型.md)。本文只描述**嵌入式架构专业工作怎么做**。

## 1. 领域定位

嵌入式架构负责把产品/工程目标转成可实现、可验证的系统边界和技术约束，重点回答：系统怎么分、接口怎么定、资源够不够、失败怎么隔离、平台变化影响什么。

## 2. 典型任务

- `architecture_design` / `technical_feasibility_review`；
- Linux / MCU / RTOS 职责划分；
- 跨仓、跨 MCU 接口或协议变化；
- CPU/RAM/ROM/带宽/时延/功耗资源冲突；
- Boot、Power、OTA、Watchdog、Recovery 生命周期设计；
- 平台迁移、兼容性和系统级 NFR 影响分析。

任务走什么 Mode 只在 [任务类型运行矩阵](../03-流程与运行/05%20任务类型运行矩阵.md) 维护。

## 3. 必要输入

- Task Brief 与 Acceptance；
- 产品/平台/board/SoC/MCU identity；
- 当前系统架构、接口和依赖；
- CPU/RAM/ROM/buffer/thread/task 现状或预算；
- 时延、周期、功耗、成本、可靠性约束；
- 相关 TRM/datasheet/schematic/source/log/evidence。

缺少资源事实时可以给 target/budget 与风险，不把目标数字写成 measured fact。

## 4. 分析方法

```text
目标与约束
→ 模块 / 责任边界
→ 接口与数据流
→ 资源与时序预算
→ 生命周期与失败模式
→ 平台 / 版本兼容
→ 实施边界
→ Verification 要求
```

### 模块和责任

确认 Linux 与 MCU 各自承担什么、BSP/Driver/Service/Application 的边界，以及是否存在责任空档或重复实现。公共抽象必须由真实复用需求驱动。

### 接口

至少说明 owner、方向、sync/async、数据单位、lifetime、thread/ISR context、timeout/retry、错误码、versioning、compatibility 和 rollback。

### 资源

CPU、RAM、ROM、stack、buffer、DMA/CMA、task/thread、带宽和存储均区分 target / estimate / measured。

### 生命周期

检查 boot、normal runtime、suspend/resume、watchdog/recovery、OTA/rollback、异常掉电和升级中间态。

## 5. Evidence 要求

架构结论可引用 exact source/interface、TRM/datasheet/schematic、map/size/profile、timing measurement、compatibility matrix、prototype/device/HIL 结果。

“业界通常这样做”只能作为方案候选来源，不能写成本项目事实。涉及实测指标必须能追到测量条件和对象 identity。

## 6. 输出

至少形成：Architecture Impact、接口/兼容结论、resource/timing budget 与待验证项、failure/recovery、platform/version impact、engineering scope、Verification 要求、unresolved questions / risks。

## 7. 协作与交接

- P03/P04/P05：证明具体平台、MCU 和设备事实；
- P06：当系统现象根因未知时维护 Hypothesis 与 RCA；
- P01：收敛 Technical Decision 和 Engineering Package；
- P07：把系统 Claim 转为 required Verification；
- Engineering：按明确范围实施，不反向改写架构目标。

## 8. 常见错误

- 接口只有正常路径，没有 timeout/error/version；
- Linux/MCU 对单位、枚举或生命周期理解不一致；
- 资源估算被写成实测值；
- 为未来可能的平台提前增加复杂抽象；
- 只设计升级终态，不覆盖中间失败状态；
- 架构假设要求领域事实“服从设计”。

## 9. BLOCK 条件

以下情况不应给高置信或可实施架构结论：目标/Acceptance 不清、关键平台 identity 不清、接口一方事实缺失、关键资源约束无来源、硬件/软件 authority 相互冲突且未取证、系统变化无法定义最小 Verification 范围。
