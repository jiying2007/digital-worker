# 14 跨专家团协作与职责边界

> 同步基线：`v0.7.0 / provider-neutral`

## 1. 原则

跨团队不用“Agent 自由聊天”划职责，而用 Contract、Ownership 与 Evidence。必须明确 SSOT、Provider、Consumer、Schema、最终判断权和冲突回流。

## 2. 产品专家团 ↔ 嵌入式系统专家团

产品专家团负责 What/Why/用户场景/优先级/产品范围/产品验收意图；嵌入式专家团负责 How/技术可行性/架构与平台影响/工程范围/资源性能风险/验证策略。

正式协议：`technical-review-request.v1 → Embedded Expert Team → embedded-feasibility-review.v1`。

缺证据返回 `INSUFFICIENT_EVIDENCE`。

## 3. 人类研发工程师 / Engineering Agent Runtime

- Expert Team：技术判断、约束、Handoff；
- Engineer + selected Engineering Agent Runtime：在授权 repo/base/action scope 内实施；
- Verification：独立验证；
- Review：独立审查。

Runtime 可替换，不允许某个 Runtime 成为专家团身份或权限来源。

## 4. Interaction / Work Item Provider

飞书、WorkBuddy、Web/CLI 等可承担不同入口或工作项角色，但它们不拥有专业结论权，也不能直接绕过 Gate/Action Policy 控制开发机、设备或 Release。

## 5. Knowledge Provider / Sources

- 飞书文档、NAS、Git、CI/HIL、Artifact Store 等按事实类型保持 source truth；
- WeKnora 或其他 Knowledge Provider 负责检索/索引/引用，不自动成为唯一知识主库；
- 跨专家团不复制第二份项目权威事实；
- Provider 选型由 #16/#17 PoC 与 Capability Matrix 决定。

## 6. 端侧底座专家团

Ownership vocabulary：OWN / SHARED / CONSUME / PROVIDE / OUT_OF_SCOPE。

Boot/BSP、Kernel、RTOS、Drivers、Middleware、AI Runtime、OTA、Diagnostics、HIL、Platform Abstraction 等具体 ownership 尚未裁决，由 #11 基于规范化来源证据处理。

SHARED 必须明确 canonical owner、SSOT、provider、consumer、handoff、version compatibility、change notification、review owner。

## 7. 硬件/电路团队

嵌入式专家团消费 schematic、board revision、signal/power assumptions、measurement evidence、hardware constraints，但不能伪造硬件事实。未来可形成 board-manifest / schematic-reference / measurement-evidence / hardware-change-notice。

## 8. Provider 与 Expert Team 的边界

Provider 可承担多个角色，但每个角色必须分别证明能力；“已经购买”“支持 MCP”“可以调用 Agent”均不等于获得总体架构控制权。

## 9. 评审重点

- 产品/嵌入式/端侧底座 ownership；
- HIL 是专家团能力还是共享平台；
- Work Item 与 Interaction Provider 是否分开选；
- Knowledge Provider 是否需要主备；
- Engineering Runtime default / backup / task-specific 策略；
- Provider failure 时如何保持 Contract/Evidence 连续。
