# 总体架构设计

## 1. 要解决的工程问题

嵌入式研发的困难不在于“缺一个会回答问题的工具”，而在于任务经常同时跨越产品目标、板卡版本、Linux、MCU、驱动、设备、测试和发布。如果没有统一的工作边界，容易出现以下问题：

- 同一个问题由不同人使用不同版本的源码、固件或板卡分析；
- 调试过程中“猜测”逐渐变成“事实”，后续没有人再核对；
- Coding 工具完成修改后直接被当成验证通过；
- CI 通过被误解为设备、HIL 或 OTA 已验证；
- 历史经验被复制到多个地方，版本和适用范围失控；
- 每接入一个新工具，就重新设计一套流程和输出格式。

专家团设计的目标是把这些问题收敛为一条可追溯的工程链，而不是建立一个更大的聊天入口。

## 2. 设计目标

当前架构坚持六点：

1. **一项任务只有一条主身份链**：Work Item、Run、源码、产物、设备和验证结果能串起来。
2. **一个事实只保留一个权威来源**：索引、搜索和总结不能取代原始 Source。
3. **专业判断与工程实施分开**：专家负责判断和约束，工程师及受控 Runtime 负责实施。
4. **实施与验证分开**：实现成功不自动等于验证通过。
5. **验证与放行分开**：Verification 说明证据覆盖，Independent Review 判断是否足以放行。
6. **工具可替换，工作规则稳定**：Provider 或模型更换时不重做 Task、Gate、Evidence 和 Verification。

## 3. 系统上下文

```text
产品 / 项目 / 现场 / 测试提出任务
              │
              ▼
      Work Item / Task Brief
              │
              ▼
       嵌入式系统专家团
   ┌──────────┼───────────┐
   │          │           │
 技术分析   工程约束    风险/验证计划
   │          │           │
   └──────────┼───────────┘
              ▼
      Engineering Package
              │
              ▼
 工程师 + Engineering Runtime
              │
      修改 / 构建 / 测试
              ▼
        Delivery Receipt
              │
      ┌───────┴────────┐
      ▼                ▼
 Verification     Independent Review
      │                │
      └───────┬────────┘
              ▼
          Delivery / Closure
              │
              ▼
        Knowledge Harvest
```

外围系统包括 Git、CI、HIL、设备实验室、NAS、协作文档、Artifact Store 和知识检索系统。它们提供资料、执行环境或证据，但不因为“能被调用”就自动获得技术判断或发布权限。

## 4. 组织模型：1+7

|角色|主要责任|不负责什么|
|---|---|---|
|主理人|接单、分类、Gate、路由、交接、恢复、收口|不替专业角色给结论，不自签验证|
|嵌入式架构|系统边界、接口、资源、实时性、平台影响|不代替 BSP/MCU 完成具体实现|
|Linux/BSP|Boot、Kernel、DT、IRQ/DMA、Storage、板级资源|不替硬件确认测量事实|
|MCU/RTOS|Startup、Linker、ISR、RTOS、Watchdog、低功耗、MCU OTA|不负责 Linux 平台事实|
|驱动与组件|设备驱动、组件接口、跨平台复用、替代兼容|不决定系统级职责分配|
|调试与可靠性|时间线、Hypothesis、Root Cause、长稳和性能诊断|不替领域专家编造硬件/平台事实|
|验证|验证计划、层级状态、证据身份、回归充分性|不替实现者补代码，不做最终业务放行|
|独立审查|风险、错误放行、Release Readiness|不重复执行实施工作|

Wi-Fi、Flash、Audio、FOC、Camera 等专项先作为 Skill/知识域处理；只有真实工作量证明其职责长期独立，才讨论增加正式角色。

## 5. 两条链必须分开

### 5.1 任务执行链

```text
Engineer / Work Item
  → Runtime Session
  → digital-worker 的任务/专家/门禁规则
  → Knowledge Provider / 原始 Source
  → ADK 派生能力
  → Engineering Execution
  → Verification / Review
```

这条链服务于当天的研发任务。

### 5.2 能力演进链

```text
外部实践 / 项目经验
  → llm_agent 收集与比较
  → agent-dev-kit 形成可复用资产
  → immutable release
  → 各 Runtime Binding 消费
```

这条链服务于工具和能力的长期演进。两条链混在一起，会造成“运行工具既写规则、又改知识、又给自己放行”的职责冲突。

## 6. 四个稳定控制面 + N 个 Runtime Binding

长期边界采用：

- `digital-worker`：任务、专家、领域流程、Gate、Action Policy、Identity/Evidence、Verification、Review、Pilot；
- `knowledge-hub`：知识 Registry、authority、ACL、freshness、context/evidence 查询与生命周期；
- `agent-dev-kit`：可复用 Agent/Skill 资产、Asset Profile、发布和回滚；
- `llm_agent`：外部实践收集、采用度/健康度观察、Runtime 对比；
- Runtime Binding：Codex、Claude、IDE/Internal Runtime 等具体工程执行环境；
- Thin Session Bootstrap：在单次会话启动时装配项目、模式、Contract、Skill 和 Provider 身份，不成为新的控制面。

详细职责见《系统边界与控制面》。

## 7. 任务类型与流程模式

当前有 14 类任务：

`feature_development / defect_debugging / architecture_design / technical_feasibility_review / platform_bringup / bsp_porting / driver_development / component_development / mcu_firmware_development / performance_optimization / stability_reliability / code_review / release_ota / field_incident`。

对应 7 种流程模式：

`full_chain / short_chain / diagnostic_chain / bringup_chain / review_only / release_chain / single_expert`。

设计重点不是“模式越多越好”，而是**不让所有事情默认 full-chain**。任务分类发生在执行之前，模式扩展由主理人明确决定。

## 8. Provider-neutral 的实际含义

Provider-neutral 不等于“所有工具能力相同”，而是：

- 工具可以有不同性能、成本、权限和操作方式；
- 但交接必须使用相同的工程语义；
- 权限不会因为品牌不同而放宽；
- Runtime 输出不能直接生成 Domain Verification PASS；
- Provider 更换时，Work Item、exact base、验收、证据、风险和未验证项不能丢失。

因此可以通过真实 Pilot 选择默认 Runtime，而不是先把架构写死。

## 9. 当前不做的事

为了避免过度建设，当前不把以下能力当成前置条件：

- 企业统一 Knowledge Platform；
- 全量 Context Broker；
- Knowledge Graph；
- 统一 Runtime Gateway；
- 为每个专项新增 Agent；
- 大量新增 Schema；
- A5-A7 自动化扩权。

这些能力只有在真实任务反复出现信息断点、重复劳动或安全问题时才立项。

## 10. 架构验收标准

一项架构设计在当前阶段至少应满足：

- 换一个 Runtime 不需要修改领域流程和放行规则；
- 缺关键资料时系统能 BLOCK，而不是补语言解释；
- 源码、产物、设备和测试证据可以关联到同一 Run；
- Debug 的事实、推断和确认状态不会混用；
- 实施者不能独立完成最终 Verification + Review；
- 知识检索失败或冲突时能回到原始 Source；
- 高风险动作仍需明确授权和人工 Gate；
- 单阶段失败可以从责任阶段恢复，不强制整条链重跑。

满足这些条件只说明架构具备运行基础，不代表已经通过真实生产化验证。
