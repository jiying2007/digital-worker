# 评审说明与决策清单

## 1. 评审目的

这次评审不是讨论某个模型、某个办公产品是否“好用”，而是判断嵌入式研发的工作方式是否清楚、是否能落地、是否能避免错误放行，以及当前哪些结论已经可以作为团队基线。

评审人应重点回答四类问题：

1. **职责是否清楚**：谁负责技术判断、谁实施、谁验证、谁有最终放行权？
2. **流程是否可运行**：资料不足、执行失败、验证失败、跨仓失败时能否回到明确阶段继续？
3. **证据是否可信**：源码、产物、设备、测试结果和结论是否能追溯到同一任务？
4. **复杂度是否合适**：是否有过度设计，是否把未来可能用到的平台能力提前做成硬依赖？

## 2. 评审范围

本轮应评：

- 1+7 的组织方式；
- 任务分类与 7 种流程模式；
- Gate K/M/0/T/E/V/R/C；
- 工程实施、验证、独立审查的职责分离；
- A0-A7 操作权限；
- Provider-neutral / 多 Runtime 的工程交接；
- Source of Truth stays at source 的知识原则；
- 真实 Pilot 的准入与 Productionization 门槛；
- `digital-worker / knowledge-hub / agent-dev-kit / llm_agent / Runtime Binding` 的边界。

本轮不应因为文档完整而提前决定：唯一知识平台、唯一 Coding Runtime、统一 Context Broker、A5-A7 自动化扩权或 Production Ready。

## 3. 已经形成的基线决策

|编号|议题|当前结论|主要理由|需要再次讨论的触发条件|
|---|---|---|---|---|
|D01|专家组织|保持 1+7|覆盖主要职责，同时避免按 Wi-Fi/Flash/Audio/FOC 等专项无限拆角色|真实任务长期出现新的独立职责|
|D02|任务路由|14 类 task type + 7 种 mode 作为当前基线|能区分 Debug、Bring-up、Review、Release 等差异，不默认 full-chain|Pilot 证明某条链长期过重或缺阶段|
|D03|实施与验证|必须分开|“代码改完”不能证明设备、HIL 或 Release 已通过|组织规模变化也不能取消证据独立性|
|D04|独立审查|保留 Gate R|Verification 回答“证据证明了什么”，Review 回答“是否足以放行”|只有职责重新设计并有安全证据时|
|D05|工程 Runtime|允许多个，统一 Contract|避免把工作方法绑定到单一工具，便于真实对比和替换|Multi-runtime Pilot 后确定默认/备选|
|D06|知识权威|原文留在原 Source|Git、NAS、CI/HIL、协作文档各自擅长保存不同类型事实|PoC 证明集中迁移确有明显收益且不损失版本/ACL|
|D07|自动化权限|P0 Skill 默认不超过 A2；A6/A7 人工批准|防止分析能力自然膨胀成设备写入和发布权限|建立独立授权、审计、回滚和长期安全数据|
|D08|Skill 扩展|先用 23 个 P0 Skill，P1 由真实重复需求触发|避免先把专项知识做成大量不可维护 Skill|多个真实任务重复出现同一方法缺口|
|D09|Knowledge Hub|作为知识控制面，不替代原始事实源|集中做 registry / authority / ACL / freshness / lifecycle，比在各仓复制知识更清楚|外部 Source Pilot 证明需要调整边界|
|D10|仓库治理|iterative-development 阶段不以 main protection 阻塞 Pilot；Productionization 前严格开启|当前重点是拿到真实运行证据，server enforcement 属生产化门槛|阶段切换到 productionization|

## 4. 仍需证据支持的事项

|议题|当前状态|最小证据|
|---|---|---|
|真实 Debug 闭环|未完成|1 个真实任务从问题→根因→修复→验证→Review→Knowledge Harvest 完整结束|
|真实 Feature 闭环|未完成|1 个真实开发任务含 engineering package、delivery receipt、设备/必要 HIL 验证|
|真实 Review/Release 闭环|未完成|1 个真实候选版本完成 source/artifact/verification/risk/rollback 审查|
|Knowledge reuse|未完成|知识项在后续真实任务中被读取、引用并产生帮助|
|外部知识源|未完成|至少三类 Source，包含 ACL negative、freshness/stale/conflict 测试|
|Multi-runtime|未完成|同一冻结输入由两种 Runtime 独立执行并由同一标准验证|
|端侧底座 ownership|仍需组织决策|明确 OWN/SHARED/CONSUME/PROVIDE 与 canonical owner|

## 5. 评审时应追问的问题

### 架构

- 如果某个 Runtime 下线，任务 Contract 和证据链还能不能继续？
- 如果飞书/NAS/Knowledge Provider 的内容冲突，谁是最终权威？
- 多仓任务中，一个仓完成、另一个仓失败，Run 如何保持一致状态？
- 设备验证失败后，是否知道应该回到分析、实现还是资料阶段？

### 流程

- 简单任务是否被迫走过多 Gate？
- `review_only` 是否可能偷偷演变成改代码？
- Debug 是否真的使用同一 Hypothesis Registry，而不是每个专业各猜一个根因？
- Acceptance 是否能逐条找到对应证据？

### 安全与治理

- 设备写入和发布有没有明确的人类批准人？
- Risk waiver 能否被追踪到具体责任人和期限？
- 敏感日志、core、固件和生产密钥是否有隔离要求？

## 6. 评审输出

评审结束至少形成：

- `ACCEPT / REVISE / DEFER` 的决策清单；
- 每个 `REVISE / DEFER` 的 Owner、证据缺口和退出条件；
- 是否允许继续推进当前真实 Pilot；
- 是否存在需要修改 ADR / Contract / Schema 的事项；
- 是否出现了新的 P1 Skill / 平台能力候选。

没有证据的 Provider 能力不填 PASS；没有完成验证的工程结果不写“已闭环”。
