# 评审说明与决策清单

## 1. 评审目的

评审的目标不是讨论某个模型或办公产品是否“好用”，而是判断嵌入式研发的工作方式是否清楚、可运行、可恢复、可审计，哪些结论已经成为团队基线，哪些仍必须用真实工程证据证明。

## 2. 评审范围

本轮持续评估：1+7 组织方式、14 task types/7 modes、Gate K/M/0/T/E/V/R/C、实施/验证/审查分离、A0-A7、Provider-neutral 工程交接、Source of Truth stays at source、真实 Pilot 与 Productionization 门槛，以及四控制面 + Runtime Binding 边界。

本轮不因为文档完整而提前决定唯一知识平台、唯一 Coding Runtime、全量 Context Broker、A5-A7 自动扩权或 Production Ready。

## 5. 评审时优先追问

### 架构

- 某个 Runtime 下线后，Task/Package/Evidence 是否还能继续？
- 多个 Knowledge Source 冲突时谁是 authority？
- 多仓一部分成功、一部分失败时系统级状态是否真实？
- 哪些质量属性仍没有可量化目标，准备怎么取证？

### 流程

- 简单任务是否被迫走过多 Gate？
- `review_only` 是否可能隐式改代码？
- Debug 是否维护同一 Hypothesis Registry？
- Acceptance 是否逐条映射 evidence？
- 失败后是否知道回到哪个责任阶段？

### 组织

- 产品、项目、开发、硬件、HIL、Verification、Release Owner 的责任是否分开？
- Risk Acceptance 由谁承担？
- A6/A7 的批准人是否明确？

## 6. 评审输出

一次正式评审至少形成：

- Decision Register 的状态变化；
- `REVISE / EVIDENCE_PENDING` 的 Owner、Tracking 和退出条件；
- 是否允许继续当前真实 Pilot；
- 是否需要修改 ADR / Contract / Schema；
- 是否出现新的 P1 Skill / 平台能力候选。

没有 evidence 的 Provider 能力不填 PASS；没有完成验证的工程结果不写“已闭环”。
