# 评审总览与阅读路径

> 本页面向架构评审、技术评审、研发管理、质量/验证、安全与平台负责人。  
> 目标不是让评审者“读完所有文件”，而是保证任何结论都能从 **框架 → 责任 → 能力 → Skill → 运行 → Evidence → Assurance → 决策** 逐层追溯。

## 1. 评审对象到底是什么

本目录评审的不是某个 LLM、某个 IDE、某个 Coding CLI，也不是“文档写得是否完整”。评审对象是 Edge Foundation 在嵌入式研发场景下能否形成一套稳定、可替换 Runtime、可审计、可阻断、可验证的数字责任与工程闭环。

评审必须同时覆盖六个面：

1. **Architecture**：Domain / Role / Expert / Capability / Skill 是否分层稳定；
2. **Operation**：任务如何分类、路由、进入 Gate、生成工程交接并收口；
3. **Engineering Depth**：Linux/BSP、MCU/RTOS、Driver/Component、Architecture、Debug/Reliability 是否具备真实工程方法；
4. **Trust**：Identity、Evidence、Verification、Independent Review、Action Policy 是否能防止“看起来完成”；
5. **Knowledge**：知识如何引用、复用、更新、处理冲突，不制造第二份 Source of Truth；
6. **Productization**：真实产品证据、运行指标、风险、权限、回滚、治理是否足以进入生产化。

三个必须始终成立的分离关系：

- Responsibility ≠ Runtime；
- Engineering ≠ Verification ≠ Review；
- Canonical routing authority ≠ Product readiness。

## 4. 框架到细节的追问顺序

对任一评审结论，至少能连续回答：

1. **为什么存在这项责任？**
2. **责任属于哪个 Role / Expert / Capability / Assurance？**
3. **什么 Task Type 会进入它？**
4. **由哪些 Skill 承担方法？**
5. **Skill 需要哪些必需材料？缺失时是否 BLOCK？**
6. **Runtime 能做什么，Action ceiling 到哪里？**
7. **输出是什么结构化产物？**
8. **哪个 Evidence 直接支持结论？Evidence identity 是否绑定目标对象？**
9. **谁执行 Verification？谁执行 Review？是否存在自签？**
10. **失败时回到哪个 Gate/责任阶段？**
11. **知识是否只沉淀被证据支持的增量？**
12. **该结论是架构成立、Pilot 成立、Product readiness，还是 Productionization？四者是否被误混？**

只要其中任一环无法回答，就不是“文档细节问题”，而是可追踪的评审缺口。

## 5. 当前权威层级

| 内容 | Human View | Machine / Decision Authority |
|---|---|---|
| Domain / Expert / Capability | 本核心参考 | `domains/edge-foundation/domain.yaml` |
| Task routing | 任务类型运行矩阵 | `domains/edge-foundation/routing.yaml` |
| Skill ownership / path | Skill 能力地图 | `domains/edge-foundation/skills.yaml` |
| Skill 方法 | Skill 规划说明 | 各 `skills/<id>/SKILL.md` |
| Gate | 流程文档 | `gate-policy.yaml` 及相关 Contract |
| Runtime mode / action | Runtime 文档 | `runtime/task-modes.yaml` / action policy |
| Verification / Review | 治理文档 | `assurance/*.yaml` |
| Product readiness | 评审文档 | evaluator 输出 + frozen evidence |
| 历史设计原因 | ADR / Git | ADR + Git history |

原则：Human View 负责“解释”，机器/决策权威负责“裁决”。Human View 不复制第二份可执行配置。

## 6. 评审状态语义

评审意见建议只使用以下语义，避免“差不多”“基本可用”：

- **ACCEPTED_BASELINE**：责任/架构原则已接受，除非触发重新打开条件；
- **EVIDENCE_PENDING**：设计方向可继续，但缺真实证据，不能提升成熟度；
- **REVISE**：设计或实现本身需要修改；
- **BLOCKED**：当前任务/决策缺不可替代材料或证据；
- **PASS / PASS_WITH_RISK**：只能由对应 Assurance/Decision contract 在明确对象和范围内给出。

## 7. 评审输出最少要留下什么

一次正式评审至少产生：

- Decision Register 变化；
- 未关闭问题的 Owner / Tracking / Exit Criteria；
- 架构或 Contract 需要修改的具体位置；
- 是否存在新 Skill 候选、Skill 拆分/合并/退役候选；
- 哪些 claim 仍缺 real evidence；
- 是否允许进入下一成熟度阶段；
- 若涉及发布/高风险动作，明确 human approval 与 rollback 条件。

评审最终要证明的不是“资料很多”，而是：**任意重要结论都能被正确责任方、正确输入、正确方法、正确 Evidence 和正确 Assurance 追溯。**
