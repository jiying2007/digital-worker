# 架构到证据追踪矩阵

本页是评审的“纵向索引”。每一层都列出：它解决什么问题、Human View 在哪里、机器权威在哪里、评审必须看到什么证据。

## 1. 纵向追踪矩阵

| 层级 | 核心问题 | Human View | Canonical Authority | 最小评审证据 |
|---|---|---|---|---|
| Domain | 边界是什么 | 责任模型、总体架构 | `domain.yaml` | Domain scope、跨域升级条件 |
| Role | 谁负责协调但不产出专业事实 | Edge Coordination 文档 | `coordination.yaml` | route/material/evidence normalization 边界 |
| Expert | 哪些责任需要长期独立 owner | 责任模型 | `domain.yaml` | 独立 scope、决策权、升级条件 |
| Capability | Expert 内稳定专业能力面 | 5 个能力域指南 | `experts/**/capabilities/*.yaml` | 输入、方法、输出、质量属性 |
| Skill | 可组合原子方法 | 根 `SKILLS.md`、Skill 能力地图/规划文档 | `skills.yaml` + `skills/*/SKILL.md` | 必需输入、方法、输出、BLOCK、action ceiling |
| Skill maturity | Skill 是否真的从定义走到可验证能力 | Skill 成熟度台账、评测与证据闭环 | `skill-evaluation-plan.yaml` + invocation/evaluation/summary receipts | positive + BLOCK、semantic evidence hash、bounded maturity summary |
| Task Type | 用户问题如何进入体系 | 任务类型运行矩阵 | `routing.yaml` | mapped route、mode、assurance |
| Gate | 任务何时可前进 | 生命周期与 Gate | gate policy / contracts | entry/exit、block、failure return |
| Runtime | 谁真正执行工程动作 | Runtime 文档 | runtime policy / binding contract | exact runtime identity、source set、action |
| Artifact | 做出了什么 | 工程交付文档 | deliverable/receipt contracts | exact artifact identity / provenance |
| Evidence | 结论凭什么成立 | 身份证据架构 | evidence contracts / frozen bundle | source identity、object identity、directness |
| Verification | Acceptance 是否被证明 | Verification 文档 | `assurance/verification.yaml` | acceptance→evidence mapping |
| Review | 是否独立发现风险/错误放行 | Review 文档 | `assurance/review.yaml` | independence、findings、risk boundary |
| Knowledge | 什么可以复用 | 身份证据与知识架构 | knowledge registry / external authority | authority、freshness、ACL、reuse receipt |
| Product readiness | 真实产品是否满足当前证据轨 | Pilot/成熟度文档 | evaluator + receipts | real source/device/HIL/release evidence |
| Productionization | 是否可扩大组织级使用 | 治理文档 | strict governance + human decision | permissions、audit、rollback、ops metrics |

## 2. 横向追踪：一个 Task 必须怎样穿过体系

```text
Request
  -> task type
  -> routing decision
  -> material readiness
  -> exact source/system identity
  -> capability selection
  -> skill composition
  -> runtime execution
  -> engineering artifact/evidence
  -> verification
  -> review (when required/available by policy)
  -> decision / closure
  -> knowledge harvest
```

评审时禁止跳步推导。例如：

- “CI 绿”不能直接推出 target device PASS；
- “Skill 文件存在”不能推出 Skill 已成熟；
- “Skill invocation receipt 存在”不能推出 Skill 已 EVALUATED；
- “CI synthetic evaluation PASS”不能推出 canonical Skill maturity 已提升；
- “Verification PASS”不能推出 Independent Review PASS；
- “Feature track eligible”不能推出整个 Product readiness PASS；
- “canonical routing 已成立”不能推出 Production Ready；
- “Runtime 能做某动作”不能推出它有权限做该动作。

## 3. 典型追踪示例：UBIFS 只读 Debug

| 追踪点 | 应看到的内容 |
|---|---|
| Task Type | `defect_debugging` |
| Primary Capability | `embedded.debug-reliability` |
| Evidence-driven expansion | `embedded.linux-bsp` / storage |
| Skills | `log-triage`、`storage-filesystem-analysis`，必要时 `irq-dma-analysis` |
| Required identity | exact repo/SHA、firmware、board/device、NAND、partition、kernel/config、test |
| Debug control | 同一 Hypothesis Registry |
| Direct evidence | raw UBI/UBIFS/MTD logs、reproduction、source/config facts |
| Engineering output | technical analysis / decision / patch or config change |
| Verification | same target identity 上的复现/回归 |
| Knowledge | 只沉淀已确认 root cause、diagnostic pattern 或 explicit NO_KNOWLEDGE_DELTA |

如果只有“类似平台经验”而没有 exact target evidence，结论最多是 hypothesis，不能写 Confirmed。

## 4. 典型追踪示例：MCU HardFault

| 追踪点 | 应看到的内容 |
|---|---|
| Capability | `embedded.debug-reliability` + `embedded.mcu-rtos` |
| Skills | `crash-hardfault-analysis`、`linker-map-analysis`，必要时 `rtos-concurrency-analysis` |
| Required evidence | fault registers、stack/frame、ELF/MAP、exact firmware identity、task/ISR context |
| Block condition | symbol/firmware identity 不匹配；缺 crash frame 却声称 exact root cause |
| Verification | 修复后 fault path + regression，必要时 stress/long-run |
| Review focus | 是否把 inference 写成 confirmed；是否遗漏 secondary corruption |

## 5. 典型追踪示例：器件替代

| 追踪点 | 应看到的内容 |
|---|---|
| Capability | `embedded.driver-component`，必要时 Hardware Expert |
| Skill | `driver-integration-review` |
| Material | datasheet/TRM/schematic、bus timing、电源、driver source、生产配置 |
| Output | compatibility matrix、adapter/driver change、risk list |
| Verification | normal/error/power/recovery/production calibration |
| Block | 只比较寄存器表或 pin compatible 就声明 drop-in replacement |

## 6. 变更影响追踪

任何以下变化都必须触发对应复核：

| 变化 | 至少复核 |
|---|---|
| 新 Task Type | routing、runtime mode、Gate、Golden Case |
| 新 Capability | Expert 边界、RACI、routing、Skill owner |
| 新 Skill | ownership、input/output、action、positive/BLOCK evaluation plan、tests |
| Skill maturity 晋级 | frozen Skill contract、invocation receipt、positive+BLOCK semantic evidence、maturity summary |
| Skill owner 变化 | `skills.yaml`、frontmatter、routing/capability |
| Action ceiling 提升 | security、rollback、audit、human approval |
| 新 Runtime | binding contract、identity、evidence、qualification |
| 新 Knowledge Source | authority、ACL、freshness、conflict |
| 新 Release path | provenance、rollback、Device/HIL、A7 |
| Product stage 切换 | review hard gates、repository governance、ops metrics |

## 7. 评审判定原则

完整性不是“每个格子都有文字”，而是：

- 责任边界无重叠冲突；
- 输入不足能正确 BLOCK；
- 方法可重复；
- 输出可交接；
- claim 与 Evidence 强度匹配；
- Assurance 独立；
- failure 可回到明确阶段；
- 真实产品证据与架构/工具链证据不混用。

这张矩阵应作为所有正式评审的目录页：**从任何一层进入，都能向上追到责任，向下追到证据。**
