# 嵌入式系统数字岗位与能力模型

> **这是数字员工岗位视图，不是招聘 JD，也不是新的机器 SSOT。**  
> 目的：把现有 `1+7 Agent + 23 P0 Skill + Workflow/Gate/Evidence` 用现实研发组织语言表达清楚，让管理者、研发人员和后续能力建设人员能直接回答“这个数字员工相当于什么岗位、负责什么、要具备什么能力、如何证明胜任”。
>
> 机器执行仍以 `expert-groups/embedded-system/` 下的 Agent、Skill Registry、I/O Contract、Workflow、Action Policy、Gate、Schema 和 Evaluation 为准。本页不能覆盖机器规则。

## 1. 先统一概念

|数字员工体系|现实组织类比|本体系含义|
|---|---|---|
|Expert Group|研发部门 / 专家团队|一组稳定数字岗位组成的嵌入式研发团队|
|Module|职能模块|一类稳定工程工作，用于组织理解和能力规划|
|Position|岗位|人类可读的职责、工作内容、工作要求和资格模型|
|Agent|数字员工|承担某个 Position 的可执行数字员工定义|
|Skill|岗位技能 / SOP|Agent 完成具体工程工作的标准能力|
|Knowledge|岗位知识与资料|规范、代码、TRM、历史 RCA、项目事实等|
|Workflow|工作流程|多个数字岗位围绕一个任务如何协作|
|Gate|质量 / 审批门|进入下一阶段前必须满足的条件|
|Action Policy|岗位权限|数字员工能执行到什么动作等级|
|Evidence|工作凭据|证明判断、执行和验证结论成立的可追溯事实|
|Verification|独立质检|判断 Evidence 真正证明到了哪一层|
|Review|独立放行审查|判断现有证据、风险和例外是否足以交付|
|Runtime|工程工作台|Codex、Claude、IDE Agent、Internal Runtime 等可替换执行环境|

最重要的四个关系：

```text
Module  = 职能模块，不参与机器路由
Position = 数字岗位的人类定义
Agent    = 承担岗位的数字员工
Skill    = 数字员工掌握的岗位技能
```

当前阶段默认：**1 Position ↔ 1 Agent Definition**。Runtime 可以替换，但不能因此增加岗位、改变职责或绕过 Gate。

## 2. 数字研发组织：6 个职能模块 + 8 个数字岗位

```text
嵌入式系统数字员工团队
│
├─ M1 技术规划与工程编排
│  ├─ P01 嵌入式技术负责人
│  └─ P02 嵌入式系统架构师
│
├─ M2 Linux / BSP 平台
│  └─ P03 Linux / BSP 平台工程师
│
├─ M3 MCU / RTOS 底层固件
│  └─ P04 MCU / RTOS 固件工程师
│
├─ M4 驱动与组件平台
│  └─ P05 驱动与组件工程师
│
├─ M5 调试与可靠性
│  └─ P06 系统调试与可靠性工程师
│
└─ M6 验证与技术治理
   ├─ P07 Verification / HIL 工程师
   └─ P08 独立技术审查工程师
```

### 2.1 六大模块职责

|模块|模块定位|主要工作内容|工作要求|包含数字岗位|
|---|---|---|---|---|
|M1 技术规划与工程编排|定目标、定边界、定方案、组织闭环|Task 分类；架构；接口；资源；技术决策；工程交接；失败恢复；收口|只拉必要岗位；目标/事实分开；重大决策可追溯；不能自签最终验证|P01、P02|
|M2 Linux / BSP 平台|建立 Linux 与目标板的平台软件基础|Boot；Kernel；DT；Clock/Reset/Pinctrl；IRQ/DMA；Storage；Power；Bring-up|绑定 exact BSP/board；硬事实有 TRM/代码/测量；Build PASS 不等于设备 PASS|P03|
|M3 MCU / RTOS 底层固件|建立 MCU 启动、实时系统、底层固件和 OTA 能力|Startup；Linker；ROM/RAM；ISR/DMA；RTOS；Watchdog；Low Power；Bootloader/OTA|实时性需测量；并发需分析最坏情况；HardFault 不只凭 PC 猜根因；OTA 必须考虑掉电和 rollback|P04|
|M4 驱动与组件平台|把设备能力可靠接入系统并形成可复用接口|Driver；Protocol；Platform Adapter；Stable API；Error Recovery；器件替代；组件化|Init/Deinit/Error/Power 完整；API 编译通过不等于兼容；抽象由真实复用驱动|P05|
|M5 调试与可靠性|把复杂异常推进到可证实 Root Cause|Timeline；Hypothesis；Crash/HardFault；Memory；Deadlock/Race；Performance；长稳；故障注入|Observed/Inferred/Confirmed 分开；假设可证伪；单变量实验优先；现象消失不等于根因确认|P06|
|M6 验证与技术治理|独立证明“做对了”并判断“是否足以交付”|Verification Plan；Build/Device/HIL Evidence；Regression；Review；Release Readiness|禁止跨验证层推导；实施与最终验证/审查分离；P0/P1 风险不能被进度掩盖|P07、P08|

> **Module 不是新的运行层。** 真实任务仍然按照 `Task Type → Workflow Mode → Agent Routing → Gate / Evidence / Verification` 执行，不能改成 `Task → Module → Agent`。

# 4. 数字岗位说明书

## P01 嵌入式技术负责人

**Agent ID**：`embedded-system-team-lead`  
**所属模块**：M1 技术规划与工程编排

### 岗位定位

嵌入式数字研发团队的任务负责人和工程闭环负责人。重点不是替所有专业岗位下结论，而是让任务有清楚目标、正确路由、完整材料、明确 Gate、可执行工程包和真实收口。

### 岗位职责

- 接收 Task Brief，完成任务分类和 workflow mode 选择；
- 判断 Knowledge / Material / Intake 是否达到进入分析条件；
- 按任务影响面选择最小必要专业岗位；
- 汇总领域分析，组织 Technical Decision；
- 形成 Engineering Package，明确 exact source、验收、动作边界和回滚；
- 管理失败恢复、跨阶段回流和最终 Closure；
- 组织 Knowledge Harvest，但不把候选知识直接提升为权威事实。

### 典型工作内容

需求转工程任务、缺陷接单、新板任务分流、跨仓功能拆解、Release 前闭环检查、材料不足 BLOCK、跨专业冲突收敛。

### 工作要求

- 不默认 `full_chain`；
- 不把缺材料任务伪装成 READY；
- 不替 BSP/MCU/Driver 等领域 Owner 编造事实；
- 不自签最终 Verification；
- A6/A7 不得绕过人工批准；
- 所有 Closure 必须与真实 Evidence 和 open risk 一致。

### 数字任职要求

- **Knowledge**：理解完整 Task / Gate / Evidence / Verification 模型；
- **Skills**：必须具备本岗位注册的全部 P0 Skill；
- **Context**：能识别 repo/base/board/device/material 缺口；
- **Action**：默认能力不突破 A2，受控执行遵守 Action Policy；
- **Evidence**：能把每项实质判断追到 Source/Evidence；
- **Qualification**：任务分类准确、正确 BLOCK、无越权、无错误收口。

### P0 Skills

- `embedded-task-classifier`
- `embedded-material-readiness`
- `embedded-evidence-normalizer`

## P02 嵌入式系统架构师

**Agent ID**：`embedded-architecture-expert`  
**所属模块**：M1 技术规划与工程编排

### 岗位定位

负责系统边界、接口、资源和质量属性，把产品/工程目标转为可实现的系统方案和技术约束。

### 岗位职责

- Linux / MCU / RTOS / Driver 责任边界；
- Interface / Data Flow / API / ABI / versioning；
- CPU、RAM、ROM、带宽、时延、功耗等资源预算；
- Boot、Power、OTA、Watchdog、Recovery 生命周期；
- 平台兼容、故障隔离和 Verification 范围；
- 系统级技术取舍和 Architecture Impact。

### 典型工作内容

架构设计、技术可行性评审、跨 MCU/Linux 接口、跨仓协议变更、资源不足分析、平台迁移影响、OTA/Power 生命周期设计。

### 工作要求

- target / estimate / measured 必须区分；
- 接口必须覆盖 timeout/error/version/recovery；
- 不为尚未发生的复用过度抽象；
- 不用架构假设覆盖 TRM、代码和测量事实；
- 系统级变化必须同步定义 Verification。

### 数字任职要求

- **Knowledge**：系统分层、接口、资源、实时性、可靠性、生命周期；
- **Skills**：具备架构影响与接口审查能力；
- **Context**：需要产品目标、平台/板卡、现状架构和关键约束；
- **Evidence**：资源和性能结论能区分预算与实测；
- **Qualification**：能发现跨层冲突而不越过领域事实 Owner。

### P0 Skills

- `architecture-impact-analysis`
- `interface-contract-review`

---

## P03 Linux / BSP 平台工程师

**Agent ID**：`linux-bsp-expert`  
**所属模块**：M2 Linux / BSP 平台

### 岗位定位

负责目标板从 Bootloader 到 Linux Kernel、Device Tree、板级资源、Storage 和 Power Management 的系统级事实与 Bring-up。

### 岗位职责

- BootROM / SPL / U-Boot / Kernel 启动链；
- Kernel / DT / Kconfig / Defconfig；
- Clock / Reset / Pinctrl / Regulator；
- Memory / IRQ / DMA / Cache；
- Flash / MTD / UBI / UBIFS / Filesystem；
- Suspend / Resume / Runtime PM；
- 新 SoC、新板、BSP Porting 和平台问题定位。

### 典型工作内容

新板 Bring-up、启动失败、probe fail、DMA/cache 异常、UBIFS 只读、Flash 替代、Suspend/Resume、Kernel panic、Boot 优化。

### 工作要求

- 绑定 exact BSP / kernel / SDK / board revision；
- Clock、DMA、Memory Map 等硬事实缺 TRM/代码时不做高置信结论；
- Bring-up 逐层确认最后可信阶段；
- 不用另一块 board 的 evidence 推导当前 board；
- Build PASS 不替代 target-device evidence；
- 软件日志不能替代硬件电压/波形事实。

### 数字任职要求

- **Knowledge**：Bootloader、Kernel、DT、IRQ/DMA、Storage、Power；
- **Skills**：具备 Boot、DT、IRQ/DMA、Storage 四类核心 P0 Skill；
- **Context**：exact source、board、DTS/Kconfig、TRM/schematic、log/image identity；
- **Tools/Runtime**：必须能在授权工程 Runtime 中读取源码、构建信息、日志和设备只读 Evidence；
- **Evidence**：平台结论必须能追到 source/TRM/log/device；
- **Qualification**：能够正确 BLOCK 材料不足，且不会从 build 结果跨层推导设备结论。

### P0 Skills

- `boot-chain-analysis`
- `device-tree-review`
- `irq-dma-analysis`
- `storage-filesystem-analysis`

## P04 MCU / RTOS 固件工程师

**Agent ID**：`mcu-rtos-expert`  
**所属模块**：M3 MCU / RTOS 底层固件

### 岗位定位

负责 MCU 从 Reset/Startup 到 RTOS、实时控制基础、低功耗和 Bootloader/OTA 的系统软件能力。

### 岗位职责

- Startup / Vector / C Runtime / Clock；
- Linker Script、ELF/MAP、ROM/RAM/Stack；
- ISR / Timer / DMA / Watchdog；
- RTOS Task / Priority / Mutex / Queue / IPC；
- 实时性、Worst-case jitter；
- Low Power；
- Bootloader / MCU OTA / rollback。

### 典型工作内容

MCU Bring-up、ROM/RAM 不足、HardFault、Task stack、死锁/优先级问题、控制周期抖动、Watchdog reset、低功耗、Boot/App OTA。

### 工作要求

- 内存问题基于 MAP/ELF/section，而不是 binary 总大小；
- 实时性数字必须说明测量方法；
- ISR 不执行无边界阻塞和长耗时逻辑；
- 并发分析考虑 priority inversion、lock order 和 worst-case；
- PC 落点不是 HardFault 根因证明；
- OTA 覆盖 integrity、掉电恢复、rollback 和版本组合。

### 数字任职要求

- **Knowledge**：Startup、Linker、ISR/DMA、RTOS、Watchdog、OTA；
- **Skills**：具备 Startup、MAP、RTOS 并发三项 P0 Skill；
- **Context**：MCU/board/fw exact identity、startup/linker/map/ELF、RTOS 配置、fault context；
- **Evidence**：实时性和异常结论必须有 trace/register/map/device Evidence；
- **Qualification**：能够区分 fault site 和 root cause，且不以平均值掩盖 worst-case。

### P0 Skills

- `mcu-startup-analysis`
- `linker-map-analysis`
- `rtos-concurrency-analysis`

## P05 驱动与组件工程师

**Agent ID**：`driver-component-expert`  
**所属模块**：M4 驱动与组件平台

### 岗位定位

负责把具体硬件能力可靠接入系统，并将重复项目实现逐步沉淀为稳定、可维护、可测试、可移植的软件组件。

### 岗位职责

- Device / Bus / Protocol 集成；
- Low-level Driver 与 Platform Adapter；
- Stable Component API / ABI / Version；
- IRQ/DMA/thread context、lifetime、error/timeout/retry；
- Power / Suspend / Resume；
- 器件替代 Compatibility Matrix；
- 跨平台组件化和现场可诊断性。

### 典型工作内容

Wi-Fi/Flash/Power/Sensor 接入、Driver bring-up、器件国产替代、平台 Adapter、API 稳定化、异常恢复、跨 SigmaStar/Rockchip/MCU 复用。

### 工作要求

- Init 成功之外必须覆盖 Deinit / Error Recovery；
- API 可编译只证明很小一部分兼容性；
- 平台细节尽量留在底层和 Adapter；
- 器件替代覆盖异常、功耗、性能、校准和生产流程；
- 公共组件必须由真实复用需求驱动；
- workaround 必须有适用条件和退出计划。

### 数字任职要求

- **Knowledge**：总线、驱动生命周期、并发、错误恢复、平台抽象、兼容性；
- **Skills**：当前 P0 以 Driver Integration Review 为核心；
- **Context**：device/board identity、datasheet/TRM/schematic、bus、平台资源、现有 API、目标复用范围；
- **Evidence**：兼容结论必须基于 Compatibility Matrix 与目标环境回归；
- **Qualification**：能够识别“能编译/能初始化”与“可量产兼容”的差距。

### P0 Skills

- `driver-integration-review`

> 当前职责覆盖明显宽于 P0 Skill 数量。后续的器件替代、Wi-Fi、Flash、Power 等专项 Skill 必须由真实 Pilot 反复出现的稳定工作模式驱动，不能仅因为岗位说明书列出了工作内容就直接注册为 P0。

## P06 系统调试与可靠性工程师

**Agent ID**：`debug-reliability-expert`  
**所属模块**：M5 调试与可靠性

### 岗位定位

负责把复杂、偶发、长稳和性能异常从现象推进到可证实 Root Cause，并定义最小修复和回归边界。

### 岗位职责

- Context 冻结和异常时间线；
- Observed / Inferred / Confirmed 分层；
- 统一 Hypothesis Registry；
- Crash / Panic / HardFault；
- Memory corruption / leak；
- Deadlock / Race / DMA ownership；
- Performance / Resource trend；
- 长稳、故障注入、RCA 和 residual risk。

### 典型工作内容

Kernel panic、HardFault、内存踩踏、死锁、长期资源增长、TCP/socket 异常、存储只读、性能下降、现场偶发问题。

### 工作要求

- 先时间线和事实，后根因；
- Hypothesis 必须可证伪，并同时记录 supporting / opposing evidence；
- 区分实验尽量一次只改变关键变量；
- 不维护多份互相矛盾的 RCA；
- “改后暂未复现”不写成 confirmed root cause；
- Root Cause 必须解释主要现象并可被 Verification 独立复核。

### 数字任职要求

- **Knowledge**：OS、并发、内存、Crash、Storage、Performance 的诊断模型；
- **Skills**：Log、Crash/HardFault、Memory Corruption、Performance 四项 P0 Skill；
- **Context**：exact source/fw/device、完整上下文日志、最近变更、复现条件；
- **Evidence**：每个 Root Cause 状态都能追到区分其他候选的 Evidence；
- **Qualification**：能够正确输出 `evidence insufficient`，不以语言置信度代替事实。

### P0 Skills

- `log-triage`
- `crash-hardfault-analysis`
- `memory-corruption-analysis`
- `performance-analysis`

---

## P07 Verification / HIL 工程师

**Agent ID**：`verification-expert`  
**所属模块**：M6 验证与技术治理

### 岗位定位

负责把 Acceptance 转成可执行的 Verification Plan，并独立判断 Evidence 实际证明到了哪个 Verification Layer。

### 岗位职责

- required verification layer；
- Verification Plan；
- regression scope；
- Build / Device / HIL Evidence check；
- Verification Report；
- 对证据缺口给 `FAIL / BLOCKED / NOT_RUN / N/A` 等真实状态。

### 典型工作内容

Host/cross-build/SIL/Device/HIL 验证、回归范围设计、设备证据核对、HIL case、Release candidate 证据检查。

### 工作要求

- Verification 对象是明确 Claim；
- 每层只接受对应层直接 Evidence；
- `device_verified` 不推导 `hil_verified`；
- `hil_verified` 不推导 `release_verified`；
- 测试/HIL 执行和 Verification 判断职责分开；
- 不为了提高完成率事后把失败层改为 N/A。

### 数字任职要求

- **Knowledge**：测试设计、回归、设备/HIL、版本和 Evidence identity；
- **Skills**：计划、回归、Build、Device、HIL 五项 P0 Skill；
- **Context**：Acceptance、Engineering Package/Receipt、直接 Test/HIL Evidence；
- **Evidence**：所有 PASS 都能映射到直接 Evidence；
- **Qualification**：`incorrect_pass_rate` 必须保持安全优先，不允许跨层推导。

### P0 Skills

- `verification-plan-builder`
- `regression-scope-analysis`
- `build-evidence-check`
- `device-evidence-check`
- `hil-evidence-check`

## P08 独立技术审查工程师

**Agent ID**：`embedded-review-governor`  
**所属模块**：M6 验证与技术治理

### 岗位定位

负责从独立视角判断现有 Evidence、Verification、Open Risk、Rollback 和 Provenance 是否足以允许交付或 Release。

### 岗位职责

- Code / Technical / Release Review；
- P0/P1 finding；
- Evidence 与 Verification 完整性检查；
- Risk Acceptance 边界；
- Rollback / provenance / candidate identity；
- Release Readiness Decision。

### 典型工作内容

重要代码审查、Release/OTA readiness、风险审查、错误 PASS 拦截、开放问题和 waiver 检查。

### 工作要求

- 不重复实施；
- 不把 Review 变成另一次功能测试；
- 进度压力不能改变 Verification 事实；
- P0/P1 finding 必须显式解决或按政策处理；
- A7 发布仍由明确 Release Owner / 人工 Gate 决定。

### 数字任职要求

- **Knowledge**：系统风险、Verification、Release、rollback、provenance；
- **Skills**：具备 Release Readiness Check；
- **Context**：Technical Decision、Delivery Receipt、Verification Report、open risks；
- **Evidence**：Review Finding 必须指向具体证据、规则或缺口；
- **Qualification**：能阻止 evidence 不充分和 incorrect PASS 的错误放行。

### P0 Skills

- `release-readiness-check`


岗位说明书本身**不产生新的 Skill**。

# 6. 数字任职资格模型

“任职要求”不是招聘条件，而是判断 Agent 是否真正具备岗位能力的数字资格模型。

|维度|数字任职要求|
|---|---|
|Knowledge|必须能够访问并正确使用该岗位所需的工程知识，Source of Truth stays at source|
|Skills|岗位核心 Skill 必须已注册，并由该 Agent owner|
|Context|进入实质工作前必须拿到该任务所需的 exact source / board / device / material；不足则 BLOCK 或显式降级|
|Tools / Runtime|只能在授权 Runtime 和工具边界内执行；更换 Runtime 不改变岗位职责|
|Action|岗位能力不能自行提升 A0-A7；A5 需授权，A6/A7 保留人工批准|
|Evidence|重大判断、实施结果和验证结果必须能追到 Evidence Ref|
|Gate / Governance|必须遵守 K/M/0/T/E/V/R/C 及 fail-closed 规则|
|Qualification|通过 Golden Case、负向 Case、真实 Pilot 和安全指标证明胜任|

因此：

```text
会回答问题 ≠ 具备岗位资格
有 Skill ≠ 可以越权执行
执行成功 ≠ Verification PASS
Verification PASS ≠ A7 发布批准
```

# 7. 岗位能力成熟度

岗位能力可以用四个自然语言阶段理解，但**当前不作为新的机器状态，也不参与 Action Policy**：

|阶段|含义|
|---|---|
|基础能力|能按标准输入执行单一已注册 Skill，能正确识别缺材料|
|独立能力|能完成岗位内常规任务，正确产生 Artifact/Evidence，并能正确 BLOCK|
|高级能力|能处理多 Skill、异常路径、跨上下文和复杂故障，Human Correction 较低|
|专家能力|能处理高复杂度方案取舍、复杂 RCA 或独立风险审查，并保持安全边界|

**岗位能力成熟度与 Action Level 正交。** 即使达到“专家能力”，也不能自动获得 A6_DEVICE_WRITE 或 A7_RELEASE。

# 8. 数字员工绩效与资格评测

数字员工不以“回答多少次”“输出多少文字”作为绩效。当前评价沿用专家团机器基线中的工程指标：

- `routing_accuracy`
- `evidence_coverage`
- `unsupported_claim_rate`
- `correct_block_rate`
- `incorrect_pass_rate`
- `root_cause_accuracy`
- `verification_completeness`
- `human_correction_rate`
- `audit_trace_completeness`

岗位重点可以不同：

|岗位|优先关注指标|
|---|---|

当前 `incorrect_pass_rate` 仍然是安全优先指标。

# 9. “岗位替代”如何判定

数字员工是否能够替代某类人工岗位，不能以“Agent 已创建”判断。建议至少同时满足：

```text
岗位职责覆盖
+ 核心 Skill Coverage
+ 资格 Case PASS
+ 真实任务 / Pilot Evidence
+ Human Correction 可接受
+ Unsupported Claim 受控
+ Incorrect PASS = 0
+ 权限与审计边界稳定
```

当前仓库状态仍是 `pilot-operations-ready / iterative-development`。因此本页描述的是**岗位模型和资格框架**，不声明任何岗位已经达到完全替代人工的 Production Ready 状态。

# 10. 治理边界

以下原则冻结为岗位模型的长期边界：

1. Module 只服务组织理解和能力规划，不参与机器路由；
2. Position 是人类岗位视图，不是新的运行实体；
3. Agent 是数字员工定义；
4. Skill 是岗位技能，不升级为独立岗位；
5. 当前 Position 与 Agent Definition 默认 1:1；
6. Runtime 可替换，但岗位职责、Contract 和 Gate 不随 Runtime 改变；
7. 任职要求必须能转化为 Evidence、Case 或 Policy 检查；
8. 岗位能力成熟度不能提升 Action 权限；
9. Skill 演进由真实 Pilot 驱动；
10. 本仓库禁止再维护独立 `positions.yaml` / `positions/` 作为第二套岗位 SSOT。

最终可以用一句话理解这套体系：

> **我们不是在堆一组 AI Agent，而是在建立一个具有岗位、技能、资格、权限、证据和绩效标准的数字化嵌入式研发组织。**
