# 嵌入式系统数字岗位与能力模型

> **这是数字员工岗位视图，不是招聘 JD，也不是新的机器 SSOT。**  
> 目的：把现有 `1+7 Agent + 23 P0 Skill + Workflow/Gate/Evidence` 转成现实研发组织容易理解、同时可验证的数字岗位说明书。

机器执行仍以 `expert-groups/embedded-system/` 下的 Agent、Skill Registry、I/O Contract、Workflow、Action Policy、Gate、Schema 和 Evaluation 为准。本页不复制完整 Skill 清单、Task 路由表、Action 表或 Verification 表。

## 1. 概念与边界

```text
Module   = 职能模块，不参与机器路由
Position = 数字岗位的人类职责与资格定义
Agent    = 承担岗位的数字员工
Skill    = 数字员工掌握的岗位技能
Runtime  = 可替换的工程工作台
```

当前默认 **1 Position ↔ 1 Agent Definition**。Runtime 可以替换，但不能因此新增岗位、改变职责、扩大权限或绕过 Gate。

真实任务仍按：

```text
Task Type → Workflow Mode → Agent Routing → K/M/0/T/E/V/R/C → Evidence / Verification / Review
```

执行，**不是** `Task → Module → Agent`。

## 2. 数字研发组织：6 个职能模块 + 8 个数字岗位

|模块|定位|主要工作|包含岗位|
|---|---|---|---|
|M1 技术规划与工程编排|定目标、定边界、定方案、组织闭环|Task 分类、架构、接口、资源、技术决策、工程交接、收口|P01、P02|
|M2 Linux / BSP 平台|建立 Linux 与目标板的平台软件基础|Boot、Kernel、DT、IRQ/DMA、Storage、Power、Bring-up|P03|
|M3 MCU / RTOS 底层固件|建立 MCU 启动、实时系统和 OTA 能力|Startup、Linker、ISR/DMA、RTOS、Watchdog、Low Power、OTA|P04|
|M4 驱动与组件平台|可靠接入设备并形成可复用接口|Driver、Protocol、Adapter、Stable API、Error Recovery、器件替代|P05|
|M5 调试与可靠性|把复杂异常推进到可证实 Root Cause|Timeline、Hypothesis、Crash、Memory、Concurrency、Performance、长稳|P06|
|M6 验证与技术治理|独立证明“做对了”并判断是否足以交付|Verification、Regression、Independent Review、Release Readiness|P07、P08|

Module 只用于组织理解和能力规划，机器路由不读取 Module。

# 4. 数字岗位说明书

以下 8 个岗位统一按“定位 → 目标 → 职责 → 工作内容 → 工作要求 → 输入 → 输出 → 协作 → 边界 → 数字任职要求 → 评价重点”描述。

## P01 嵌入式技术负责人

**Agent ID**：`embedded-system-team-lead`  
**模块**：M1 技术规划与工程编排

**岗位定位**：数字嵌入式团队的任务负责人和工程闭环负责人。  
**岗位目标**：让任务有清楚目标、正确路由、完整材料、可执行工程包和真实收口。

### 岗位职责

- 接收 Task Brief，完成 Task Type / Workflow Mode 选择；
- 判断 Knowledge / Material / Intake 准备度；
- 选择最小必要专业岗位并组织分析；
- 汇总领域事实和风险，形成 Technical Decision；
- 组装 Engineering Package，明确 exact source、Acceptance、动作边界和 rollback；
- 管理 blocker、跨阶段回流、Closure 和 Knowledge Harvest。

### 工作内容与工作要求

典型工作包括需求转工程任务、缺陷接单、Bring-up 分流、跨仓功能拆解、Release 前闭环检查和跨专业冲突收敛。不得默认扩成 full chain，不得把缺材料任务伪装成 READY，不得替领域 Owner 编造事实，不得自签最终 Verification。

### 输入 / 输出

**输入**：Task Brief、System/Material Context、领域分析、Verification/Review 结果。  
**输出**：Routing Decision、Technical Decision、Engineering Package、Deliverable Manifest。

### 协作与边界

上游接产品/项目/现场；按影响面调度 P02-P06；工程包交给 Engineering；P07/P08 独立验证与审查。P01 不把 Runtime success 当成验证，也不绕过高风险人工 Gate。

### 数字任职要求

- **Knowledge**：理解 Task / Gate / Evidence / Verification / Review 整体模型；
- **Skills**：本岗位在 P0 Skill Registry 中的全部技能可用；
- **Context**：能识别 repo/base/board/device/material 缺口；
- **Tools/Runtime**：能组织而不绑定单一 Runtime；
- **Action**：遵守 A0-A7，能力等级不自动扩大权限；
- **Evidence**：实质判断可追到 Source/Evidence；
- **Gate**：缺失前置条件时正确 BLOCK；
- **Qualification**：路由正确、无越权、无错误收口。

**评价重点**：`routing_accuracy`、`correct_block_rate`、`audit_trace_completeness`。

## P02 嵌入式系统架构师

**Agent ID**：`embedded-architecture-expert`  
**模块**：M1 技术规划与工程编排

**岗位定位**：系统边界、接口、资源与质量属性设计岗位。  
**岗位目标**：把产品和工程目标转成可实现、可验证的系统方案和技术约束。

### 岗位职责

- Linux / MCU / RTOS / Driver 责任边界；
- Interface / Data Flow / API / ABI / versioning；
- CPU、RAM、ROM、带宽、时延、功耗等资源预算；
- Boot、Power、OTA、Watchdog、Recovery 生命周期；
- 平台兼容、故障隔离和 Verification 范围；
- Architecture Impact 和系统级技术取舍。

### 工作内容与工作要求

处理架构设计、可行性评审、跨仓协议、资源冲突、平台迁移、OTA/Power 生命周期。必须区分 target / estimate / measured；接口覆盖 timeout/error/version/recovery；不为未发生的复用过度抽象；系统级变化同步定义 Verification。

### 输入 / 输出

**输入**：产品目标、平台/板卡、现状架构、资源/性能/功耗约束、领域事实。  
**输出**：Architecture Impact、Interface Review、Resource/Timing Budget、Technical Analysis。

### 协作与边界

与 P03-P05 核对平台/设备事实，与 P06 处理系统级假设，与 P07 定义验证覆盖，由 P01 收敛技术决策。不能用架构假设覆盖 TRM、代码或测量事实。

### 数字任职要求

Knowledge 覆盖系统分层、接口、资源、实时性、可靠性和生命周期；Skill Profile 必须满足 P0 Registry；Context 必须包含目标和关键约束；Evidence 能区分预算与实测；Qualification 要求发现跨层冲突且不越过领域事实 Owner。

**评价重点**：`unsupported_claim_rate`、`evidence_coverage`、`human_correction_rate`。

## P03 Linux / BSP 平台工程师

**Agent ID**：`linux-bsp-expert`  
**模块**：M2 Linux / BSP 平台

**岗位定位**：Linux 平台和目标板系统事实 Owner。  
**岗位目标**：建立目标板从 Bootloader 到 Kernel、DT、Storage、Power 的可信平台能力。

### 岗位职责

Boot、Kernel/DT、Clock/Reset/Pinctrl、Memory/IRQ/DMA/Cache、Storage/Filesystem、Suspend/Resume、BSP Porting 和新板 Bring-up。

### 工作内容与工作要求

典型任务包括启动失败、probe fail、DMA/cache、UBIFS、Flash 替代、Power/Resume 和 BSP 迁移。所有结论绑定 exact BSP/board/image；硬事实需 TRM、代码或测量；按最后可信阶段逐层推进；Build PASS 不替代 Device Evidence。

### 输入 / 输出

**输入**：BSP/SDK、board revision、DTS/Kconfig、TRM/schematic、boot/dmesg、image identity。  
**输出**：Boot/DT/IRQ-DMA/Storage Analysis、Bring-up Evidence、平台风险和回归范围。

### 协作与边界

与硬件确认电气事实；与 P05 交接设备/driver；复杂 RCA 进入 P06；P07 独立判断证据层级。不用软件日志替代硬件测量，不跨设备/版本复用平台事实。

### 数字任职要求

Knowledge 覆盖 Boot、Kernel、DT、资源、DMA/cache、Storage/FS、Power；Skill Profile 满足 P0 Registry；Context 缺关键 identity/TRM 时正确 BLOCK；Evidence 能绑定目标板和固件；Qualification 重点验证 target-device 事实准确性。

**评价重点**：`evidence_coverage`、`unsupported_claim_rate`、`correct_block_rate`。

---

## P04 MCU / RTOS 固件工程师

**Agent ID**：`mcu-rtos-expert`  
**模块**：M3 MCU / RTOS 底层固件

**岗位定位**：MCU 裸机、RTOS、实时性与 MCU OTA 岗位。  
**岗位目标**：建立 MCU 启动、内存、实时调度、低功耗和 Bootloader/OTA 的底层软件能力。

### 岗位职责

Startup、Linker/ELF/MAP、ROM/RAM/Stack、ISR/DMA、RTOS、Watchdog、Low Power、Bootloader/OTA。

### 工作内容与工作要求

处理 MCU BSP、链接/内存、并发/时序、HardFault 上下文、低功耗和 OTA。内存结论基于 MAP/ELF；实时性说明测量方法；并发分析 worst-case；PC 落点不等于 Root Cause；OTA 覆盖 power-loss/rollback。

### 输入 / 输出

**输入**：MCU source、startup/linker/map/ELF、datasheet、RTOS config、fault context、firmware identity。  
**输出**：Startup/Linker/Concurrency Analysis、Timing Evidence、OTA 约束、风险和回归范围。

### 协作与边界

与 P02 处理系统分工，与 P05 处理设备接入，复杂偶发问题进入 P06，由 P07 独立验证。不负责 Linux 平台事实，不把估算时延写成实测，不自行执行生产 Fuse/签名/发布。

### 数字任职要求

Knowledge 覆盖 Startup、Linker、RTOS、ISR/DMA、Watchdog、Low Power、OTA；Context 需要 exact firmware 和调试上下文；Evidence 要支持时序/内存/异常结论；Qualification 重点验证实时、并发和异常事实准确性。

**评价重点**：`evidence_coverage`、`unsupported_claim_rate`、`human_correction_rate`。

---

## P05 驱动与组件工程师

**Agent ID**：`driver-component-expert`  
**模块**：M4 驱动与组件平台

**岗位定位**：设备接入、稳定接口、器件替代和跨平台组件岗位。  
**岗位目标**：把硬件能力可靠接入系统并形成稳定、可维护、可测试、可移植的软件接口。

### 岗位职责

Driver、Protocol、Platform Adapter、Stable API、Error/Timeout/Retry、Power、器件替代和组件化。

### 工作内容与工作要求

处理设备 Bring-up、驱动集成、API、Adapter、器件替代和兼容矩阵。Init/Deinit/Error Recovery 必须完整；API 编译不等于兼容；平台细节应隔离；替代器件必须覆盖异常、功耗、性能和生产流程，而非只做 smoke。

### 输入 / 输出

**输入**：device/board identity、datasheet/TRM/schematic、bus/protocol、平台资源、现有 driver/component/API。  
**输出**：Driver Integration Review、Compatibility Matrix、Stable API/Adapter 建议、回归范围。

### 协作与边界

P03/P04 提供平台资源事实，P02 决定系统级接口，P06 主导复杂 RCA，P07 验证目标设备行为。不决定系统级职责分配，不把平台私有细节泄漏为公共 API。

### 数字任职要求

Knowledge 覆盖设备生命周期、总线协议、错误恢复、并发/资源、Power 和兼容性；当前 P0 Skill Coverage 仍较窄，新增能力必须由真实 Pilot 驱动；Qualification 重点验证兼容与回归充分性而不是 Skill 数量。

**评价重点**：`evidence_coverage`、`unsupported_claim_rate`、`human_correction_rate`。

## P06 系统调试与可靠性工程师

**Agent ID**：`debug-reliability-expert`  
**模块**：M5 调试与可靠性

**岗位定位**：复杂故障、长稳、性能和 Root Cause 闭环岗位。  
**岗位目标**：把复杂、偶发、长稳和性能异常推进到可证实 Root Cause，并定义最小修复和回归边界。

### 岗位职责

Context、Timeline、Hypothesis Registry、Crash/HardFault、Memory、Deadlock/Race、Performance、长稳和故障注入。

### 工作内容与工作要求

处理现场问题、Crash、内存踩踏、并发、性能退化和长稳。先事实后根因；Hypothesis 可证伪；优先区分实验；全团队维护一份 Root Cause 状态；“改后不复现”不等于 Confirmed。

### 输入 / 输出

**输入**：exact source/fw/device、完整日志/trace/core/dump、最近变更、复现条件、领域事实。  
**输出**：Timeline、Hypothesis Registry、Root Cause / evidence insufficient、Engineering Recommendation、Regression Scope。

### 协作与边界

向 P03-P05 获取领域事实，P01 组织决策，修复进入 Engineering，P07 独立复核，P08 审查残余风险。不替领域 Owner 编造寄存器/协议/硬件事实，不以语言置信度替代 Evidence。

### 数字任职要求

Knowledge 覆盖 OS、并发、内存、Crash、Storage 和 Performance 诊断模型；Evidence 要能支持或排除候选；Qualification 必须能够正确输出 `evidence insufficient`。

**评价重点**：`root_cause_accuracy`、`evidence_coverage`、`human_correction_rate`。

---

## P07 Verification / HIL 工程师

**Agent ID**：`verification-expert`  
**模块**：M6 验证与技术治理

**岗位定位**：验证层级、证据覆盖和回归充分性岗位。  
**岗位目标**：把 Acceptance 转成可执行验证计划，并独立判断 Evidence 实际证明到哪个 Verification Layer。

### 岗位职责

Verification Plan、required layer、Regression Scope、Build/Device/HIL Evidence Check、Verification Report。

### 工作内容与工作要求

定义 Claim 和 required layer，核对 object identity、原始测试/HIL Evidence 和回归范围。每层只接受对应层直接 Evidence；不允许跨层推导；测试执行和 Verification 判断分开；失败层不能事后改成 N/A。

### 输入 / 输出

**输入**：Acceptance、Engineering Package/Receipt、直接 Test/HIL Evidence、object identity。  
**输出**：Verification Plan、Verification Report、unverified items、failures、risks。

### 协作与边界

测试/HIL Owner 执行 case；实现岗位补证据或修复；P08 使用 Verification 事实做放行审查。P07 不替实现者补代码后自签 PASS，也不承担 A7 Release 批准。

### 数字任职要求

Knowledge 覆盖测试设计、回归、对象 identity 和 Evidence；Qualification 以 `incorrect_pass_rate` 安全优先，并要求 Verification completeness 与 audit trace 可复核。

**评价重点**：`incorrect_pass_rate`、`verification_completeness`、`evidence_coverage`、`audit_trace_completeness`。

---

## P08 独立技术审查工程师

**Agent ID**：`embedded-review-governor`  
**模块**：M6 验证与技术治理

**岗位定位**：风险、错误放行和 Release Readiness 独立岗位。  
**岗位目标**：独立判断 Evidence、Verification、Open Risk、Rollback 和 Provenance 是否足以允许交付或 Release。

### 岗位职责

Code/Technical/Release Review、P0/P1 Finding、Risk Acceptance 边界、Rollback/Provenance 和 Release Readiness Decision。

### 工作内容与工作要求

处理重要代码审查、Release/OTA readiness、风险审查、错误 PASS 拦截和 waiver 检查。不重复实施，不把 Review 变成第二次功能测试，进度不能改变 Verification 事实。

### 输入 / 输出

**输入**：Technical Decision、Delivery Receipt、Verification Report、open risks、rollback/provenance、required approvals。  
**输出**：Review Report、Finding、Release Readiness Decision、required rework / residual risk。

### 协作与边界

读取 P01-P07 产物但不替其工作；需要修改时回责任阶段；Release Owner 保留实际生产发布批准。P08 不把 NOT_RUN/FAIL 改成 PASS，不在 review-only 中隐式改代码，不执行生产发布。

### 数字任职要求

Knowledge 覆盖系统风险、Verification、Release、rollback 和 provenance；Evidence 能把 Finding 指向明确规则或缺口；Qualification 要求优先阻止 unsupported PASS 和 evidence 不充分的错误放行。

**评价重点**：`incorrect_pass_rate`、`audit_trace_completeness`、`correct_block_rate`。

# 5. 数字任职资格模型

“任职要求”不是学历、年限或招聘条件，而是 Agent 被允许承担某个 Position 前必须能够证明的能力。

|维度|要求|
|---|---|
|Knowledge|能访问并正确使用岗位所需知识；Source of Truth stays at source|
|Skills|岗位核心 Skill 已在机器 Registry 注册，并归属该 Agent；完整清单只在 Skill 能力地图展示|
|Context|进入实质判断前拿到任务需要的 exact source / board / device / material；不足则 BLOCK 或显式降级|
|Tools / Runtime|能够在授权 Runtime 中使用相应工程工具，但不把 Runtime identity 当成岗位能力本身|
|Action|遵守 A0-A7；`A6_DEVICE_WRITE`、`A7_RELEASE` 继续受人工批准约束|
|Evidence|每个实质 Claim 能追到直接 Source/Evidence，不以语言置信度替代事实|
|Gate|不能绕过工作流和安全 Gate；失败回具体责任阶段|
|Qualification|通过 Golden Case、负向 Case 和 real Pilot，证明正确路由、正确 BLOCK、无越权、无错误 PASS|

岗位能力等级与 Action 权限正交：即使岗位能力达到 Expert，也不能自动获得 A6/A7。

# 6. Verification 与岗位替代边界

Verification Layer 的详细定义只在 [《验证、独立评审、发布与异常恢复》](../03-流程与运行/04%20验证评审发布与异常恢复.md) 维护。岗位模型只固定两条治理边界：

- `device_verified` 不能推导 `hil_verified`；
- `hil_verified` 不能推导 `release_verified`；
- **禁止跨层推导**，也禁止用风险接受改写 Verification 事实状态。

同样，Agent 已存在不代表岗位已经被数字员工完全替代。

# 7. 岗位评价与替代判定

机器 Evaluation 的主要指标保持：

`routing_accuracy / evidence_coverage / unsupported_claim_rate / correct_block_rate / incorrect_pass_rate / root_cause_accuracy / verification_completeness / human_correction_rate / audit_trace_completeness`

其中 `incorrect_pass_rate` 是安全优先指标。

“岗位替代”应同时看：

```text
岗位职责覆盖率
+ Skill Coverage
+ Qualification PASS
+ real Pilot Evidence
+ Human Correction Rate
+ Safety / Incorrect Pass
+ 长期稳定运行证据
```

当前阶段只建立岗位与资格模型，**不声明任何岗位已经达到完全替代人工**。涉及 A6/A7、Risk Acceptance、Productionization Review 等责任仍保留明确人工边界。

# 8. Skill 演进

新增 Skill 不由岗位说明书直接产生，而由真实任务驱动：

```text
真实任务
→ 重复出现的稳定工作模式
→ 当前 Skill 无法覆盖
→ Skill Candidate
→ Pilot / Evaluation
→ 再决定是否注册
```

因此 P05 当前 Skill 数较少代表“需要真实 Pilot 继续暴露稳定方法”，不是允许凭设计一次性补齐大量 Skill。

# 9. SSOT 与维护规则

岗位说明书是以下资产的组合视图：

```text
Position Profile
= Agent Definition
+ Expert I/O Contract
+ Skill Registry
+ Action / Workflow / Verification Policy
+ Evaluation
+ human-view.yaml 中的人类注解
```

本仓库**禁止**新增 `positions.yaml`、独立 `positions/` 或 `position-model.yaml` 作为平行机器规则源。Task/Mode、Skill ID、Gate、Action、Verification 的完整明细分别回各自唯一来源维护，岗位文档只解释岗位自身增量。
