# 嵌入式系统专家团｜架构与运行总览

> **第一阅读入口。** 目标是让第一次接触的人在 10 分钟内理解全貌，让日常工程人员在 30 秒内判断一项任务应该怎么走。
>
> 本页是**人类总览视图**，不是第二个 SSOT。任务路由、Gate、Action Policy、Verification、Schema 与 Contract 仍以 `expert-groups/embedded-system/` 下的机器资产为准。

## 02. 任务路由矩阵

这是软件侧对应硬件“固定串并行链”的核心视图：**软件不固定专家顺序，而固定任务分类和阶段骨架。**

|task_type|中文场景|默认 mode|允许 mode|主责专家|关键产物 / 特别要求|典型验证起点|
|---|---|---|---|---|---|---|
|`feature_development`|新功能开发|`short_chain`|`short_chain` / `full_chain`|架构、驱动、MCU、BSP 按影响面|架构影响 + Engineering Package + Acceptance→Evidence|cross-build + device；系统级变化按需 HIL|
|`defect_debugging`|缺陷调试|`diagnostic_chain`|`diagnostic_chain`|调试与可靠性|共享 Hypothesis Registry + Root Cause / 证据不足结论|原复现 + 受影响层回归|
|`architecture_design`|架构设计|`short_chain`|`short_chain` / `review_only`|嵌入式架构|影响矩阵 + 接口/资源/NFR + 验证策略|Review evidence；实施另开链|
|`technical_feasibility_review`|技术可行性评审|`review_only`|`review_only`|嵌入式架构|Feasibility + 条件 + 风险 + 未决项|证据充分性；通常不要求无关 Device/HIL|
|`platform_bringup`|新板/新平台 Bring-up|`bringup_chain`|`bringup_chain`|Linux/BSP、MCU/RTOS、驱动组件|Board/System Context + 分层 Bring-up evidence|cross-build + target device；关键链按需 HIL|
|`bsp_porting`|BSP 移植|`bringup_chain`|`bringup_chain` / `short_chain`|Linux/BSP|Boot/DT/resource/driver 适配证据|cross-build + device|
|`driver_development`|驱动开发|`short_chain`|`short_chain`|驱动组件、Linux/BSP|Driver integration review + error recovery|cross-build + device|
|`component_development`|组件开发|`short_chain`|`short_chain`|驱动组件、架构|Stable API + platform adapter + regression scope|host/cross-build + target integration|
|`mcu_firmware_development`|MCU 固件开发|`short_chain`|`short_chain` / `full_chain`|MCU/RTOS|Startup/RTOS/resource/OTA 影响 + Engineering Package|cross-build + target；实时/安全关键按需 HIL|
|`performance_optimization`|性能优化|`short_chain`|`short_chain` / `diagnostic_chain`|调试可靠性、架构|baseline → measurement → change → re-measurement|同环境指标复测 + regression|
|`stability_reliability`|稳定性/可靠性|`diagnostic_chain`|`diagnostic_chain`|调试可靠性、验证|时间线 + Hypothesis + 长稳/恢复证据|device/HIL/long-run 按目标定义|
|`code_review`|代码审查|`review_only`|`review_only`|独立审查|Review Report；不得隐式改代码|Review 本身；按需读取已有 evidence|
|`release_ota`|Release/OTA|`release_chain`|`release_chain`|验证、独立审查|source/artifact manifest + rollback + open risk + approval|device + rollback/power-loss + release evidence|
|`field_incident`|现场问题|`diagnostic_chain`|`diagnostic_chain`|调试可靠性、验证|现场 identity + 时间线 + Hypothesis + containment|复现/替代证据 + 修复后受影响层验证|

### 7 种 workflow mode

|mode|用途|
|---|---|
|`full_chain`|跨多专业、从技术分析到验证和收口的完整链路|
|`short_chain`|已有产品/平台上的常规功能、驱动、组件或优化|
|`diagnostic_chain`|缺陷、长稳、现场问题的证据驱动诊断闭环|
|`bringup_chain`|新板、新 SoC、新 BSP 或平台 Bring-up|
|`review_only`|技术可行性、架构或代码审查，不自动扩展为实施|
|`release_chain`|Release/OTA/rollback/provenance/readiness|
|`single_expert`|边界清晰、无需跨专家判断的单领域分析|

## 03. 串并行与 Gate

|阶段|名称|类型|Owner|核心输出|核心问题|FAIL / 恢复|
|---|---|---|---|---|---|---|
|`gate.k`|Knowledge Readiness|Gate|`embedded-system-team-lead`|`knowledge-readiness`|所需知识能追到可信 Source？|缺知识 → `needs_information` / BLOCK|
|`gate.m`|Engineering Material Readiness|Gate|`embedded-system-team-lead`|`material-manifest`|repo/base/board/device/material 齐全？|缺材料 → `needs_information` / BLOCK|
|`gate.0`|Intake Clarity|Gate|`embedded-system-team-lead`|`task-charter`|目标/范围/边界/约束/验收清楚？|返回澄清|
|`phase.triage`|Technical Triage and Routing|串行|`embedded-system-team-lead`|`routing-decision`|task type / mode / 主责是否正确？|重新分类和路由|
|`phase.analysis`|Domain Analysis|**按需并行**|`routed-domain-expert`|`technical-analysis`；诊断类加 `hypothesis-registry`|领域事实、推断、风险和假设是什么？|继续取证或增加相关专业|
|`gate.t`|Technical Decision Gate|Gate|`embedded-system-team-lead`|`technical-decision`|方案、影响、风险、验证、回滚足够？|回 Analysis|
|`gate.e`|Engineering Handoff Gate|Gate|`embedded-system-team-lead`|`engineering-task-package`|工程师能否按包直接执行？|补 exact identity / acceptance / 动作边界|
|`phase.execution`|Engineering Execution|执行|`engineer-plus-engineering-agent`|`delivery-receipt`|按 exact base 实施并记录真实动作|记录 blocker / resume point|
|`gate.v`|Verification Gate|Gate|`verification-expert`|`verification-report`|证据真正证明到了哪一层？|回 precise failed stage|
|`gate.r`|Independent Review Gate|Gate|`embedded-review-governor`|`review-report`|证据、残余风险和例外是否足以放行？|REQUEST_CHANGES / BLOCKED → 责任阶段|
|`gate.c`|Closure Gate|Gate|`embedded-system-team-lead`|`deliverable-manifest`|交付、blocker、risk、verification 是否真实完整？|不满足不得 `completed`|

### 各 mode 的阶段路径

```text
full_chain       K→M→0→Triage→Analysis→T→E→Execution→V→R→C
short_chain      K→M→0→Triage→Analysis→T→E→Execution→V→R→C
diagnostic_chain K→M→0→Triage→Analysis→T→E→Execution→V→R→C  + Hypothesis Registry
bringup_chain    K→M→0→Triage→Analysis→T→E→Execution→V→R→C  + 逐层 Bring-up evidence
review_only      K→M→0→Triage→Analysis→T→R→C                 （无 Execution/V）
release_chain     K→M→0→Triage→Analysis→T→V→R→C               （默认只做 readiness，不发布）
single_expert     K→M→0→Triage→Analysis→T→C
```

**失败原则**：单阶段失败回到具体责任阶段；不因为一个失败机械重跑整条链。跨阶段自动回流最多一次，之后需要人类明确决策。

详细说明：[任务生命周期与 Gate](../02-流程与运行/01%20任务生命周期与Gate.md)

## 05. 权限 × Verification × 人工 Gate

> **做过了 ≠ 验证通过；验证通过 ≠ 可以发布；可以发布 ≠ 已执行发布。**

### A0-A7

|Action|能做什么|默认策略|前置 / 批准|典型 Evidence|明确不能推导|
|---|---|---|---|---|---|
|`A0_READ`|读取已授权源码、文档、日志、配置和证据|allowed|授权范围|source/read refs|读取成功不证明结论正确|
|`A1_ANALYZE`|静态分析、检索、推理、风险识别、方案比较|allowed|已有可信输入|analysis refs|分析结果不等于 Verification|
|`A2_GENERATE`|生成设计、任务包、补丁建议、测试计划、知识候选|allowed|动作仍停在生成|design/package|生成补丁不等于实施|
|`A3_MODIFY_WORKTREE`|修改隔离分支或受控工作树|controlled|repo root + exact base + dirty baseline|diff/patch|修改成功不等于 build/device PASS|
|`A4_BUILD_TEST`|Host、静态检查、交叉构建、受控 SIL|controlled|command scope + artifact identity|build/test/artifact|build PASS 不等于 device/HIL PASS|
|`A5_DEVICE_READ`|串口/JTAG/SSH/ADB 等设备只读诊断|authorization-required|device identity + access authorized|device evidence|读到设备不获得写权限|
|`A6_DEVICE_WRITE`|烧录、配置写入、重启、升级等改变设备状态|**human-approval-required**|device identity + rollback + explicit approval|action receipt + device evidence|写入成功不等于 release PASS|
|`A7_RELEASE`|发布、签名、promotion、生产 OTA|**human-approval-required**|Release Owner + release evidence + explicit approval|release evidence|readiness 不等于实际发布|

### 7 层 Verification

|Verification layer|直接证据|能证明|不能自动证明|
|---|---|---|---|
|`implemented`|exact source / diff / unit evidence|实现存在、部分逻辑成立|目标板行为|
|`host_verified`|Host test / static check|主机层行为|目标工具链/设备|
|`cross_build_verified`|exact toolchain/config/build log + artifact|目标工具链可构建|设备功能正确|
|`sil_verified`|受控 SIL / 仿真 evidence|仿真环境行为|真实硬件时序/电气|
|`device_verified`|board/device/fw identity + measurement|指定设备条件下行为|系统级/长期回归充分|
|`hil_verified`|case/fixture/target/run evidence|指定 HIL case 的系统行为|所有 Release 风险|
|`release_verified`|candidate manifest + rollback/power-loss + required evidence|指定候选版本的发布证据完整|A7 人工批准、实际发布动作|

禁止跨层推导：`forbid_cross_layer_inference = true`。

|活动|产品负责人|项目负责人|嵌入式主理人|开发工程师|硬件工程师|测试/HIL Owner|Verification|Review Governor|Release Owner|Knowledge Owner|IT/Security|

|目标/产品验收意图|A/R|C|C|I|I|C|C|I|I|I|I|
|Task Brief / 技术入口澄清|C|C|A/R|C|C|C|I|I|I|I|I|
|工程材料/版本身份确认|I|C|A|R|R(硬件)|C|C|I|I|C|I|
|技术分析/方案|C|C|A|R/C|C|C|C|I|I|I|I|
|代码/配置实施|I|I|C|A/R|C|I|I|I|I|I|C(权限)|
|设备写入 A6 批准|I|C|C|R|C|C|I|I|I|I|A/C(组织政策)|
|测试/HIL 执行|I|C|C|C|C|A/R|C|I|I|I|I|
|Verification Plan/Report|I|I|I|C|C|C|A/R|I|I|I|I|
|Independent Review|I|I|I|C|C|C|C|A/R|I|I|I|
|Risk Acceptance|C|A(项目风险)|C|I|I|C|C|C|A(发布相关)|I|C(安全相关)|
|A7 Release 批准|I|C|I|I|I|C|C|C|A/R|I|C|
|Knowledge Harvest|I|I|A/R|C|C|C|C|C|I|C|I|
|知识正式提升/撤权|I|I|C|C|C|C|I|I|I|A/R|C|

关键边界：

- **产品负责人**定义产品层“什么算完成”；主理人 + Verification 把它变成可执行、可取证的 Acceptance Criterion；
- **测试/HIL Owner**负责正确执行 case 和保存原始结果；**Verification**负责判断这些结果能证明什么；
- **硬件工程师**对 schematic、board revision、电气/时序测量等硬件事实负责；软件日志只能提出假设，不能替代测量；
- **Risk Acceptance**不能改变 Verification 事实状态；
- **Release Owner**承担 A7 发布批准，不由 Runtime、实现者或 Verification 自动获得。

详细说明：[跨团队 RACI](../03-角色与领域/02%20跨团队RACI.md)

## 07. 术语与一次任务走查

### 常用术语

|术语|辅助类比|通俗说明|本体系对应物|不要误解为|
|---|---|---|---|---|
|专家团|技术部门|一组稳定职责和工作规则，对外承接工程任务|1+7 角色 + Task/Gate/Evidence|不是一堆聊天机器人|
|主理人|项目调度 / 流程中枢|管任务、路由、Gate、恢复和收口|`embedded-system-team-lead`|不是万能专家|
|Expert Role|岗位职责|稳定专业判断边界|7 个专业角色|不等于某个模型|
|Runtime|工程工具 / 工作台|在真实工作树和环境里执行分析、修改、构建|Codex / Claude / IDE / Internal Runtime|不是领域身份|
|Skill|标准作业方法 / 工具按钮|可复用工程方法|23 个 P0 Skill|不自动扩大权限|
|Gate|质量门|条件不到不能进入下一阶段|K/M/0/T/E/V/R/C|不是会议本身|
|Receipt|施工记录|记录实际发生了什么|Delivery / Runtime Receipt|不是 Verification|
|Evidence|原始凭据|支撑 Claim 的可追溯事实|SHA / log / hash / device / HIL|不是语言置信度|
|Verification|独立质检|判断证据证明到了哪一层|7 层 Verification|不是最终放行|
|Review|放行审查|判断证据、风险和例外是否足以交付|Gate R|不是再跑一次测试|
|Run|一次受控工程实例|可恢复、可审计、可 supersede|`work_item_id / run_id`|不是聊天会话|
|SSOT|唯一权威来源|某类事实只认一个原始 Source|Git / CI / HIL / NAS / 正式文档|Knowledge Provider 不自动成为权威|

> 类比只帮助理解，不参与规范推导。正式定义以机器 Contract 和工程手册为准。

### 示例：UBIFS 长稳后异常只读

> 这是走查示例，**不计入 real Pilot evidence**。

|步骤|工程动作|关键产物|关键判定|
|---:|---|---|---|
|1|接到“设备长稳后 UBIFS 变只读”|Task Brief|先冻结目标与验收，不猜根因|
|2|确认 kernel/BSP/board/firmware/log/device identity|Material Manifest|身份冲突先 BLOCK|
|3|路由 `diagnostic_chain`，拉 Debug + BSP|Routing Decision|不默认 full-chain|
|4|建立时间线与 H1~Hn 假设|Technical Analysis + Hypothesis Registry|Observed / Inferred / Confirmed 分开|
|5|用 ECC/MTD/BDMA 等区分实验收敛|Evidence refs|实验必须能排除候选|
|6|形成最小修改、风险、回滚、验证计划|Technical Decision|方案未足够不进工程|
|7|按 exact base 修改/构建/受控测试|Engineering Package + Delivery Receipt|实施成功不等于验证通过|
|8|原复现、ECC 正/负 case、长稳/掉电按需|Verification Report|只给直接证据支持的层级 PASS|
|9|独立审查吞错、数据完整性、回滚风险|Review Report|P0/P1 不可被普通 waiver 掩盖|
|10|收口并沉淀可复用规则或 `NO_KNOWLEDGE_DELTA`|Deliverable Manifest + Knowledge Harvest|真实 Pilot 才计成熟度证据|
