## 2. 数字研发组织

```text
嵌入式系统数字员工团队
│
├─ M1 技术规划与工程编排
│  ├─ P01 嵌入式技术负责人
│  └─ P02 嵌入式系统架构师
│
├─ M2 Linux / BSP 平台
│  └─ P03 Linux / BSP 平台工程师
│
├─ M3 MCU / RTOS 底层固件
│  └─ P04 MCU / RTOS 固件工程师
│
├─ M4 驱动与组件平台
│  └─ P05 驱动与组件工程师
│
├─ M5 调试与可靠性
│  └─ P06 系统调试与可靠性工程师
│
└─ M6 验证与技术治理
   ├─ P07 Verification / HIL 工程师
   └─ P08 独立技术审查工程师
```

概念关系固定为：

```text
Module   = 职能模块，只用于组织理解和能力规划
Position = 数字岗位的人类职责视图
Agent    = 承担岗位的数字员工定义
Skill    = 数字员工掌握的标准工程技能
Runtime  = 可替换的工程工作台
```

**Module 不参与机器路由。** 真实任务仍由 Task Type、Workflow Mode 和 Agent Routing 决定。

## 3. 一项任务怎么运行

```text
产品 / 项目 / 现场 / 测试
          │
          ▼
    Work Item / Run
          │
          ▼
  K → M → 0 → Triage
          │
          ▼
      Domain Analysis
   ┌────┬────┬────┬────┐
  架构  BSP  MCU  Driver  Debug   ← 只拉必要岗位，可并行
   └────┴────┴────┴────┘
          │
          ▼
          T
          │
    需要工程实施？
          │
          ▼
     E → Engineering
          │
          ▼
     V → R → C
 Verification  Review  Closure
```

其中三条边界必须始终成立：

1. **专业判断 ≠ 工程实施**：专家岗位定义约束和技术判断，工程师 + 受控 Runtime 执行修改/构建/测试；
2. **实施完成 ≠ Verification PASS**：证据只能证明它直接覆盖的层级；
3. **Verification PASS ≠ Release 已批准/已执行**：风险审查和高风险动作仍有独立责任人及人工 Gate。

详细阶段、失败回流和不同 mode 路径只在 [任务生命周期与 Gate](../03-流程与运行/01%20任务生命周期与Gate.md) 展开。

## 4. 五条身份与证据原则

- **一项任务一条主身份链**：Work Item → Run → exact source → artifact → device → test/HIL → evidence → Verification → Review；
- **Source of Truth stays at source**：索引、总结和 Knowledge Provider 不取代原始权威 Source；
- **Observed / Inferred / Confirmed 分开**：推断不能悄悄升级为事实；
- **能力等级 ≠ 动作权限**：岗位再强也不能自动获得设备写入或发布权限；
- **Runtime 可替换，工程规则不变**：换 Codex、Claude、IDE Agent 或其他 Runtime，不改变岗位职责、Gate 和 Verification 语义。

详细身份与证据模型见 [身份证据与知识架构](../02-架构设计/03%20身份证据与知识架构.md)。

## 6. 当前推进重点

当前缺口不是继续扩写架构或复制规则，而是取得真实工程证据：

`Debug real Pilot → Feature real Pilot → Review/Release real Pilot → Knowledge reuse → Multi-runtime → Productionization Review`

因此后续内容调整应由真实任务暴露的职责、Skill、流程或证据缺口驱动；本总览只维护**稳定模型、关键边界和导航**，不再复制详细规则表。
