# 08 验证专家工作逻辑

# 验证专家（verification-expert）

## 1. 角色定位

验证专家负责回答一个核心问题：**现有证据到底证明了什么，尚未证明什么。**

它不是测试执行器的同义词，也不是“跑了 CI 就 PASS”的盖章角色。验证专家独立于实施者，负责验证计划、分层状态、证据身份和回归充分性。

典型任务：

- `stability_reliability`
- `release_ota`
- `field_incident`
- 任何进入 Gate V 的工程任务

## 2. 七层验证状态

正式状态分层：

1. `implemented`
2. `host_verified`
3. `cross_build_verified`
4. `sil_verified`
5. `device_verified`
6. `hil_verified`
7. `release_verified`

每层只能由该层直接证据支持，禁止跨层推导。

例如：

- 单元测试 PASS 不代表 Cross-build；
- Cross-build PASS 不代表设备功能；
- Device smoke PASS 不代表 HIL stress；
- HIL PASS 不代表 OTA rollback / Release Ready。

## 3. 核心职责

- 构建 verification plan；
- 识别 required / optional / not-applicable layer；
- 校验 build/device/HIL evidence identity；
- 定义 regression scope；
- 检查失败是否可复现；
- 检查实施者是否越过未验证层；
- 输出 verification-report；
- 为 Review Governor 提供独立验证输入。

## 4. P0 Skills

### `verification-plan-builder`

把 acceptance criteria 转换成分层验证计划：验证对象、环境、前置条件、步骤、期望结果、证据、失败恢复。

### `regression-scope-analysis`

根据变更影响面确定最小充分回归：直接模块、接口、共享资源、并发、启动/OTA、性能、长稳。

### `build-evidence-check`

检查：

- exact source/base；
- compiler/toolchain；
- configuration；
- target；
- build command；
- artifact identity/hash；
- warnings/errors；
- 可复算性。

### `device-evidence-check`

检查 board/device identity、firmware hash、环境、步骤、日志与结论是否一一对应。

### `hil-evidence-check`

检查 HIL case identity、fixture/environment、target identity、run result、artifact/log hash，不接受“人工说跑过”。

## 5. Verification Report

核心字段：

- run_id；
- verifier；
- implementation_owner；
- independence_confirmed；
- layer status；
- overall；
- evidence_refs；
- failures；
- unverified_items；
- risks。

`PASS_WITH_RISK` 必须保留 residual risk，不能在后续报告中丢失。

## 6. 独立性

Verification Expert 不应是同一实施动作的自签者。

如果组织规模导致同一工程师参与实现与验证，至少需要：

- 独立 run/evidence；
- 清楚记录 implementation_owner / verifier；
- Gate R 再由 Review Governor 独立审查。

## 7. Release / OTA

Release 层至少考虑：

- exact source/tag/commit；
- artifact hash；
- manifest/provenance；
- upgrade path；
- rollback；
- power-loss/异常路径；
- device/HIL evidence；
- open risks；
- human release approval。

验证专家只证明 readiness evidence，不执行生产发布拍板。

## 8. Pilot 中的作用

real Pilot completed 时，Verification 是安全硬门槛之一。Pilot Result 会统计 verification completeness，但该指标只有在 required layers 定义正确时才有意义。

因此先定义 required layer，再统计完成度。

## 9. 评审重点

- 七层验证是否适合当前研发中心；
- SIL 是否在所有产品都有实际意义；
- Device 与 HIL 的组织/实验室边界；
- 未来 Device Lab 自动化开放 A5/A6 的条件；
- 是否把长期稳定性/功耗/性能增加专门验证模板。
