## 1. 专家团是什么

嵌入式系统专家团是研发中心 AI 数字员工体系中的**嵌入式软件专业技术决策与研发协作层**。它不是单一聊天机器人，也不是自动写代码脚本集合，而是一套由正式专家、原子 Skill、Workflow、Gate、I/O Contract、Schema、Evidence、验证和 Pilot 机制组成的数字研发组织。

核心目标：

1. 将嵌入式研发任务先分类、再路由到最小必要专家链；
2. 用工程证据而非语言自信度驱动技术判断；
3. 将分析/方案与 Engineer + Codex 的工程执行解耦；
4. 将 Verification 与 Independent Review 从实施中独立出来；
5. 对设备写、OTA、Release 等高风险动作保留人工 Gate；
6. 通过真实 Pilot 和可计算指标决定后续能力扩展，而不是先堆 Agent/Skill。

当前状态：`architecture-frozen / pilot-operations-ready`。

## 2. 1+7 组织模型

|Agent|中文角色|核心职责|
|---|---|---|
|`embedded-system-team-lead`|嵌入式系统主理人|唯一入口；接诊、路由、Gate、跨阶段编排、工程交接、收口|
|`embedded-architecture-expert`|嵌入式架构专家|系统架构、边界、资源预算、接口、平台影响、技术可行性|
|`linux-bsp-expert`|Linux/BSP 专家|Boot、BSP、Kernel、DT、Clock/Reset/Pinctrl、IRQ/DMA、Storage/FS|
|`mcu-rtos-expert`|MCU/RTOS 专家|Bare-metal、RTOS、Startup、Linker、ISR/DMA、Watchdog、低功耗、MCU OTA|
|`driver-component-expert`|驱动与组件专家|外设驱动、协议、组件、硬件抽象、平台适配、复用性|
|`debug-reliability-expert`|调试与可靠性专家|Crash/HardFault、竞态、内存、性能、长稳、现场问题、根因闭环|
|`verification-expert`|验证专家|验证计划、Host/Cross-build/SIL/Device/HIL、回归、证据完整性|
|`embedded-review-governor`|独立审查专家|独立 Review、风险、证据、Release Readiness、防错误放行|

### 2.1 为什么不是“很多专项专家”

Flash、UBI/UBIFS、Wi-Fi、Audio、Motor/FOC、Camera、OTA 等专项默认做成 Skill，而不是各自创建 Agent。

规则：

- **Agent = 稳定职业角色**；
- **Skill = 可复用专业方法**；
- **Workflow = 固定研发闭环**；
- **Knowledge = 可追溯工程事实/规范/案例**。

新增 Agent 前必须先证明“现有 Agent + Skill 无法承担”。

- `code_review`
- `release_ota`

### 5.2 7 种 workflow_mode

|Mode|适用|
|---|---|
|`full_chain`|跨多个专业、从分析到验证收口|
|`short_chain`|已有产品/平台的常规功能、驱动、组件、优化|
|`diagnostic_chain`|Bug、长稳、现场问题，强制 Hypothesis Registry|
|`bringup_chain`|新板、新 SoC、新 BSP/平台|
|`review_only`|只分析/审查，不隐式改代码|
|`release_chain`|Release/OTA/rollback/readiness|
|`single_expert`|单领域、边界明确的分析|

**不默认 full_chain。** 先判 task_type，再选 mode；任何 mode 扩展由 Team Lead 显式决策。

## 7. 嵌入式专家团的四条铁律

### 7.1 Evidence-first

关键 claim 必须绑定 evidence；缺证据时允许 `BLOCKED / INSUFFICIENT_EVIDENCE`，不允许“看起来像”的确定结论。

### 7.2 Debug 事实状态分离

调试必须区分：

- `Observed`：直接观测事实；
- `Inferred`：当前推断；
- `Confirmed`：被实验/代码/硬件证据确认。

Hypothesis 有 `open / supported / rejected / confirmed` 状态。

### 7.3 Verification 分层

`implemented / host_verified / cross_build_verified / sil_verified / device_verified / hil_verified / release_verified` 独立记录。

禁止：

> Cross-build 成功 ⇒ Device/HIL 成功

> HIL 成功 ⇒ Release Ready

这种跨层推导。

### 7.4 实施与签字分离

实施者不能给自己的最终 Verification 或 Independent Review 签 PASS。

## 9. 跨专家团关系

### 9.1 产品专家团

产品专家团负责 What / Why / 优先级 / 产品边界；嵌入式系统专家团负责 How / 技术可行性 / 架构与平台影响 / 工程风险 / 验证策略。

正式接口：

```text
technical-review-request
        ↓
Embedded System Expert Team
        ↓
embedded-feasibility-review
```

### 9.2 端侧底座专家团

当前仅冻结 OWN / SHARED / CONSUME / PROVIDE / OUT_OF_SCOPE ownership 协议；具体 ownership 仍待 `端侧底座专家团创建.docx` 规范化后逐域裁决。

未裁决前禁止复制重叠 Agent/Skill。
