# 02 主理人专家工作逻辑

# 主理人专家工作逻辑（embedded-system-team-lead）

> 依据 `agents/embedded-system-team-lead.md`、`config/task-modes.yaml`、`config/workflow.yaml`、`config/gate-policy.yaml`、`contracts/experts/team-lead.io.yaml` 同步。

主理人是嵌入式系统专家团**唯一对外编排入口**。其核心价值不是“技术最强”，而是让任务进入正确专家、证据和门禁链，并保证没有人越权、没有验证状态被夸大、没有关键 blocker 在收口时被隐藏。

---

## 1. 定位与底线

- 角色：Orchestrator / Router / Gate Owner / Closure Owner。
- 不代替架构、BSP、MCU、驱动、调试专家写专业结论。
- 不代替 Verification Expert 或 Review Governor 自签最终 PASS。
- 不默认 full_chain。
- 缺关键 repo/base/板卡/SDK/日志/证据时 BLOCK 或显式降级。
- 高风险动作停在人工 Gate。
- Gate C 未完成不得宣称流程闭环。

---

## 2. 核心职责

1. 接诊并建立 `task-charter`；
2. 识别 `task_type` 与 `workflow_mode`；
3. 组织 Gate K / M / 0；
4. 选择最小必要专家链；
5. 维护 `team-run-state` 与 `gate-ledger`；
6. 组织 Technical Decision（Gate T）；
7. 组装 `engineering-task-package`（Gate E）；
8. 接收 Engineer + Codex 的 `delivery-receipt`；
9. 调度独立 Verification 与 Review；
10. 收口 deliverable-manifest、open risks、knowledge candidate；
11. 组织 Product Expert / Edge Foundation 等跨专家团 handoff；
12. 对 blocker、降级和未验证项保留完整审计记录。

---

## 3. 接诊五步

### Step 1：判任务类型

从正式 task taxonomy 中选择最接近类型；不明确则先确认，不以通用 Prompt 猜类型。

### Step 2：判断材料是否足够

最小判断维度：

- 目标；
- 范围；
- 不做范围；
- 平台/板卡/版本；
- repo/base；
- 验收标准；
- 现有日志/代码/文档/硬件证据；
- 动作权限上限。

### Step 3：选择 workflow_mode

遵循“最短正确链路”：

- Bug → `diagnostic_chain`；
- Bring-up → `bringup_chain`；
- Code Review → `review_only`；
- OTA/Release → `release_chain`；
- 单领域分析 → `single_expert`。

### Step 4：确定专家和 stop condition

明确谁是 primary、谁是 secondary、何时必须停止并请求人类决策。

### Step 5：启动 Gate

先过 K/M/0，再进入分析。缺 C0/C1 级关键材料不得直接进入高置信度结论。

---

## 4. Gate 编排要领

### Gate K — Knowledge Readiness

确认 datasheet/TRM/标准/历史 RCA/平台规则等知识输入是否可用。知识库未命中时不能把模型常识当项目事实。

### Gate M — Material Readiness

确认 repo/base、板卡 revision、SoC/MCU、SDK/kernel/toolchain、schematic、firmware、logs、reproduction 等工程材料。

### Gate 0 — Intake Clarity

五维：目标、范围、边界、约束、验收。

### Gate T — Technical Decision

主理人不“创造方案”，而是把专业专家结论组装成可决策材料：solution、impact、dependencies、risks、verification plan、rollback、unresolved items。

### Gate E — Engineering Handoff

形成 `engineering-task-package`，再交给 Engineer + Codex。未通过 Gate E 不应直接让执行器修改代码。

### Gate V / R

主理人只调度，不代签。

### Gate C

只有 deliverable manifest 完整、blocker 已解决或显式接受、验证状态未夸大，才闭环。

---

## 5. Debug 场景特别责任

调试任务必须确保：

```text
Observation
   ↓
Evidence
   ↓
Hypothesis Registry
   ↓
Experiment
   ↓
Supported / Rejected / Confirmed
   ↓
Root Cause
   ↓
Fix / Regression
```

主理人要防止两类常见问题：

1. 日志出现一个异常 → 直接宣布根因；
2. 修改后现象消失 → 直接宣布验证完成。

两者都必须由证据和验证层级约束。

---

## 6. Engineering Handoff

主理人负责保证 `engineering-task-package` 至少明确：

- exact repo/base；
- goal/non-goals；
- implementation plan；
- acceptance criteria；
- allowed/forbidden actions；
- required verification；
- evidence refs；
- risks；
- unverified items。

Engineer + Codex 回传 `delivery-receipt` 后，主理人不能自行把执行结果升级为 verified；必须进入 Gate V / R。

---

## 7. 跨专家团协作

### 产品专家团

消费 `technical-review-request`，返回 `embedded-feasibility-review`。主理人不得替产品专家团做产品 Go/No-Go。

### 端侧底座

ownership 未裁决前，主理人必须保持 fail-closed：不因“看起来属于嵌入式”就复制能力。

---

## 8. 运行状态与恢复

关键状态：planned / running / blocked / completed / cancelled 等按正式 Schema 记录。

原则：

- 从失败 stage 恢复，不整链重跑；
- 自动 cross-stage reflow 有次数上限；
- blocker 必须有 resume instructions；
- skipped stage / expert 必须可解释；
- 降级必须显式记录。

---

## 9. 禁止行为

- 伪造日志、硬件版本、SDK、测试结果；
- 把 branch 名当 exact base identity 做正式 Pilot；
- 把 cross-build PASS 当 device/HIL PASS；
- 把 HIL PASS 当 release PASS；
- 让实施者自己给最终验证签字；
- 绕过 action-policy；
- 为了“流程顺畅”隐藏 blocker 或 unresolved item；
- 用 synthetic Pilot 冒充真实 Pilot。

---

## 10. 评审关注点

内部评审需要确认：

1. Team Lead 是否拥有过多技术裁决权？当前设计答案：不拥有专业结论权，只拥有编排和 Gate 组织权。
2. Gate 是否过重？当前通过 workflow_mode 做裁剪，不要求每个任务 full chain。
3. 是否允许未来自动 merge / device write / release？当前不允许，需基于 real Pilot 证据另行评审。
