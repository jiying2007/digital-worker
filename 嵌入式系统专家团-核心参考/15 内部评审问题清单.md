# 15 内部评审问题清单

> 同步基线：`v0.7.0 / provider-neutral`
>
> 本文用于评审专家团组织与治理；总体 Provider 选型同时参见 16。

## A. 组织

### A1 1+7 是否接受？
建议接受；专项优先 Skill 化。Security 是否升正式 Agent 由真实任务证据决定。

### A2 Team Lead 是否只编排、不代写专业结论？
建议接受。

## B. Workflow / Gate

### B1 14 task types + 7 modes？
建议作为当前 baseline，Pilot 后按证据调整。

### B2 Gate K/M/0 是否分离？
建议底层保持分离，UI 可合并。

### B3 Verification / Review 是否职责独立？
建议职责不可合并，内容可按 mode 裁剪。

## C. 专业边界

Linux/BSP vs Driver、Architecture vs Edge Foundation、Audio/FOC/Wi-Fi/Flash 是否 Agent 化等按 ownership/Skill 原则处理；端侧底座由 #11 裁决。

## D. Engineering Handoff

### D1 是否保持“办公/交互入口与工程执行 Contract 松耦合”？
**建议接受。** 不再把问题表述成 WorkBuddy vs Codex；任何 Interaction Provider 都不能天然遥控个人 Engineering Runtime/设备。

### D2 exact base 是否强制？
真实 Pilot 和正式执行强制。

### D3 是否允许多个 Engineering Agent Runtime？
建议允许，并通过 #18 用统一 Contract 对比至少两个 Runtime；默认/备用/特定任务 Runtime 由证据决定。

## E. Evidence / Verification

分层 Verification 建议接受；defect/stability/field incident 强制 Hypothesis Registry；`incorrect_pass_rate=0` 保持安全硬门槛。

## F. Autonomy

P0 Skill 上限 A2 建议保持；A3/A4 由受控 Engineering Runtime 执行；A5 不全局开放；A6/A7 保持人工 Gate。Action Level 与 Provider 品牌无关。

## G. Knowledge / Data

### G1 是否接受 Source of Truth stays at source？
**建议接受。** 不提前规定飞书或 WeKnora 为全企业唯一知识主库。

### G2 Knowledge 方案是否先做 Source Inventory + PoC？
**建议接受。** #16 覆盖飞书、NAS、Git、CI/HIL 等真实 Source，并比较集中式/联邦式/Hybrid。

### G3 Context Broker 是否立即建设？
建议先作为概念和接口验证；只有 PoC 证明收益后再平台化。

### G4 原始日志/core/firmware 是否进 digital-worker？
建议不进，只保留受控引用/hash/evidence bundle。

## H. Provider 选型

### H1 WorkBuddy/飞书/WeKnora/Codex/Claude 是否现在冻结？
**建议不冻结。** 由 #17 Capability Matrix + #16/#18 PoC 决定。

### H2 是否要求 fallback / exit plan？
建议所有默认 Provider 必须有 fallback 或迁移路径。

### H3 Provider 能力是否按角色分别证明？
建议接受。一个产品可承担多个角色，但 Interaction/Work Item/Knowledge/Runtime/Action 必须分别验真。

## I. Pilot / Productionization

3 个 real Pilot 是进入第一次评审的最低资格，不是成熟证明。首批建议覆盖 Debug、Feature、Review/Release，并加入一个材料不完整案例验证 BLOCK 能力。

## J. 跨专家团

产品 handoff 建议接受；端侧底座 ownership 为 P0；HIL/Platform Abstraction/OTA 的共享边界应基于 ownership map。

## K. GitHub / Governance

### K1 main protection？
建议立即启用 `Embedded Expert Contracts / validate` required check，#12 跟踪。

### K2 merged branch 是否及时 GC？
建议接受 `docs/governance/branch-lifecycle.md`：默认只长期保留 main，任务分支 merge + main CI success 后删除；#19 处理当前残留。

## 建议本轮形成的 12 个 Decision

1. 1+7 组织模型；
2. task taxonomy / workflow modes；
3. Verification / Review 独立性；
4. P0 Skill A2 上限；
5. Provider-neutral Engineering Handoff；
6. exact base / Evidence-first / verification layering；
7. Source-of-Truth-stays-at-source；
8. Knowledge Source Inventory / PoC；
9. Multi-runtime Pilot；
10. Provider Capability Matrix + fallback；
11. ownership / main protection / branch lifecycle owner；
12. Productionization Review 评审人和门槛。

## 评审输出

Decision List、Owner、due date、blocker、是否启动 real Pilot/PoC、ADR-003 是否 accepted/revise/remain proposed，以及本目录是否从 `review-ready` 升级为 `reviewed-baseline`。
