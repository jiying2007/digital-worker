# 15 内部评审问题清单

> 本文用于内部评审会直接逐项拍板。建议不要逐字评审所有文档，而是优先对以下架构/治理问题形成 Decision。

## A. 组织与角色

### A1. 是否接受“1+7”作为当前正式组织？

**当前建议：接受。**

理由：已覆盖嵌入式系统主要职业角色，专项能力先 Skill 化，避免 Agent 爆炸。

需要拍板：是否缺少 Security 专家作为正式 Agent，还是先保持 Review Governor + 后续 Skill。

### A2. Team Lead 是否只做编排、不代写专业结论？

**当前建议：接受。**

否则主理人会变成万能专家，破坏专业责任和独立 Review。

---

## B. Workflow / Gate

### B1. 是否接受 14 类 task_type + 7 类 mode？

**当前建议：接受为 V1 baseline。**

Pilot 后允许增删，但必须有真实任务证据。

### B2. Gate K / M / 0 是否太复杂？

**当前建议：底层保持分离，UI 可合并展示。**

- K = 知识是否够；
- M = 工程对象是否明确；
- 0 = 任务是否清楚。

三者解决不同风险。

### B3. Verification 与 Independent Review 是否所有任务都必须完整跑？

**建议：职责不可合并，内容允许按 mode 裁剪。**

---

## C. 专业职责边界

### C1. Linux/BSP 与 Driver/Component 的边界是否清楚？

当前：平台资源/内核集成归 BSP；设备协议/组件复用归 Driver。

### C2. Architecture 与端侧底座 Architecture 是否重叠？

**未决。** Issue #11 必须依据原文做 ownership。

### C3. Audio/FOC/Wi-Fi/Flash 是否要独立 Agent？

**当前建议：不要。**

先 P1 Skill Pack，除非多项目证明存在独立职业角色和专属 workflow。

---

## D. Engineering Handoff

### D1. 是否继续保持 WorkBuddy 不直接遥控个人 Codex？

**当前建议：一期保持。**

未来可以加受控 Runner/Gateway，但不要破坏输入输出 Contract。

### D2. 是否强制 exact base SHA？

**建议：真实 Pilot 和正式交付强制。**

一般分析可使用 branch context，但进入 execution/pilot 必须冻结 identity。

---

## E. Evidence / Verification

### E1. 是否接受 Host/Cross-build/SIL/Device/HIL/Release 分层状态？

**建议：接受。**

这是防止嵌入式场景“编译过=设备好了”的关键治理机制。

### E2. Hypothesis Registry 是否对所有 Bug 强制？

**当前建议：对 defect/stability/field incident 强制。**

极简单问题也可以很轻量，但不能跳过事实/假设区分。

### E3. `incorrect_pass_rate=0` 是否过严？

**建议：安全门槛保持 0。**

小样本下一个 incorrect PASS 就应触发复盘，而不是用平均数稀释。

---

## F. Autonomy

### F1. P0 Skill 上限 A2 是否合适？

**建议：Pilot 阶段保持。**

A3/A4 仍由 Engineer + Codex 受控执行。

### F2. 是否允许 A5 Device Read 默认开放？

**建议：暂不全局开放。**

未来可按实验室设备 allowlist + 审计逐步开放。

### F3. A6 Device Write 是否可以会话级授权？

**待评审。** 建议先在专用测试设备验证 Capability Broker/锁/恢复机制后再开。

### F4. A7 Release 是否自动化？

**当前建议：不自动。**

---

## G. Knowledge / Data

### G1. 飞书 canonical + WeKnora retrieval 是否接受？

**建议：沿研发中心 V2，不在 embedded team 复制企业知识主库。**

### G2. 原始现场日志/core/firmware 是否进 digital-worker？

**建议：不进。** 仅保留受控引用、hash、结构化 evidence bundle。

---

## H. Pilot / Productionization

### H1. 第一轮 Pilot 是否 3 个任务？

**建议：3 个是进入第一轮评审的最低资格，不是证明成熟。**

三轨后可再决定是否扩大样本。

### H2. Pilot 首批任务如何选？

建议：

- Debug：有历史人工根因、证据完整但具有真实复杂度；
- Feature：中等规模驱动/组件，不选纯文档小改；
- Review/Release：真实 PR 或 OTA readiness，存在明确人工基准。

### H3. Production Ready 谁拍板？

必须是独立人工 Productionization Review，不由 Expert Team 自己改状态。

---

## I. 跨专家团

### I1. 产品专家团 handoff 是否接受？

**建议：接受。** What/Why 与 How/Feasibility 分离合理。

### I2. 端侧底座 ownership 何时完成？

**建议：P0。** 至少在首批真实 Pilot 涉及域开跑前完成局部裁决。

---

## J. GitHub / 治理

### J1. 是否启用 main branch protection + required `Embedded Expert Contracts / validate`？

**建议：立即启用。** 当前 Issue #12 已登记，属于正式生产化前必做。

### J2. 是否要求至少 1 位 Reviewer 才能 merge？

建议在内部评审确定 reviewer pool 后启用，避免仅靠 AI/作者自审。

---

# 建议本次评审形成的 10 个明确 Decision

1. 接受/修改 1+7 组织模型；
2. 接受/修改 task taxonomy 与 workflow modes；
3. 接受 Verification / Review 独立性；
4. 接受 P0 Skill A2 权限上限；
5. 接受 Engineering Handoff + Codex 松耦合；
6. 接受 exact-base / Evidence-first / verification layering；
7. 确定首批 3 个 real Pilot；
8. 指定端侧底座 ownership 裁决 owner 和时限；
9. 指定 main protection 管理员和 required check；
10. 确定 Productionization Review 的评审人/门槛，不允许专家团自我宣布上线。

# 评审输出建议

会议结束至少形成：

- Decision List；
- 修改项 Owner；
- due date；
- blocker；
- 是否允许启动 #6/#7/#8 real Pilot；
- 是否接受本文档集从 `review-draft` 转为 `reviewed-baseline`。
