# 案例：器件替代兼容性走查

> 流程示例。可用于 Wi-Fi、Flash、Power、Sensor 等国产替代或第二供应商导入，不代表某个具体料号已经验证。

## 1. 场景

现有器件因成本、供应或国产化要求需要替换。新器件宣称 pin/API 兼容，但团队必须判断是否真的能在现有产品上量产使用。

## 2. 不能从“能编译”开始得出结论

至少建立 Compatibility Matrix：

|维度|核对内容|
|---|---|
|电气/板级|电压、电流、pin、reset、上电时序、外围器件|
|总线/协议|I2C/SPI/UART/SDIO/USB 语义和时序|
|初始化|寄存器、firmware、NVM/calibration|
|能力|缺失/新增 feature、限制条件|
|性能|吞吐、时延、功耗、温升|
|异常|timeout、掉线、坏块、brownout、reset 行为|
|软件接口|Linux/MCU API、DT、配置、版本兼容|
|生产|烧录、校准、ATE/老化、序列号/追溯|
|回归|直接功能和间接系统影响|

## 3. 架构与领域判断

架构先判断替代是否改变系统接口/资源/启动/OTA；BSP/MCU/Driver 分别证明平台资源、实时性和设备行为。采购提供供应信息，但不能替代工程兼容性结论。

## 4. 分阶段验证

```text
Datasheet/board compatibility
 → low-level communication
 → init/basic function
 → error/recovery
 → performance/power
 → system integration
 → stress/long-run
 → production calibration/test
```

早期失败就停止扩大测试，避免在明显不兼容时浪费系统级资源。

## 5. 负向和异常路径

替代最容易漏掉的不是基本功能，而是：

- 掉电/重启后恢复；
- timeout/retry；
- 热插拔/掉线；
- 边界温度/电压；
- flash bad block/ECC；
- Wi-Fi 弱网/漫游；
- power IC brownout/charge state；
- 生产校准或 NVM 差异。

## 6. 结论分级

建议区分：

- `LAB_COMPATIBLE`：实验室基本功能通过；
- `ENGINEERING_COMPATIBLE`：系统功能、异常、性能和长稳达到工程要求；
- `PRODUCTION_READY_CANDIDATE`：生产校准/测试、供应追溯和 Release evidence 也已准备；
- 最终量产导入仍由组织正式流程批准。

这些标签若要进入机器状态，需要后续真实 Pilot 证明后再 Schema 化；当前只作为评审表达。

## 7. Knowledge Harvest

Compatibility Matrix 是最值得沉淀的组织资产之一，但必须带产品/board/SDK/器件 revision 和 evidence；不要把“某项目可替代”传播成“所有平台通用替代”。
