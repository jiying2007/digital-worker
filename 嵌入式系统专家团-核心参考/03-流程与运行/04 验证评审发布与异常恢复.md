# 验证、独立评审、发布与异常恢复

> **本页是 Verification Layer、Independent Review Decision、Release/OTA Readiness 和异常回流的唯一详细人类流程来源。** 专业 SOP 只解释岗位怎么执行，不维护第二份层级/Decision 定义；机器权威仍在 Expert/Workflow/Schema Contract。

## 1. 为什么分三层

工程团队经常把下面三件事混成一个“PASS”：

1. 实施完成；
2. 测试/Verification 通过；
3. 可以放行或发布。

三者承担的风险不同，因此必须分别记录。

## 2. 七层 Verification

当前验证状态分为：

1. `implemented`
2. `host_verified`
3. `cross_build_verified`
4. `sil_verified`
5. `device_verified`
6. `hil_verified`
7. `release_verified`

每层只能由该层的直接 Evidence 支持。

|证据|能证明什么|不能自动证明什么|
|---|---|---|
|代码 diff / 单测|实现存在、部分逻辑正确|目标板能运行|
|Host test / static check|主机层行为|目标工具链/设备行为|
|交叉构建|目标工具链可构建|设备功能正确|
|SIL|仿真环境行为|真实硬件时序/电气行为|
|Device test|指定设备/固件条件下功能|长期/系统回归充分|
|HIL|指定 case/fixture 的系统行为|所有 Release 风险已处理|
|Release verification|指定候选版本的发布证据完整|人类 Release Owner 已批准或已执行发布|

## 3. Verification Plan 先定义 required layer

验证完整度只有在“哪些层必须跑”先确定后才有意义。

例如：文档/接口评审可能 `device/hil = N/A`；Linux Driver 新功能通常至少需要 cross-build + device；涉及关键硬件时序可能要求 HIL；OTA Readiness 通常需要 device + rollback/power-loss + release evidence。

不能为了让完成率变高，把失败层事后改成 N/A。

## 4. Independent Review

Verification 回答：**Evidence 证明了哪些层。**  
Review 回答：**现有 Evidence、残余风险和例外是否足以放行。**

Review Decision：

- `APPROVE`
- `APPROVE_WITH_RISK`
- `REQUEST_CHANGES`
- `BLOCKED`

Finding severity：P0/P1/P2/P3。P0 correctness、安全或不可逆风险原则上不能以普通 waiver 放行。

## 5. APPROVE_WITH_RISK

它不是“赶进度”的通道。至少写清 risk description、impact/scope、evidence、why accepted now、owner、expiry/target fix、rollback/containment 和有权接受的人。

后续报告不能把 residual risk 丢掉，也不能用 Risk Acceptance 改写 Verification 事实状态。

## 6. Release / OTA Readiness

Release 层至少检查 exact source/tag/commit、artifact hash/manifest/provenance、配置和目标型号、upgrade path、rollback、power-loss/异常路径、required device/HIL、open issue/waiver、Release Owner 和 A7 人工批准。

`release_chain` 默认做 Readiness，不自动执行生产发布。

## 7. 工程执行失败后的恢复

### Runtime 中断

记录已执行命令、worktree 状态、已生成 artifact、未完成步骤、Runtime identity 和 resume instructions。切换 Runtime 时沿用原 package，不重新发明任务边界。

### Build FAIL

回 Execution；如果 toolchain/config identity 不清，再回 Gate M/E。

### Device FAIL

先判断实现、设备/固件 identity、环境或 Acceptance 哪个出错，再返回具体责任阶段。

### HIL 不可用

如果 HIL 是 required layer，则保持 BLOCKED/NOT_RUN；可以经明确批准阶段性降级，但不能把低层 PASS 提升为 HIL PASS。

### Review REQUEST_CHANGES

Finding 指向责任阶段、修改对象和重新验证范围。修复后优先增量复验，不机械重跑全部链路。

## 8. 错误放行防线

以下情况优先 fail-closed：

- required evidence 缺失却 outcome=PASS；
- source/artifact/device identity 不一致；
- 实施者自签最终 Verification + Review；
- 未完成 A6/A7 人工 Gate；
- P0 Finding 未关闭；
- Release required rollback/provenance 缺失；
- 通过一个 Verification Layer 推导另一个层级。

`incorrect_pass_rate = 0` 是 Productionization 的安全硬指标。

## 9. 收口后的知识处理

任务结束后只做两种判断：

- `NO_KNOWLEDGE_DELTA`：没有新增可复用知识；
- `KNOWLEDGE_CANDIDATE`：存在新的 RCA、Design Rule、Compatibility、Known Issue、Checklist、Test Case 或 Skill candidate。

不要把每个任务都强制写成长文档；知识价值在于后续能被正确找到、判断适用范围并复用。
