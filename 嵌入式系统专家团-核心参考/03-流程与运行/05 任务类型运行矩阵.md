# 任务类型运行矩阵

> 本页展示 **canonical Edge Foundation routing semantics**。机器权威是 `domains/edge-foundation/routing.yaml`；Runtime mode policy 由 `domains/edge-foundation/runtime/task-modes.yaml` 约束。核心参考不维护第二套路由表。

## 1. Canonical routing matrix

| task_type | target mode | Embedded Capability | Assurance | 跨域/特别约束 |
|---|---|---|---|---|
| `feature_development` | `single_domain` | architecture / driver-component / mcu-rtos / linux-bsp（按影响面） | verification | 不默认 full surface |
| `defect_debugging` | `diagnostic` | debug-reliability，必要时 evidence-driven 扩展 | verification | 共享 Hypothesis Registry |
| `architecture_design` | `single_domain`（可 review） | architecture | verification | 只评审时可进入 review |
| `technical_feasibility_review` | `review` | architecture | review | 不隐式执行实现 |
| `platform_bringup` | `single_domain` | linux-bsp / mcu-rtos / driver-component | verification | 电气证据触发 Hardware Expert / multi_domain |
| `bsp_porting` | `single_domain` | linux-bsp | verification | exact BSP/board identity |
| `driver_development` | `single_domain` | driver-component / linux-bsp | verification | 电气/供电/信号证据触发 Hardware Expert |
| `component_development` | `single_domain` | driver-component / architecture | verification | stable API 与 regression scope |
| `mcu_firmware_development` | `single_domain` | mcu-rtos | verification | target build/device identity |
| `performance_optimization` | `single_domain`（可 diagnostic） | debug-reliability / architecture | verification | baseline → measure → remeasure |
| `stability_reliability` | `diagnostic` | debug-reliability | verification | long-run / recovery evidence |
| `code_review` | `review` | 由评审对象决定；默认不新增执行 Capability | review | execution forbidden |
| `release_ota` | `review` | 由 release candidate 对象决定 | verification + review | real device/release evidence；A7 human approval |
| `field_incident` | `diagnostic` | debug-reliability，必要时 evidence-driven 扩展 | verification | 现场 identity / containment / RCA |

表中 Capability 使用简称，完整 ID 均以 `embedded.*` 开头。所有任务默认 primary Domain Expert 是 `embedded-system-expert`；只有显式跨域 Evidence 才加入其他 Domain Expert。

## 2. 高层责任 mode

- `single_domain`：一个 Domain Expert 内完成，可使用多个 Capability；
- `multi_domain`：多个 Domain Expert，必须有跨域 Evidence；
- `diagnostic`：以 Timeline / Hypothesis / discriminating experiment 驱动；
- `review`：分析/审查路径，不自动获得 Engineering 或 Release authority。

Runtime 仍可以使用 `short_chain / diagnostic_chain / bringup_chain / review_only / release_chain / full_chain / single_expert` 等执行 mode，但它们只描述运行步骤；责任语义由本 canonical routing 决定。

## 3. 路由原则

1. 先确定 `task_type`；
2. 从 `routing.yaml` 得到 target mode、Expert、Capability、Assurance；
3. Edge Coordination 只加载必要 Capability；
4. 缺 Material/System Context 时 Gate M BLOCK；
5. 跨域升级必须给出 trigger Evidence；
6. Verification requirement 独立定义，不从任务复杂度猜测；
7. Review/Release 不因为 Hosted CI 绿就获得 Device/Release PASS；
8. Product readiness 不控制 routing authority。

## 4. Cross-domain triggers

当前机器 Contract 给 Bring-up / Driver 定义显式 Hardware escalation，例如：板级电气状态未知、原理图或电源时序不一致、外围电气接口不确定、signal/power cause 有直接迹象。没有这些 Evidence 时保持 Embedded 单域。

Structure Expert 同理：只有机械/结构事实成为问题必要条件时才由 Coordination 建立跨域 handoff，不预先塞进每条软件流程。

## 5. Assurance 与 Product readiness

Verification 是工程类和诊断类任务的核心 Assurance。Independent Review 在 review/release 场景仍是正式 Assurance；当前 iterative Pilot 若 Review unavailable，可使用 static checks + Hosted CI + traceable Verification evidence 完成 Pilot，但不能声称 Review PASS，也不能降低真实 Device/HIL/Release evidence 或 A7 human gate。

当前 Feature real Pilot 已形成 1 条 eligible receipt；Debug 与 Review/Release 尚未形成 eligible real receipt，因此 Product readiness 仍为 BLOCKED。该状态只表示产品成熟度尚未完成，不会把 canonical routing 回退到其他执行面。
