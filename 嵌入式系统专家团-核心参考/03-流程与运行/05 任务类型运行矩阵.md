# 任务类型运行矩阵

> **本页是 14 类 Task Type、默认/允许 Workflow Mode 和主责专业的唯一详细人类来源。** 总览、岗位和案例只引用，不复制第二份路由矩阵；机器权威仍是 `expert-groups/embedded-system/config/task-modes.yaml`。

这张表用于日常接单时快速判断“走哪条流程、谁主责、至少要留下什么”。表中的“典型验证”是工程起点，不替代 Task Brief/Verification Plan 对 required layer 的正式定义。

|---|---|---|---|---|---|
|`feature_development`|short_chain|short_chain / full_chain|架构、驱动、MCU、BSP 按影响面|架构影响、Engineering Package、Acceptance→Evidence|cross-build + device；系统级变化按需 HIL|
|`defect_debugging`|diagnostic_chain|diagnostic_chain|调试可靠性|共享 Hypothesis Registry、Root Cause/证据不足结论|原复现 + 受影响层回归|

## 1. 如何使用

1. 先定 `task_type`；
2. 使用默认 mode，除非有明确理由扩展/缩短；
3. 只拉必要专业角色；
4. Gate M 冻结 repo/base/board/device/material；
5. Gate T 前收敛跨专业接口、资源和风险；
6. 再由 Verification Plan 正式定义 required layer。

## 2. 三类容易选错的任务

### 性能优化

已知明确优化点通常走 `short_chain`；原因未知的性能异常应切 `diagnostic_chain`，先建立 baseline 和 Hypothesis。

### 架构设计

只做方案评审可使用 `review_only`；需要实际落代码则进入 `short_chain`。不要在 `review_only` 中顺手修改代码。

### BSP Porting

新平台/新板优先 `bringup_chain`；成熟平台的局部 BSP 适配可 `short_chain`，但仍保留 exact platform identity。

## 3. Mode 不是“复杂度等级”

`short_chain` 不代表可以跳过关键安全阶段；`full_chain` 也不代表质量一定更高。选择标准是任务边界和风险，而不是任务“看起来重要”。

## 4. 验证层的解释

表中的典型验证起点不能覆盖以下规则：

- required layer 必须在工程实施前或至少 Gate E 前明确；
- 事后不能为了提高完成率把失败层改成 N/A；
- 低一层 PASS 不向高一层推导；
- 文档/纯 review 类任务允许 device/HIL 为 N/A，但理由要明确；
- Release/OTA 的 rollback、power-loss、provenance 不能被普通 build PASS 替代。
